# M7.4 — Warden Eval Harness

*Draft spec v5 — fixture state is captured once at authoring time, not reconstructed live at eval-run time*

---

## Purpose

M7.1 gave us turn-by-turn readback of `game_events` / `adventure_telemetry` for manual playtest review. That manual pass over `playtest-2026-07-15.md` produced a taxonomy of ten confirmed Warden failure modes (see `docs/playtest-review/2026-07-15-taxonomy-report.md`). Two of those (`STATUS-FIELD-OVERLOAD`, `SNAPSHOT-GAP`) are already ticketed as direct fixes and are explicitly **out of scope** for this harness (see below) — their own regression signal is the next playtest report, not a scripted eval.

This milestone builds a scripted regression harness for the remaining eight categories: replay fixed, pre-seeded turns through the real turn pipeline, under one or more Warden prompt variants (via `WARDEN_PROMPT_OVERRIDE`), and assert whether each turn's known failure mode recurs.

**Deliverable:** a CLI script, not a UI, consistent with M7.1.

---

## Decisions Already Made

### The harness drives the real turn pipeline, in-process

Most of the taxonomy is about what happens around the completion, not the raw completion itself — tool-call sequencing, `roll_source`, whether a write lands, correction-loop behavior. The harness imports and calls `SessionService` directly (NestJS `TestingModule`-style bootstrap) against the same Drizzle client the real backend uses. HTTP, auth, and the controller layer are out of scope — that's the existing e2e/integration suite's job, not this tool's.

### Prompt variants go through `WARDEN_PROMPT_OVERRIDE`

No new prompt-swapping mechanism. The harness invokes against a given variant per run; A/B comparison is two runs plus a diff, not a built-in harness feature.

### Seeded state is captured once, at fixture-authoring time — not reconstructed live when the harness runs

**Corrected after further review.** An earlier version of this section had the harness calling `reconstructStateAsOfTurn` directly, live, on every run. That's the wrong default: `reconstructStateAsOfTurn` (M7.3, already implemented) does the right computation, but calling it fresh on every harness run would make a fixture's "fixed input" a moving target — fix a bug in the replay applier next month, and every historical fixture's seeded state silently shifts with it. A harness run could no longer distinguish "the prompt change helped" from "the replay engine's own behavior changed underneath the fixture" — exactly the non-determinism problem this spec already rejected once, for the rolling-summary question (see below).

The fix: `reconstructStateAsOfTurn` is called **once, at fixture-authoring time**, by a small new capture tool (this milestone's scope, not M7.3's — M7.3 is already implemented and isn't being revisited). Its output — `campaignState`, `gmContextBlob`, `pendingCanon`, `messages` — is written into the fixture file as literal, static content. The harness itself never calls `reconstructStateAsOfTurn` and has no runtime dependency on the source adventure's `game_events`/`pending_canon`/message history at all — it just seeds a fresh scratch adventure directly from whatever's frozen in the fixture file.

**New deliverable: `capture-fixture` CLI.** Thin wrapper around M7.3's existing `reconstructStateAsOfTurn(adventureId, targetSequenceNumber)`, invoked by hand once per fixture during authoring:

```
npx tsx scripts/capture-fixture.ts <adventure-id> <target-sequence-number> \
  --tag OUT-OF-ORDER-RESOLUTION \
  --id turn19-out-of-order-resolution \
  --output apps/zoltar-be/eval/fixtures/turn19-out-of-order-resolution.json
```

Writes a fixture file with `seededState` already populated from the reconstruction. The fixture author then hand-adds `playerInput` and `assertion` to complete it. This tool has no other logic of its own — it's `reconstructStateAsOfTurn` plus file I/O, same spirit as `save-synthesis`'s old role, just producing a richer artifact.

`reconstructStateAsOfTurn`'s output already includes `messages` up through the player message that triggers the target turn — see next section for why that's sufficient on its own, with no summary workaround needed.

### There is no rolling summary — confirmed, and no longer a fixture-authoring concern

**Investigated by CC during spec review; an earlier premise in this spec (that a per-turn narrative summary exists and would need to be pinned into fixtures) was wrong.** There is no summary-plus-recent-turns scheme. What actually runs (`session.window.ts`, `session.service.ts`) is a plain byte-capped rolling window: `buildMessageWindow()` walks the full persisted message history backward from the newest message, accumulating serialized size, and stops at `MESSAGE_WINDOW_MAX_BYTES` (40KB, hardcoded). Anything older is simply dropped from the prompt — no summary compensates for it. The `adventures.rollingSummary` column exists but is dead: nothing reads or writes it, consistent with `docs/decisions.md`'s record that rolling summarization was designed for M5 and explicitly deferred pending playtest evidence it's needed.

Since `buildMessageWindow` is a pure deterministic function of persisted message rows plus a fixed constant, and `reconstructStateAsOfTurn` (M7.3) already restores the actual `messages` rows as part of its output, there's nothing further this milestone needs to do here — no pinning, no synthetic summary text, no fixture-authoring workaround. This is resolved by M7.3's scope, not an open item for this spec.

### Judge model: Claude Sonnet 5 (`claude-sonnet-5`)

**Confirmed in review.** The Warden currently runs on Sonnet 4.6; the judge for judged-category grading runs on Sonnet 5. This is a deliberate, known asymmetry — Sonnet 5 is the eventual target for the Warden too, but that upgrade needs eval baselines first (which is what this harness is for), so the two models won't match until the Warden itself is upgraded. Revisit judge-model choice at that point; no action needed now beyond documenting why the mismatch exists.

> **Revisited 2026-08-03 — the trigger fired and the judge stays put.** The harness produced the baselines it existed to produce, and the Warden moved to `claude-sonnet-5`. The asymmetry this section described is therefore gone: generator and judge are now the same model, and every judged check self-grades.
>
> The judge was **not** pinned back to 4.6 to restore the gap. Pinning trades a self-grading bias for grader drift against a model the product no longer ships, and the second is worse precisely because nobody would be watching it — an unwatched grader is the failure mode this corpus has already hit twice.
>
> What this costs is real and is recorded rather than argued away: the 4.6 → Sonnet 5 comparison has a Sonnet 5 judge grading a 4.6 generator on one side and grading itself on the other, so its judged rows carry an asymmetry its structural rows don't. Two things bound it — `eval:judge-variance` measures grader stability against frozen input regardless of which model produced that input, and the two structural checks reach verdicts with no model in the loop at all. The honest next step is an independent grader, which means an Opus-tier judge; that is a cost question, not a design question, and it is open. See `decisions.md`, "Warden model upgraded to `claude-sonnet-5`."

### Judge rubrics: one per tag, not one per fixture

**Confirmed in review.** A single rubric per judged tag, with only the fixture-specific facts (perception boundary, expected resolution level) varying per fixture. Keeps rubric maintenance centralized instead of duplicated across fixtures.

### Fixture-count bar: 2 confirmed instances is sufficient coverage

**Confirmed in review.** Categories with only one confirmed instance so far (`MISSING-CANON-CAPTURE`, `UNSURFACED-CHECK`, `OVER-RESOLUTION`) need a second before being considered adequately covered — this is an action item for Alex to find in existing or future playtest data, not something CC needs to solve. The harness should support building/running a fixture set with fewer than 2 instances per tag without erroring, since coverage will fill in incrementally.

## Two Assertion Modes

### Structural assertions (deterministic, no second LLM call)

Checked directly against `game_events`, `adventure_telemetry`, and DB state after the turn completes.

| Tag | Assertion |
|---|---|
| `OUT-OF-ORDER-RESOLUTION` | Damage roll for an entity does not appear in the tool-call sequence before that entity's to-hit roll resolves. Damage/consequence rolls do not appear before the action they depend on has been declared by the player. |
| `SYSTEM-ROLLED-PLAYER-ACTION` | Dice rolls attributable to the player's own declared action carry `roll_source: player_entered` or produce a `dice_request` awaiting player input — not `system_generated`. |
| `UNAUDITABLE-MAPPING` | For rolls whose `purpose` indicates a narrative-selection/interpretation function (not pure mechanical resolution), the `purpose` string states the result-to-meaning mapping before the roll fires. |
| `MISSING-CANON-CAPTURE` | If the fixture's expected narration introduces a new spatial or plot-relevant detail not already present in `world_facts`, the turn's response includes a `world_facts` or `proposed_canon` write. |
| `NARRATING-PAST-A-BLOCK` | If the turn is blocked on missing data or an unresolved player dice_request, the response does not continue narrating events past the block point. |
| `UNSURFACED-CHECK` | Rolls that gate player-visible content produce a `dice_request` to the player rather than resolving system-side without disclosure. |

*(`STATUS-FIELD-OVERLOAD` and `SNAPSHOT-GAP` removed per review — no scripted eval for either; both are direct-fix tickets, validated by the next playtest report instead.)*

### Judge-graded assertions (fixed output, single grading call per fixture)

| Tag | Rubric basis |
|---|---|
| `HIDDEN-INFO-LEAK` | Fixture specifies the player character's actual perception boundary at this point. Judge call: does the response reveal anything — including specific roll values, thresholds, or mechanical outcomes — beyond that boundary? |
| `OVER-RESOLUTION` | Fixture specifies whether the action is on-screen or off-screen/summarized. Judge call: does roll count and granularity match the expected resolution level, or does it over-simulate off-screen content? |

Both rubrics are authored once per tag as part of this milestone (see "Judge rubrics: one per tag," above); fixtures supply only the per-instance facts (perception boundary text, resolution-level expectation) the rubric asks about.

## Fixture Format

```typescript
interface EvalFixture {
  id: string;                    // e.g. "turn19-out-of-order-resolution"
  tag: FailureModeTag;
  sourceAdventureId: string;
  sourceSequenceNumber: number;   // traceability back to the original report

  seededState: {
    // Captured once via `capture-fixture` at authoring time — literal,
    // static content, not a live reference. The harness seeds a scratch
    // adventure directly from this; it never calls reconstructStateAsOfTurn
    // or touches the source adventure's history at eval-run time.
    campaignState: Record<string, unknown>;   // MothershipCampaignStateSchema shape
    gmContextBlob: Record<string, unknown>;
    pendingCanon: PendingCanonRow[];
    messages: MessageRow[];                   // up through the triggering player message

    capturedAt: string;                       // provenance only, not used at eval-run time
  };

  playerInput: {
    type: 'message' | 'diceResult';
    content: string;
  };

  assertion:
    | { mode: 'structural'; check: string }
    | { mode: 'judged'; rubric: string; facts: Record<string, string> };
}
```

Fixtures live as versioned JSON/YAML files under `apps/zoltar-be/eval/fixtures/`, one file per fixture.

## Harness Invocation

```
npm run eval:harness -- \
  --fixtures apps/zoltar-be/eval/fixtures/ \
  --tag OUT-OF-ORDER-RESOLUTION,HIDDEN-INFO-LEAK \
  --prompt-variant mothership-m7-candidate-1.txt \
  --output report
```

A/B workflow is two invocations (baseline prompt, candidate prompt) plus a diff of the two reports — not a built-in harness feature.

## Testing the Harness Itself

For each structural assertion, build one deliberately-broken counterexample (e.g., a manually constructed tool-call sequence with damage before to-hit) to confirm the checker fails it, alongside the real fixture confirming it passes clean behavior. Without this, a checker bug could silently report false passes indefinitely.

---

## Out of Scope (This Milestone)

- `STATUS-FIELD-OVERLOAD` and `SNAPSHOT-GAP` — direct-fix tickets, no eval coverage.
- The agentic graph spike itself.
- HTTP/auth/controller-layer testing.
- Non-Mothership systems.
- CI integration — manually-invoked local tool for now, same status as the M7.1 report generator.
- Automatic fixture refresh/re-capture as part of normal eval runs. Fixtures are static once captured; re-running `capture-fixture` against a fixture's `id` is a deliberate re-authoring action (e.g., the source adventure's replay logic changed and old captures need refreshing), never something the harness does on its own.

## Dependency

This milestone's only touchpoint with it is consuming `reconstructStateAsOfTurn` from the new `capture-fixture` tool (see "Seeded state is captured once," above) — a one-time call per fixture at authoring time, not a runtime dependency of the harness itself.
