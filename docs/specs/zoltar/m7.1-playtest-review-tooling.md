# M7.1 — Playtest Review Tooling

**Spec status:** Claude Code handoff
**Depends on:** M7 complete (`SessionService` running the inner tool loop; `adventure_telemetry.payload` carrying `diceRolls`, `rulesLookups`, `toolLoopIterations`; `game_events` receiving `dice_roll` rows with `roll_source`; Warden prompt still a module-level constant in `apps/zoltar-be/src/session/wardens/`)

---

## Goal

Produce the first review artifact for real Mothership playtests against the production backend, plus the tooling that makes prompt iteration measurable. After M6/M7 the backend writes a dense telemetry row per turn and a full `game_events` log per adventure; nothing reads either, and the Warden prompt is a hardcoded const. M7.1 ships:

1. A new `WardensModule` housing flat-file Warden prompts, with hash+filename capture on every telemetry row so rapid prompt iteration during playtest is visible in the data.
2. Three SQL views that shape `game_events` + `adventure_telemetry` into review-friendly rows.
3. A TypeScript CLI that renders those views into a self-contained markdown report, including the exact Warden prompt text used during the run.
4. Save/load synthesis CLIs that freeze an adventure's starting conditions to a portable JSON file and clone them into a new campaign on demand — the mechanism for running the same scenario against different Warden prompts.
5. A sanity-check pass where the tool runs against a real Mothership adventure and the `adventure_telemetry` payload shape is adjusted if anything's missing or redundant.

The report is the durable artifact. The dev DB is transient — Claude Code sessions wipe it routinely, and pre-1.0 migration consolidation will wipe it deliberately. Everything a reviewer needs to evaluate a playtest run — prompt text, snapshot content, Claude responses, dice, lookups, validator output — lands in the markdown file so the file survives wipes the DB does not. Saved synthesis JSON files follow the same "durability belongs to the filesystem" principle.

No web UI. No cross-adventure aggregation. No automated CI runs. This is a human-driven review and iteration toolkit.

### M7.1's relationship to the first real playtest

M7.1 lands immediately before the first end-to-end playtest of the production stack (not the `zoltar-playtest` app). During that playtest, rapid prompt iteration is expected — sometimes within a single session, between turns. The versioning design accounts for this: filenames encode intent (`mothership-m7`, `mothership-m7a`, `mothership-m7b`), hashes catch silent in-place edits, and the CLI report embeds the full prompt text inline so a report generated immediately after a session is a complete record even if prompt files later change.

The save/load synthesis flow accounts for a parallel need: once you have a scenario you want to iterate against, freezing it to disk lets you run the *same* scenario against multiple Warden prompt candidates. Two runs with identical starting conditions and different prompts, both reviewed with the same tool, produce diffable reports that isolate the prompt variable.

## Part 1: `WardensModule` & Prompt Files

### 1.1 Module layout

```
apps/zoltar-be/src/wardens/
  wardens.module.ts
  warden-prompts.service.ts
  warden-prompts.service.spec.ts
  prompt-paths.ts              ← shared path/hash helpers used by the service and the review CLI
  prompts/
    mothership-m7.txt
```

`WardensModule` exports `WardenPromptsService`. `SessionModule` imports `WardensModule`; `SessionService` injects `WardenPromptsService` and consumes the selected prompt through it. No other module needs the service in M7.1.

Rationale for separating from `session/`: `session/` is the turn-orchestration module (validator, applier, events, correction, telemetry, prompt assembly, service, schema — already carrying a lot). Warden prompts are domain knowledge about how to instruct Claude to play a GM for a given system, conceptually distinct from turn mechanics. A dedicated module is also the right home for future Warden-related surface (per-system schema slot overrides, prompt-cache metadata, Warden-level telemetry helpers) without forcing those into `session/` later.

Filename pattern: `<s>-<version>.txt` where `<s>` matches a known game system slug and `<version>` follows the playtest-app convention (`m7`, `m7a`, `m7b`, `m8`, `m8-experimental`, etc.). Versions are discovered by glob, not by a manifest — adding a new version is `cp` plus edit.

### 1.2 Initial content migration

Move the contents of `WARDEN_SYSTEM_PROMPT_MOTHERSHIP` (currently a TypeScript `const` somewhere under `apps/zoltar-be/src/session/wardens/` per the M7 spec) into `apps/zoltar-be/src/wardens/prompts/mothership-m7.txt`. The resulting file must hash identically to what a sha256 of the const text would produce at the end of M7 — no reformatting, no added BOM, no converted line endings. After the move, the const is deleted; any code that previously imported it now injects `WardenPromptsService`.

Verify the move preserves byte identity by comparing `sha256sum mothership-m7.txt` against a one-off hash of the prior const string before the change lands. Record both values in the PR description.

The old `session/wardens/` directory is removed in the same PR if it only held the now-migrated const and has no other residents. If M7 parked other Warden-adjacent code there, leave that code in place and remove only the prompt const.

### 1.3 `WardenPromptsService`

File: `apps/zoltar-be/src/wardens/warden-prompts.service.ts`

```typescript
import { Injectable, OnModuleInit } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';

import { hashPromptText, promptsDir, rereadPromptFile } from './prompt-paths';

export interface WardenPromptFile {
  filename: string;   // 'mothership-m7.txt'
  hash:     string;   // 8-char sha256 prefix, hex
  text:     string;   // raw file contents
}

export type SystemSlug = 'mothership';   // expand as new systems arrive

@Injectable()
export class WardenPromptsService implements OnModuleInit {
  private readonly prompts  = new Map<SystemSlug, WardenPromptFile[]>();
  private readonly selected = new Map<SystemSlug, WardenPromptFile>();

  constructor(private readonly config: ConfigService) {}

  onModuleInit(): void { /* load + resolve selections */ }

  getSelected(system: SystemSlug): WardenPromptFile;
  getAll(system: SystemSlug): WardenPromptFile[];
  getByFilename(system: SystemSlug, filename: string): WardenPromptFile | null;
}
```

`prompt-paths.ts` exposes three helpers used by both the service and the review CLI so they can't drift:

```typescript
export function promptsDir(): string;                                    // resolves against src/ not dist/
export function hashPromptText(text: string): string;                    // 8-char sha256
export function rereadPromptFile(system: SystemSlug, filename: string): WardenPromptFile | null;
```

**Discovery.** At module init, the service reads `promptsDir()` once. For each entry matching `<s>-*.txt` for a known system slug, it reads the file, hashes the raw bytes (not a normalized string — we hash what Claude will actually see), and stores the record. Unknown system prefixes are ignored with a console warn so a stray `.txt` doesn't crash startup.

**Hash.** `createHash('sha256').update(text).digest('hex').slice(0, 8)`. Eight characters is more than enough to distinguish in-playtest edits (birthday-paradox collision probability in a single adventure's worth of prompts is vanishingly small) and keeps the report's header scannable.

**Selection rule.**

- If `WARDEN_PROMPT_OVERRIDE_<s>` is set (uppercased slug), find a file whose `filename` matches. If not found, throw — startup fails with a clear message.
- Otherwise, sort by the version suffix and return the last element. Version ordering: extract the suffix after the last `-` and before `.txt`, compare with a numeric-aware sort (so `m7b` > `m7a` > `m7` > `m6b`). If the prompts directory is empty for a system that's been asked for, throw on the first `getSelected` call.

Numeric-aware sort is sufficient for the version shapes we expect; if `mothership-m10.txt` exists alongside `mothership-m9.txt` and simple extraction produces the wrong result, that's the point at which a real semver parser earns its keep. Not before.

### 1.4 `SessionService` integration

`SessionModule` imports `WardensModule`. `SessionService` injects `WardenPromptsService` and calls `getSelected('mothership')` once per request to get the current `{ filename, hash, text }`. The text flows into `systemBlocks[1]` in `buildSessionRequest` (per M5's two-breakpoint cache layout). The cache-control marker on that block stays ephemeral — a new prompt version invalidates the cache on its first turn and re-primes on subsequent turns, which is the right behavior.

Because selection happens at module init and NestJS caches providers, the process holds one `{ filename, hash, text }` triple per system for its lifetime. Editing a file at runtime does *not* hot-reload the prompt. A process restart picks up the new file. This is deliberate — mid-process prompt swaps would make telemetry interpretation impossible.

### 1.5 Override mechanism

Env var: `WARDEN_PROMPT_OVERRIDE_MOTHERSHIP` (system-scoped — future systems get their own var, keeping each independent).

Unset → default selection (latest).
Set → exact filename, must exist.

Document in `docs/ENVIRONMENTS.md` alongside the Voyage variables. Intended use: side-by-side playtest of two candidate prompts against the same saved synthesis, by running two backend instances with different overrides. Not intended for production self-hosted deployments.

### 1.6 Tests

`warden-prompts.service.spec.ts`:

- `getAll` returns every `mothership-*.txt` in a fixture `prompts/` directory, ignores non-matching files, hashes consistently across calls with the same content.
- Two files with identical text produce identical hashes. One byte difference produces different hashes.
- `getSelected` returns the highest-versioned entry with no override set.
- `getSelected` honors a valid `WARDEN_PROMPT_OVERRIDE_MOTHERSHIP` value.
- Invalid override → `onModuleInit` throws with a clear message.
- Empty prompts directory for a requested system → `getSelected` throws with a clear message.

`prompt-paths.spec.ts`:

- `rereadPromptFile` returns the current on-disk state regardless of what was captured at module init (proves in-place edits are detectable by the CLI).
- `rereadPromptFile` returns null for a missing filename.

`session.service.spec.ts` / `session.prompt.spec.ts`:

- Existing tests that reference `WARDEN_SYSTEM_PROMPT_MOTHERSHIP` directly are updated to inject a `WardenPromptsService` stub returning a known fixture. Tests remain deterministic — the fixture returns one canned `WardenPromptFile`.

## Part 3: SQL Views

Three views, all read-only, all additive to the schema. They exist so the CLI can issue straightforward queries instead of hand-rolling joins. Views are the right abstraction here because the joins are stable and shared across multiple CLI queries; a view change is also a single place to update if the telemetry payload shape evolves.

Migration file: next available `V<N>__review_views.sql`. Use `CREATE OR REPLACE VIEW` so a later migration that tweaks a view is idempotent. All three views live in one migration.

### 3.1 View: `turn_log`

One row per `gm_response` event, joined to its telemetry row. The primary per-turn view.

```sql
CREATE OR REPLACE VIEW turn_log AS
SELECT
  ge.adventure_id,
  ge.sequence_number        AS gm_response_seq,
  ge.created_at             AS turn_created_at,
  ge.superseded_by          AS superseded_by,
  at.sequence_number        AS telemetry_seq,
  at.payload                AS telemetry_payload,
  at.payload->>'playerMessage'                              AS player_message,
  at.payload->'originalResponse'->>'playerText'             AS gm_player_text,
  at.payload->'wardenPrompt'->>'filename'                   AS warden_prompt_filename,
  at.payload->'wardenPrompt'->>'hash'                       AS warden_prompt_hash,
  (at.payload->'originalRequest'->>'promptTokens')::int     AS prompt_tokens,
  (at.payload->'originalRequest'->>'completionTokens')::int AS completion_tokens,
  (at.payload->>'toolLoopIterations')::int                  AS tool_loop_iterations,
  jsonb_array_length(at.payload->'diceRolls')               AS dice_roll_count,
  jsonb_array_length(at.payload->'rulesLookups')            AS rules_lookup_count,
  (at.payload ? 'correction')                               AS had_correction
FROM game_event ge
JOIN adventure_telemetry at
  ON at.adventure_id = ge.adventure_id
  AND at.sequence_number = ge.sequence_number
WHERE ge.event_type = 'gm_response';
```

### 3.2 View: `state_history`

One row per `state_update` event. Surfaces applied deltas joined to the turn that caused them. Useful for "show me how HP evolved across this adventure" queries the CLI does not need but a human reviewer might run ad-hoc in `psql`.

```sql
CREATE OR REPLACE VIEW state_history AS
SELECT
  ge.adventure_id,
  ge.sequence_number         AS state_update_seq,
  ge.created_at              AS applied_at,
  ge.payload->'applied'      AS applied,
  ge.payload->'thresholds'   AS thresholds,
  -- The preceding gm_response (or correction) in the same adventure
  (SELECT ge2.sequence_number
     FROM game_event ge2
    WHERE ge2.adventure_id = ge.adventure_id
      AND ge2.sequence_number < ge.sequence_number
      AND ge2.event_type IN ('gm_response', 'correction')
    ORDER BY ge2.sequence_number DESC
    LIMIT 1)                AS source_response_seq
FROM game_event ge
WHERE ge.event_type = 'state_update';
```

The correlated subquery is fine at this scale — adventures are on the order of hundreds of turns, not millions. If `state_history` becomes a performance problem later (it won't in MVP), rewrite as a window function.

### 3.3 View: `correction_log`

One row per `correction` event. Joins back to the superseded `gm_response` and to the telemetry row.

```sql
CREATE OR REPLACE VIEW correction_log AS
SELECT
  c.adventure_id,
  c.sequence_number                          AS correction_seq,
  c.created_at                               AS corrected_at,
  orig.sequence_number                       AS original_seq,
  orig.payload                               AS original_response,
  c.payload                                  AS corrected_response,
  at.payload->'correction'->'rejections'     AS rejections,
  (at.payload->'correction'->'correctionRequest'->>'promptTokens')::int     AS correction_prompt_tokens,
  (at.payload->'correction'->'correctionRequest'->>'completionTokens')::int AS correction_completion_tokens
FROM game_event c
JOIN game_event orig
  ON orig.adventure_id = c.adventure_id
  AND orig.id = c.superseded_by
JOIN adventure_telemetry at
  ON at.adventure_id = orig.adventure_id
  AND at.sequence_number = orig.sequence_number
WHERE c.event_type = 'correction';
```

The join through `superseded_by` flips M6's usual direction — M6 sets `superseded_by` on the original `gm_response` row pointing forward at the correction. A moment's inspection of M6's `session.events.ts`: the correction row itself does not carry its own `superseded_by`, only the original does. The view joins `c.superseded_by` expecting the correction's row to reference the original. **Verify this direction during implementation**; if M6 stores the pointer on the original instead of the correction, swap the join predicate to `orig.superseded_by = c.id`.

### 3.4 Migration hygiene

The three views are additive. No existing table changes. The migration includes `DROP VIEW IF EXISTS … CASCADE;` for each view before its `CREATE OR REPLACE` so re-running cleanly handles schema drift across dev machines.

Document all three views in `docs/schema.md` in a new "Review Views" section. Drizzle does not model views natively — skip the Drizzle schema update; the CLI queries them via raw SQL with the existing Drizzle `sql` template, not via the query builder.

Inline formatting decisions:

- Zero-result `rules_lookup` entries get a warning marker (⚠️) in the per-turn view and are summarized in the footer. These are M7.2's primary prioritization signal; prominence here matters.
- `diceRolls` render in sequence order, labeled `[player]` or `[system]`, showing notation, purpose, result array, modifier, and total. For `[player]` rolls, the originating `requestId` is shown so a reader can trace the request→result pairing across turns.
- `applied` state changes are flattened to a bulleted diff (pool `current` from X to Y, flag flips, entity status flips) rather than dumped as JSON. Reviewer ergonomics.
- `gmUpdates.notes` gets its own line when non-empty. Dropping these on the floor would defeat their purpose.
- Corrections render twice: once inline in the turn where they fired (with original vs corrected state deltas side-by-side) and once in the "Correction events" top-level section for quick scanning.

### 4.3 Prompt hash mismatch handling

At report generation time, the tool uses `rereadPromptFile` (from `prompt-paths.ts`) for every prompt file whose filename appears in telemetry. For each distinct `{filename, hash}` pair seen in telemetry:

- If `<filename>` exists and its current hash equals the recorded hash → embed the current file's text in the Prompt texts appendix normally.
- If `<filename>` exists but its current hash differs from the recorded hash → embed the current file's text, prefixed with a clearly-delimited warning block:

  ```
  > ⚠️ **Prompt hash mismatch.** Telemetry recorded hash `a4f9c02b` for this
  > filename, but the file on disk currently hashes to `b1c27ed1`. The text
  > below is the *current* file — the text Claude actually saw for turns
  > using hash `a4f9c02b` is no longer recoverable. Regenerate this report
  > from a checkout where the file matches the recorded hash if the original
  > text is needed.
  ```

- If `<filename>` doesn't exist at all → emit the warning block noting the file was deleted and skip the embedded text.

The per-turn Warden prompt reference in the report still shows the recorded hash faithfully. Only the appendix embedding is affected.

### 4.4 Implementation notes

- The script uses the existing Drizzle `db.provider` pattern to open a pool, reusing the backend's `DATABASE_URL`. No new connection config. Close the pool cleanly on exit.
- Queries all go through the three views. The script runs three queries total: `SELECT * FROM turn_log WHERE adventure_id = $1 ORDER BY gm_response_seq`, `SELECT * FROM correction_log WHERE adventure_id = $1 ORDER BY correction_seq`, and a single lookup against `adventure` + `campaign` + `game_system` for the header. State history is not rendered per-turn; a reviewer who wants it runs `psql` directly.
- Do **not** import NestJS or boot the module graph. The script is a thin CLI — just `Pool`, Drizzle, `fs`, the markdown formatter, and the `prompt-paths.ts` helpers.

### 4.5 Tests

`playtest-review.spec.ts` (or `.spec-int.ts` if it needs DB fixtures):

- Given a fixture adventure with 3 turns, a correction on turn 2, one zero-result rules lookup on turn 1, and one system-generated roll on turn 3: the generated markdown matches a snapshot.
- A turn referencing a prompt filename whose on-disk hash differs triggers the mismatch warning block.
- A turn referencing a deleted prompt filename triggers the deletion warning block.
- An adventure id with zero turns exits with a non-zero code and a clear message.

Snapshot stability: the fixture builders set deterministic dates and UUIDs. Token counts, sequence numbers, and content are fixed. Snapshot comparison is line-by-line.

## Part 5: Save & Load Synthesis

### 5.1 What's saved

A `SynthesisExport` JSON file carries everything needed to recreate an adventure's starting conditions in a new campaign. Read path: directly from the `campaign`, `gm_context`, `campaign_state`, and `adventure` rows of a source adventure. Write path: new rows in the same four tables, with fresh UUIDs, in a single transaction.

```typescript
// apps/zoltar-be/src/synthesis/synthesis-export.schema.ts

export interface SynthesisExport {
  version:     1;
  exportedAt:  string;                   // ISO timestamp
  source: {
    campaignId:   string;                // original UUID — traceability only
    adventureId:  string;                // original UUID — traceability only
    campaignName: string;                // original name — load uses as base for new name
  };
  system: {
    slug: 'mothership';                  // for future multi-system load logic
  };
  gmContext: {
    schemaVersion: number;               // from gm_context.schema_version
    blob:          unknown;              // jsonb contents verbatim — includes openingNarration, narrative, structured, etc.
  };
  campaignState: {
    schemaVersion: number;               // from campaign_state.schema_version
    data:          unknown;              // jsonb contents verbatim — initial state
  };
  adventure: {
    mode: 'freeform';                    // M7.1 only supports freeform; initiative-mode scenarios are a Phase 2+ concern
  };
}
```

No character rows are copied as a separate concept because character data is already encoded in `campaign_state.data.resourcePools` (e.g. `dr_chen_hp: { current: 10, max: 10 }`) and in `gm_context.blob.structured.entities`. Re-materializing a character outside those two places would duplicate source-of-truth. Load reuses the saved jsonb verbatim.

### 5.2 Save script

Location: `apps/zoltar-be/scripts/save-synthesis.ts`

Invocation: `task playtest:save-synthesis -- <adventure-id>` or directly via `tsx`.

Behavior:

1. Open the DB pool (same pattern as the review CLI).
2. Load the adventure row; error cleanly if missing.
3. Error cleanly if the adventure has any `gm_response` events in `game_events` — save is for "zero-turn" adventures only, by design. The error message directs the user to the review CLI if they wanted to export a played adventure.
4. Load `campaign`, `gm_context` (by campaign_id), and `campaign_state` (by campaign_id).
5. Serialize to `SynthesisExport` shape.
6. Write to `apps/zoltar-be/synthesis-saves/<campaign-slug>-<timestamp>.json` by default; `--output <path>` to override, `--stdout` to print.
7. Add `apps/zoltar-be/synthesis-saves/` to `.gitignore`. Created on first run. Saves contain the full GM context blob including hidden information — treat as private by default.

Campaign slug: lowercase, underscores, alphanumerics only, truncated to 40 chars. Timestamps are `yyyymmdd-hhmmss` local time for sortability.

The "zero turns" constraint is enforced by a single SQL query (`SELECT 1 FROM game_event WHERE adventure_id = $1 AND event_type = 'gm_response' LIMIT 1`). If the intent shifts in Phase 2 toward "save mid-campaign state as a starting point," the constraint relaxes — but M7.1's use case is "compare prompts against the same *starting* conditions," which specifically means turn zero.

### 5.3 Load script

Location: `apps/zoltar-be/scripts/load-synthesis.ts`

Invocation: `task playtest:load-synthesis -- <file.json>` or directly via `tsx`. Optional flags:

- `--name <string>` — override the generated new campaign name. Defaults to `<original campaign name> (clone <yyyymmdd-hhmmss>)`.

Behavior:

1. Read and parse the JSON. Validate against a Zod schema for `SynthesisExport` — fail with a clear message on shape mismatch or unknown `version`.
2. Verify `system.slug` is supported (only `'mothership'` in M7.1).
3. Open a DB transaction.
4. Insert a new `campaign` row with a fresh UUID, the provided or generated name, and the correct `system_id` (looked up by slug).
5. Insert a new `gm_context` row with the saved schema version and blob, linked to the new campaign.
6. Insert a new `campaign_state` row with the saved schema version and data, linked to the new campaign.
7. Insert a new `adventure` row with a fresh UUID, `status = 'ready'`, `mode = 'freeform'`, linked to the new campaign.
8. Commit.
9. Print the new adventure id and a ready-to-paste URL: `/campaigns/<new-campaign-id>/adventures/<new-adventure-id>/play`.

Load never touches `message` rows, `game_events`, `adventure_telemetry`, `pending_canon`, or any other turn-derived table. The opening narration lives in `gm_context.blob.openingNarration` and is rendered directly by the play view on first load (per M6, which reads it from the adventure GET response and renders it as the first GM bubble when the message log is empty). No explicit message row is written.

**Idempotency.** Loading the same file twice produces two distinct new campaigns and adventures. This is intentional — the clone semantic avoids UUID collisions and lets you run the same scenario through three or four Warden prompts without re-saving.

**Creator/owner.** The new campaign is owned by a designated user. Strategy: the loader reads `PLAYTEST_LOAD_USER_ID` from env; if unset, it reads the first user row from the `user` table and prints a warning naming the chosen user; if the `user` table is empty, it fails. This is a dev-loop tool, not a production import — production import semantics are a Phase 2+ concern involving auth flows that don't exist yet.

### 5.4 Tests

`save-synthesis.spec-int.ts`:

- Saving a zero-turn adventure produces a `SynthesisExport` whose `gmContext.blob` and `campaignState.data` match the source rows byte-for-byte (deep equality after JSON round-trip).
- Saving an adventure with any `gm_response` event in `game_events` exits with a clear error and non-zero code.
- `source.campaignId` and `source.adventureId` match the source row UUIDs; new UUIDs are not generated in save.

`load-synthesis.spec-int.ts`:

- Loading a valid export creates fresh rows in `campaign`, `gm_context`, `campaign_state`, `adventure`, with fresh UUIDs and the original blobs/data preserved.
- The new adventure has `status = 'ready'` and `mode = 'freeform'`.
- Loading an unknown-version or malformed file exits with a clear error and non-zero code.
- Loading when `PLAYTEST_LOAD_USER_ID` is unset falls back to the first user and emits a warning naming the chosen user.
- Loading when the `user` table is empty exits with a clear error.

`save-load-roundtrip.spec-int.ts`:

- Save an adventure to a temp file, load it, assert the loaded adventure's `gm_context.blob` equals the source's, and the loaded `campaign_state.data` equals the source's.
- The loaded adventure is different (fresh UUIDs) but substantively identical.

## Part 6: Sanity-Check Pass

After Parts 1–5 land and the first production-stack Mothership playtest runs, execute the sanity-check pass. This is not optional — it's the whole reason M7.1 is scoped to sit before the playtest rather than after.

**Procedure:**

1. Run a full Mothership adventure through the production stack (not the playtest app). Target 15–25 turns — enough to exercise dice, rules lookups, at least one correction if the validator catches anything, and a threshold crossing or two.
2. Generate the report against that adventure.
3. Read the report end-to-end as a reviewer. For each section, ask: is this information pulling its weight? Is anything I want absent? Is anything bloating the output without earning its place?
4. For each payload field in `AdventureTelemetryPayload`, check: does it appear somewhere in the report? If not, why is it in the payload?
5. (Recommended) Save the adventure's synthesis *before* running the session, then after the session load the synthesis into a fresh campaign and run a second session with a different `WARDEN_PROMPT_OVERRIDE_MOTHERSHIP`. Generate both reports. If the tooling's ergonomics don't support this comparison workflow cleanly, that's a finding worth fixing before M7.1 closes.

**Likely findings to consider:**

- `originalRequest.systemBlocks` count (currently `number`) might be usefully richer — e.g. which blocks got cache hits. If the Anthropic SDK exposes cache-hit metadata on the response, add it. If it doesn't, drop the field.
- `originalRequest.messageCount` — is this actually useful in the report, or is it better replaced by "messages in window"?
- `notes.original` vs `notes.correction` handling in the report — is the dual presentation worth keeping or should it collapse to a single line?
- `toolLoopIterations` surface area — is per-turn sufficient, or is a dedicated "tool loop activity" section worth building (e.g. showing the interleaved order of dice rolls and lookups within a single turn)?
- Save/load output location — is `apps/zoltar-be/synthesis-saves/` the right home, or should it live at the repo root for easier sharing across dev machines?

**Deliverable for the sanity check:**

- If the payload shape changes: a new entry in `docs/DECISIONS.md` recording the change and rationale, a migration-adjacent PR note (the payload is `jsonb` so no DB migration), and corresponding updates to `AdventureTelemetryPayload`, `buildAdventureTelemetryPayload` tests, and the report generator. Ship all of this in the same PR as M7.1 or the first PR immediately after.
- If the shape is fine as-is: an entry in `docs/DECISIONS.md` saying the shape was reviewed against a real playtest and held up. That record prevents the question getting re-opened later without cause.

The sanity check is not a Part that "ships" — it's a gate. If running the script against a real adventure makes it clear the telemetry, view, or save/load shapes need changes, those changes are part of M7.1 even if they weren't anticipated here.

## Out of Scope for M7.1

Deferred, in scope for later milestones or not at all. Do not implement:

- **Web UI for review** — CLI only. Phase 2+ at the earliest, and only if offered to non-technical collaborators.
- **Prompt text stored in the database** — explicitly rejected. Flat files + git + inline report embedding covers the durability need without coupling prompt archival to DB liveness.
- **Session export** (full post-play state, resume into the same adventure) — save-synthesis is explicitly for *starting* conditions. Resuming a played adventure is a distinct feature that would replay the event log into a new adventure's state, and it's not needed for the "compare prompts against the same starting conditions" use case M7.1 is scoped around.
- **Warden prompts in `@uv/game-systems`** — considered and rejected for M7.1. The package is pure computation without I/O; adding raw-file reads and coupling prompt iteration to the `tsc` build step would degrade the iteration loop during playtest. Revisit only if a clear reason emerges.
- **Automated CI-driven report generation** — M7.1's CLI is human-invoked. CI integration is a distinct concern.
- **Cross-adventure aggregation** — a single-adventure tool. "Compare two adventures' prompt performance" is a Phase 2+ question, answered differently (probably against an analytics extract, not against live `adventure_telemetry`). Two separate reports plus `diff` is the M7.1 answer.
- **Prompt diff rendering in the report** — use `git diff` against the prompts directory. Building a structured diff renderer for prompt text inside the report is premature.
- **Warden prompt hot-reload at runtime** — requires process restart to pick up a new default. Mid-process swaps would corrupt telemetry interpretation.
- **Prompts for systems other than Mothership** — OSE, UVG, and 5e come in Phase 2+. `WardensModule` is system-keyed from the start so adding them is a file drop plus a case in `SystemSlug`.
- **Loading saved synthesis for non-Mothership systems** — the loader validates `system.slug === 'mothership'` in M7.1 and fails otherwise. Widening this is mechanical but belongs with the system's own milestone.
- **Playtest review for the `zoltar-playtest` app** — that app already exports its own self-contained JSON logs. M7.1 is scoped to the production stack (`zoltar-be`).
- **Multi-user authorization on load** — the load script creates a campaign owned by a single designated user. Production import semantics (share a saved synthesis between users, preserve attribution, etc.) are a Phase 2+ concern.

## Deferrals Introduced in M7.1

### Prompt text DB archival

The flat-file + inline-embedding design handles the durability need for M7.1. If a future workflow genuinely requires querying prompt text by hash from the DB (e.g. a SaaS telemetry pipeline where the DB is durable and flat files aren't accessible), add a `warden_prompt` table keyed by hash then. The telemetry `wardenPrompt: { filename, hash }` shape is forward-compatible — a hash-keyed lookup is a one-table addition.

### Sophisticated version ordering

Numeric-aware extraction is enough for the version shapes M7.1 expects. A real semver parser lands the first time the convention produces a wrong answer in practice, not preemptively.

### Report-to-file auto-generation on session end

The CLI is manually invoked. If playtest discipline turns out to be "forget to run the script, lose the chance before the next DB wipe," a post-session hook could auto-generate a report on adventure completion or on a configurable schedule. Deferred pending evidence that manual invocation is actually the failure mode.

### Save-synthesis for mid-session state

M7.1 saves zero-turn adventures only. A "save current state of a played adventure, replay against a different prompt from turn K onward" feature would be useful for bisecting where a prompt's behavior diverges, but it requires replaying the event log to reconstruct intermediate state and that's a meaningful piece of machinery. Deferred with no urgency.

### Multi-system save/load

The `SynthesisExport` shape is already system-tagged via `system.slug`, so widening the loader to accept other systems is a narrow change. But the first non-Mothership system (UVG or OSE) won't arrive until Phase 2, and until then there's nothing to test against.

### Structured findings tracking

The sanity-check pass (Part 6) writes findings to `docs/DECISIONS.md`. A more structured findings log (e.g. per-playtest review notes stored alongside reports) might be worth building later, but not before several playtests have accumulated enough patterns to design against.

## Open Questions

1. **`superseded_by` pointer direction.** M6's `session.events.ts` sets `superseded_by` on the original `gm_response` row pointing at the correction, per the spec text. The `correction_log` view in 3.3 joins as if the pointer is on the correction pointing back at the original. Verify during implementation — the join predicate may need flipping. (Low-risk: both directions produce a valid join; just pick the one that matches what M6 actually persisted.)

2. **Report emoji vs. ASCII flags.** Using `⚠️` for zero-result lookups is nice for rendered markdown but makes grep a tiny bit harder. Happy with emoji unless there's a preference for `[!]` or `WARN:` prefixes instead.

3. **Scope of the sanity check's "adjust if fields are missing or redundant" mandate.** If the first real playtest reveals, say, that `snapshotSent` is a 15KB string we never actually read, is dropping it from the payload in scope for M7.1's PR, or is that a follow-up? My read: in scope. The whole point of the sanity-check pass is to lock the telemetry shape against real usage before M8 starts relying on it. But that means M7.1's PR potentially grows a small-but-real telemetry migration mid-implementation. Flagging now so the scope surprise isn't a surprise.

4. **`PLAYTEST_LOAD_USER_ID` default behavior.** The loader falls back to the first user in the DB if the env var isn't set and prints a warning. That's fine for a single-developer dev loop where there's exactly one user, but if the dev DB ever has multiple users (imported a prod dump for debugging), "first user" is ambiguous. Acceptable with the warning, or should the fallback fail strictly when unset? I lean "acceptable with a printed warning" but happy to flip to strict if the dev-loop pattern prefers it.
