# M7.3 — Turn-State Replay Infrastructure

*Draft spec — prerequisite for M7.4 (Warden Eval Harness)*

---

## Purpose

The eval harness (M7.3) needs to seed the DB with state as of any arbitrary turn in an already-played adventure, so a fixture can replay that turn under a candidate Warden prompt. No such capability exists today: `save-synthesis` (M7.1) only works for zero-turn adventures — it's a snapshot *reader*, not a replay mechanism, and it throws if any `gm_response` event exists. This milestone builds the missing piece: automatic, no-action-required capture of the true starting state, plus a way to fold that state forward through the existing event log to reconstruct any later turn.

**Design bar, per Alex:** automatic (nothing to remember to do), and reuses existing code/DB structures as much as possible. This ruled out a full per-turn snapshot table (more new storage, more to keep in sync) in favor of replay-from-events, once investigation confirmed replay is actually the *cheaper* path — most of what it needs already exists.

---

## What Investigation Found

Summarizing the fact-finding that shaped this spec (full detail lives in conversation history; recorded here so the reasoning travels with the spec):

- **`campaign_state.data` already has a pure, reusable applier** — `validateStateChanges` (`session.validator.ts:42-90`) and `applyToCampaignState` (`session.applier.ts:4-17`), both `(state, payload) → newState`, no I/O. This exists because the correction loop requires it, not because anyone anticipated replay — replay just inherits the benefit.
- **`gm_context.blob`'s NPC-agenda merge does not** — `mergeNpcAgendas` (`session.repository.ts:193-225`) is inline SQL-fetch-merge-write, single call site (`session.repository.ts:580`), no forcing function ever pulled it out into its own testable function the way the correction loop did for campaign state.
- **Decision: consolidate, don't duplicate.** Rather than extracting `mergeNpcAgendas` as a second standalone pure function alongside `applyToCampaignState`, generalize the latter into one applier covering both objects: `applyValidatedTurn(priorCampaignState, priorGmContextBlob, validatedPayload) → { newCampaignState, newGmContextBlob }`. One function, one thing for replay to call, no risk of the replay path silently drifting from what production actually does — which was the whole reason the harness drives the real pipeline in the first place (see M7.3 spec, "in-process" decision).
- **`game_events` is sufficient to fold state forward, but only from a seeded turn-0 state, not from nothing** — `CampaignRepository.mergePlayerResourcePools` writes `campaign_state.data.resourcePools` directly at character creation with no `game_events` row, so a synthetic empty starting point wouldn't reconstruct correctly. Turn-0 state must be captured and persisted as its own artifact.
- **`pending_canon` has no sequence key** — only `createdAt`, and it's transactionally atomic with its turn's `game_events` (confirmed: `insertPendingCanon` runs inside the same transaction as `writeTurnEvents`), but there's no `sequence_number`/turn FK to filter "canon as of turn N" precisely. **This is a gap this milestone closes** (see below) — without it, `MISSING-CANON-CAPTURE` fixtures can't be seeded with an accurate canon-state-so-far.
- **`messages` ordering relies on `createdAt` only, no shared sequence key with `game_events`.** Player and GM messages for the same turn aren't inserted in the same transaction (intentional, per `session.repository.ts:526` — retries need to reproduce the player's action). This is an existing property of the live system, not a new risk from replay, and isn't being changed here — timestamp ordering is good enough in practice and always has been.

## Scope

### 1. Automatic turn-0 capture

Hook into the synthesis write path (wherever `submit_gm_context`'s result is committed — same transaction that inserts the initial `gm_context` and `campaign_state` rows). On commit, automatically capture and persist the same data `buildSynthesisExport` (`save-synthesis.core.ts:51-190`) already knows how to read — reuse that query logic rather than writing new extraction code.

**Storage:** a new table, e.g. `adventure_synthesis_snapshots` (`adventureId` PK, `schemaVersion`, `gmContextBlob: jsonb`, `campaignStateData: jsonb`, `capturedAt`), written once per adventure, never updated. Reuses the existing `SynthesisExport` Zod schema shape for the payload rather than inventing a new one — same validated structure `save-synthesis`/`load-synthesis` already work with today.

This makes `save-synthesis` (M7.1) redundant, not merely unnecessary — its only job was capturing turn-0 state into a portable file, and that capture now happens automatically, unconditionally, at synthesis time. **`save-synthesis.ts`/`save-synthesis.core.ts` are removed as part of this milestone**, not kept alongside the new table. `load-synthesis` is not removed — see item 2 below, its job changes rather than disappearing.

### 2. `load-synthesis` sources from the snapshot table, not a JSON file

`load-synthesis`'s job is unchanged — clone a fresh campaign + adventure with new UUIDs from a known-good starting state, so multiple prompt variants can run from identical conditions. What changes is where that starting state comes from: instead of `load-synthesis <file.json>`, it becomes `load-synthesis <source-adventure-id>`, reading the row directly from `adventure_synthesis_snapshots` rather than requiring someone to have generated and supplied a file. `load-synthesis.core.ts`'s validation (`parseSynthesisExport` against `synthesisExportSchema`) and transaction logic (`buildAndRunLoad`) carry over essentially unchanged — only the input source changes, from `readFileSync` + `JSON.parse` to a `SELECT` against the new table.

### 3. One-off script: import the existing playtest adventure's legacy snapshot

The adventure behind `playtest-2025-07-15.md` predates automatic capture — its turn-0 state exists only as a JSON file on disk (from the manual `save-synthesis` run taken before that playtest began), not as a row in `adventure_synthesis_snapshots`. A small one-time script bridges this: reads that JSON file, validates it against the existing `synthesisExportSchema` (same schema `load-synthesis` already validates against — no new validation logic needed), and inserts one row into `adventure_synthesis_snapshots` for that specific adventure id. This is a migration for the one adventure that predates the new mechanism, not part of the ongoing pipeline — it should not be wired into any regular task or script, just run once.

### 4. Consolidate `applyToCampaignState` and `mergeNpcAgendas`

Generalize into one pure function covering both objects (see "What Investigation Found," above). Update the two production call sites (`session.service.ts`'s turn-application flow, `session.repository.ts:580`) to call the unified function. Update the two existing integration tests that call `mergeNpcAgendas` standalone (`session.repository.spec-int.ts:98,138`) to match the new signature.

*Note, flagged but explicitly out of scope: "campaign state" vs. "adventure state" naming is a known semantic inconsistency Alex has already identified as a separate future cleanup. Not addressed here.*

### 5. Add a sequence key to `pending_canon`

Add a `sequenceNumber` column (or `gameEventId` FK — CC's call on which is cleaner given the existing schema), populated at insert time from the same per-adventure sequence counter `game_events` already uses (`session.events.ts:65-79`). Since `insertPendingCanon` already runs inside the same transaction as `writeTurnEvents`, this is a small, low-risk addition — no new transaction boundary, just one more column written where a value is already available.

### 6. The replay function

```typescript
async function reconstructStateAsOfTurn(
  adventureId: string,
  targetSequenceNumber: number,
): Promise<{
  campaignState: CampaignStateData;
  gmContextBlob: GmContextBlob;
  pendingCanon: PendingCanonRow[];
  messages: MessageRow[];
}>
```

**Semantics — worth stating precisely, since it's easy to get the boundary wrong:** "state as of turn N" for eval-harness purposes means state as it existed *going into* turn N — i.e., after all events with `sequenceNumber < N` have been applied, and including the player's message that triggers turn N, but *not* turn N's own GM response (that's what replay is regenerating and checking). Implementation:

1. Load the turn-0 snapshot from `adventure_synthesis_snapshots`.
2. Load all `game_events` for the adventure with `sequenceNumber < targetSequenceNumber`, ordered ascending.
3. Fold forward: for each event's logged payload, call the unified applier from (2) above, threading `campaignState`/`gmContextBlob` through in sequence.
4. Load `pending_canon` rows with `sequenceNumber < targetSequenceNumber` (once the column from (3) exists) — this is the "canon that already existed" baseline a `MISSING-CANON-CAPTURE` fixture needs to check against.
5. Load `messages` up through and including the player message associated with turn N (by `createdAt`, per the existing ordering convention — unchanged from today).

This becomes the actual mechanism behind the eval harness's `savePointRef` (M7.4 spec) — reconstructing any turn of any adventure, not just a one-time fix for the one playtest already in hand.

## Out of Scope

- The "campaign state" / "adventure state" naming inconsistency (flagged above, tracked separately).
- Changing `messages` to use a shared sequence key with `game_events` — existing timestamp ordering is adequate and unchanged.
- Any change to `save-synthesis`'s underlying query logic beyond removing the script — it's fully superseded, not modified.
- Making `load-synthesis`'s new adventure-id-based interface backward-compatible with the old `<file.json>` form — the one-off import script (item 3) is the only bridge needed for pre-existing data; no dual-mode CLI required.
- Building this as a generally-exposed API/admin feature — for now this is internal plumbing consumed by the eval harness, not a user-facing capability.
