## Goal

Populate the `rules_chunk` table. After M7 the runtime plumbing is in place — Claude can call `rules_lookup`, and the empty-index path is wired (empty results, Warden falls back to best-effort rulings and notes the miss). After M7.2 the Mothership index is populated from the Player's Survival Guide 1e and self-hosted users have a supported tooling path for ingesting their own PDF.

The split from M7 reflects a real difference in stack and lifecycle. The runtime query path is NestJS/TypeScript and lives inside the GM turn transaction. The ingestion pipeline is Python, runs offline, and has its own dependency graph (marker, pinned extraction models, hash files, Voyage in document mode). Forcing them into a single milestone made both halves harder to test and reason about.

**What ships in M7.2:**

- Python pipeline under `ingestion/` per `docs/rules-ingestion.md`: marker extraction (`--output_format chunks`, not `markdown`), fixup patch application, a column-aware reading-order sort, footer-derived page/chapter attribution, block-based chunking, SHA-256 hash verification, Voyage embedding (`input_type="document"`), Postgres insert via psycopg. Supersedes the `###`-heading-boundary design this spec originally described — see the sequencing note above.
- `ingest.py` CLI entry point with flags for system, PDF path, database URL, Voyage key/model, dry-run, hash-skip.
- `ingestion/mothership/` contents: empty `fixups.json`, `hashes/mothership-psg-1e.txt` recording the SHA-256 of Alex's reference PDF, empty `templates/` directory.
- Pinned dependency set (`requirements.txt`) — marker, voyageai, psycopg, tiktoken, pypdfium2 at specific versions.
- `ingestion/README.md` covering prereqs, usage, fixup patch file format, and troubleshooting.
- A local run against the Mothership PSG seeds Alex's dev Postgres with `rules_chunk` rows — verified by a manual `rules_lookup` sanity query before the PR merges.

## Done When

1. `python ingest.py --system mothership --pdf <path> --database-url <url>` runs end-to-end and returns zero exit status against Alex's local Postgres and his Mothership PSG PDF.
2. After a successful run, `SELECT COUNT(*) FROM rules_chunk WHERE system_id = (SELECT id FROM game_system WHERE slug = 'mothership')` returns a reasonable value (expect **50–90 chunks** for the PSG 1e; the measured figure is 66). **Corrected:** an earlier draft of this item expected 100–400, a guess written before anyone measured the book. It is arithmetically incompatible with this spec's own ~400-token chunk target — the PSG's extractable content is 20,353 tokens, so a 400-token target has a ceiling of ~50 chunks before overlap and produces 65 with it. Reaching 100 would require a ~200-token target, a chunking change nobody has argued for. Chunk size is an M7.5 lever, to be tuned against `task eval:retrieval` rather than against this number (`docs/rules-extraction-findings.md § S11.1`).
3. A manual `rules_lookup` query (e.g. "what happens when a character panics") returns **the correct pages in its top hits** — judged by whether the returned `source` citations are the pages that actually answer the question, not by the similarity number attached to them. See Part 4.3 for how to issue it. **Corrected twice.** First, the numeric bar: an earlier draft required a top result above 0.5 cosine similarity. Measurement against the populated index says that is not a property this model and corpus have — 1 of 7 answerable queries clears it, and the spec's own panic example returns the correct page at ranks 1 *and* 2 while scoring 0.456 (`docs/rules-extraction-findings.md § S12.2`). Being right and scoring above 0.5 are close to unrelated here, so the bar is dropped rather than lowered; where an honest threshold lies is M7.5's question, derived from Part 8's fixture sample rather than from a handful of hand-picked queries. Second, the example query: **Corrected:** an earlier draft of this item used "panic check of 73," describing the d100 panic table from the Mothership **0e** rules. The 1e PSG this pipeline ingests uses a d20 table (physical page 20, headed `D20 PANIC EFFECT`); a d100-shaped query would make a correctly-populated index look broken (`docs/rules-extraction-findings.md § S1.9`). Alex's `0e/` directory holds both editions' PDFs — easy to grab the wrong one when running this check.
4. Re-running the pipeline with the same PDF is idempotent — existing `rules_chunk` rows for the system are replaced, not duplicated.
5. `--dry-run` completes without embedding or inserting, and prints chunk count plus a first-chunk preview.
6. `--skip-hash-check` bypasses hash verification with a warning logged; default behavior warns on mismatch but proceeds.
7. `ingestion/README.md` is sufficient for a new self-hosted user to install prereqs, run the pipeline, and troubleshoot common failures without consulting other docs.
8. `ingestion/tests/test_chunk.py` passes, and passes in CI.
9. ~~Both models are re-baselined against the populated index...~~ **Moved to M7.5** — see the second sequencing note and Part 6. M7.2's own completion does not depend on this.
10. ~~A dedicated playtest has been run against the populated index...~~ **Moved to M7.5** — same reasoning. M7.2's own completion does not depend on this.
11. Query preprocessing is applied before every `rules_lookup` embedding call: a synthetic high-document-frequency term is verifiably dropped from a test query, and the safety floor holds (a query that's all high-frequency terms still embeds something, not an empty string). See Part 7.4.
12. `task eval:retrieval` runs the fixture set (Part 8) against the populated index and produces a report with recall@3, recall@5, MRR, and applicability (answerable fixtures scored vs. unanswerable fixtures excluded from the rate) — not a specific quality bar, which is M7.5's decision, just that the tool runs and produces real numbers against real fixtures.
13. The fixture set includes deliberately unanswerable queries (Part 8.3), and the report surfaces their top-1 similarity scores separately from the answerable-fixture recall numbers — the raw material M7.5's similarity-floor derivation needs, not the floor itself.

## Part 1: Directory Structure

```
ingestion/
  README.md
  requirements.txt
  ingest.py                      # CLI entry point
  pipeline/
    __init__.py
    extract.py                   # marker invocation (--output_format chunks --disable_ocr)
    chunk.py                     # reading-order sort, footer-derived page/chapter attribution, block merge into chunks
    fixup.py                     # fixup patch application, matched on block id
    embed.py                     # Voyage AI client (document mode)
    store.py                     # Postgres insert via psycopg
    hash.py                      # PDF SHA-256 verification
  mothership/
    fixups.json                  # initially empty array: []
    hashes/
      mothership-psg-1e.txt      # SHA-256 of the reference PDF edition
    templates/                   # fixup templates (empty in M7.2)
  tests/
    test_chunk.py
```

`chunk.py` covers three sub-steps that were originally scoped as a single heading-boundary pass: recovering reading order (blocks aren't emitted in reading order on multi-column pages), attributing page and chapter from the PDF's running footer, and merging the sorted, attributed blocks into ~400-token chunks. All three stay in one module rather than being split out — none is more than a few dozen lines, and they share the same block-list data structure end to end. See `docs/rules-ingestion.md § Step 4` for the canonical algorithm and `docs/decisions.md § Rules Ingestion` for why each piece is shaped the way it is.

The `<system>/` subdirectory pattern (`mothership/`, and later `uvg/`, `ose/`, etc.) isolates per-system fixups and hashes. Phase 2 adds sibling directories without touching pipeline code.

`tests/` as a sibling of `pipeline/` departs from the repo's "tests live adjacent to the code they test" convention in `CLAUDE.md`. That convention is written for the TypeScript apps, where `*.spec.ts` beside the module is idiomatic; a top-level `tests/` package is the corresponding idiom in Python and is what `pytest` discovers by default. Deliberate divergence, not an oversight.

## Part 2: `ingest.py` CLI

```bash
python ingest.py \
  --system mothership \
  --pdf /path/to/mothership_players_survival_guide.pdf \
  --database-url "$DATABASE_URL"
```

### Flags

- `--system <slug>` (required): maps to `game_system.slug`. Drives which `<system>/` subdirectory holds fixups and hashes.
- `--pdf <path>` (required): input PDF.
- `--database-url <url>` (required): Postgres connection string.
- `--voyage-api-key <key>` (optional, else from `VOYAGE_API_KEY` env var).
- `--voyage-model <model>` (optional, default `voyage-4-lite`). The default must stay in sync with the backend's `VOYAGE_EMBED_MODEL` default (`apps/zoltar-be/src/config/env.schema.ts`) — the same model, not merely a model of the same width. Two different models at 1024 dimensions produce similarity scores that look plausible and mean nothing.
- `--skip-hash-check` (optional): proceeds without hash verification, logs a warning. For users with different editions who know fixups won't apply cleanly.
- `--dry-run` (optional): runs extraction and chunking, logs chunk count and first-chunk preview, exits before embedding or inserting. Avoids Voyage spend while debugging chunking.

### Pipeline steps

Per `docs/rules-ingestion.md`:

1. **Hash verification** against `ingestion/<system>/hashes/<edition>.txt`. Warn on mismatch but don't block — a mismatch may mean a different printing, not a corrupted file. Block only with an explicit `--require-hash` flag (not in M7.2 scope; add when anyone actually needs it).
2. **Marker extraction** to a temp directory: `marker_single <pdf> --output_dir <tmp> --output_format chunks --disable_ocr`, not the `markdown` output format an earlier draft of this spec (and `docs/rules-ingestion.md`) both specified. Typed blocks with page and bbox metadata are what every downstream step depends on; Markdown discards that structure. `--disable_ocr` assumes a clean embedded text layer, true for the Mothership PSG — marker's default OCR path depends on a `llama.cpp` binary not installed by this pipeline's dependencies, and costs roughly 3x the extraction time. Pinned marker version in `requirements.txt`.
3. **Fixup patch application** from `ingestion/<system>/fixups.json`, matched on block `id` (e.g. `/page/11/Table/5`) — not the `{section, contains}` matcher an earlier draft of this spec and `docs/rules-ingestion.md` both specified, which cannot express the confirmed extraction defects (`contains` needs text to match, and the defective blocks have none; `section` derives from marker's `section_hierarchy`, rejected below as unreliable). Empty array for M7.2; plumbing exists for future editions and corrections.
4. **Reading-order sort.** Marker's emitted block order is not reading order on multi-column pages — a chunker that merges in emitted order concatenates a meaningful share of the book's body pages backwards (`docs/rules-extraction-findings.md § S6.2`). A deterministic geometric sort over each block's bbox recovers correct order: full-width blocks (≥60% of page width) flush the current column band and stand alone; everything else is banded by vertical position and split left/right by horizontal midline. No model call, and none is acceptable here — see the boundary note below.
5. **Page and chapter attribution**, per block, read directly from the PDF's running footer via `pypdfium2` — not from marker's own `page` field (an internal id, not a page number: physical page 0 → `'7'`, 1 → `'512'`, plausible-looking and wrong) or its `section_hierarchy` field (records the last heading seen at each visual level, which turns siblings into parents on scrambled pages, not true ancestry). Edition- and printing-specific; a new edition needs its own footer-format check before ingestion.
6. **Block-based chunking**: merge the sorted, attributed blocks (`Text`, `Table`, `ListGroup` — `SectionHeader`, `PageHeader`, `PageFooter`, `Picture` dropped) toward a ~400-token target, 50–100 token overlap between adjacent chunks, never splitting a `Table` block. A chapter change (step 5) forces a chunk boundary regardless of token count. Supersedes the `###`-heading-boundary approach this spec originally described — a confirmed dead end at 10 headings for a book that block-chunks to 65 (`docs/rules-extraction-findings.md § S1.5`). See `docs/rules-ingestion.md § Step 4` for the canonical algorithm.
7. **Voyage embedding** with `input_type="document"`. The embeddings endpoint accepts up to 1,000 texts per request, bounded by a per-model token cap (1M tokens for the lite tier). A PSG-sized book fits in a single call; batch anyway so the code doesn't need revisiting for a larger rulebook.
8. **Dimension check**: assert the returned vector length equals `game_system.embedding_dim` for the target system (1024) before inserting or deleting anything. This is the guard that would have caught the `voyage-3-lite` 512-dimension mismatch at M7 time — see `docs/decisions.md § Embedding model`. Exit `3` on failure.
9. **Postgres insert**: look up `game_system.id` by slug, `DELETE FROM rules_chunk WHERE system_id = <id>` for idempotency, then insert one row per chunk.

**The boundary on step 4, stated explicitly because it's easy to reach for the wrong tool:** the sort must be deterministic and make no model calls, ever, in the pipeline path. An LLM-assisted flagging pass may be used offline to spot-check pages the sort's own regression test can't validate against ground truth (pages without numbered section headers), but it validates the sort's output — it does not perform the reordering. Where geometry genuinely can't resolve a page, the escape hatch is a hand-blessed ordering recorded once per edition in `fixups.json`, keyed on block `id`, same as step 3.

**Two known gaps step 4–6 do not resolve, both tracked in `docs/roadmap.md` M7.2 as not yet scoped:**

- A portion of `Table` blocks extract with no text at all (14 of 32 for the PSG), dropping the pages they cover from the index entirely until a fixup or a second extraction pass addresses them (`docs/rules-extraction-findings.md § S3.2`).
- 5 pages don't resolve a chapter from the running footer. This pipeline attributes those chunks with `source` (page number only, still available from the block `id`) and a null/unresolved chapter rather than failing the run — a placeholder, not a design decision about the right fallback. `docs/rules-extraction-findings.md § Open questions` has the page list and the open options (nearest `SectionHeader`, or a synthetic chapter label).

### Exit codes

- `0`: success.
- `1`: PDF not found, unreadable, or hash check failed with `--require-hash` (future).
- `2`: marker extraction failed.
- `3`: Voyage API error (non-transient), or an embedding whose dimension does not match `game_system.embedding_dim`.
- `4`: database error.
- `5`: invalid arguments.

## Part 3: Dependencies

`ingestion/requirements.txt` — pin exact versions at implementation time:

```
marker-pdf==<pinned>
voyageai==<pinned>
psycopg[binary]>=3.2
tiktoken>=0.8
pypdfium2>=5.10
```

Notes:

- `marker-pdf` is the extraction tool — pinning is load-bearing because extraction variance across versions affects which fixup patches apply. The pin lands in the PR; bumping it is a deliberate later decision.
- `voyageai` is the official Python SDK. Using the SDK rather than raw HTTP calls (which `VoyageService` in the backend does) because the ingestion pipeline needs batching and the SDK handles it cleanly.
- `psycopg[binary]` avoids requiring `libpq-dev` at install time — friendlier for self-hosters.
- `tiktoken` counts tokens for chunk-size heuristics. Note that it is OpenAI's tokenizer, not Voyage's, so the counts are an approximation of what Voyage will bill and window. That is acceptable — the ~400-token chunk target is a retrieval-quality heuristic with no hard boundary, and the PSG is nowhere near the 32k per-input context limit. If chunk sizing ever needs to be exact, `voyageai.Client().count_tokens()` is the accurate source and `tiktoken` can be dropped. Still an open, unmeasured question whether the approximation actually holds — tracked in `docs/rules-extraction-findings.md § Open questions`, not yet a problem worth spending on.
- `pypdfium2` is used directly by `chunk.py` to read printed page numbers and chapter names from each page's running footer. Marker detects `PageFooter` blocks but emits them empty — it treats footers as noise and strips them — so this pipeline reads footer text independently rather than through marker's own output. It's likely already present as a transitive dependency of `marker-pdf` (marker uses it internally for rendering), but it's pinned explicitly here because the pipeline code imports and calls it directly, not just through marker.

Python 3.11+ is the supported version. Document in the README.

### 4.3 Sanity check

After the pipeline completes, Alex runs a manual `rules_lookup` verification. Options, best first:

- **Drive a real turn through the eval harness** (`npm run eval:run`, or `task eval:run`) against a fixture whose player input provokes a rules question. This exercises the same `RulesLookupService` path the Warden uses, with the same `VOYAGE_EMBED_MODEL`, and the captured `warden-output.json` records the lookup. Closest thing to a production check, and it already exists.
- **A one-off script under `apps/zoltar-be/scripts/one-off/`** that instantiates `RulesLookupService` and calls `lookup()` directly. Cheaper than a full turn if the only question is whether retrieval works.
- **A SQL query directly against pgvector** — requires generating a query embedding by hand, so least convenient, but it isolates the database from the service layer if the first two disagree.

Note that there is no `POST /actions` endpoint and no NestJS REPL — an earlier draft of this spec assumed both. The HTTP surface is `POST /campaigns/:campaignId/adventures/:adventureId/messages` and `/dice-results`; see `docs/api.md` and `docs/decisions.md § Narrative and dice-result submissions are separate endpoints`.

Expected outcome: a query like "what happens when a character panics" returns chunks from the Panic section in its top hits — measured, it returns `PANIC CHECKS p.21` at ranks 1 and 2, scoring 0.456. **Judge the citations, not the score**: the similarity numbers this model produces for correct answers sit well below the 0.5 an earlier draft expected, and no numeric bar survives contact with the measurement (Done When 3, `docs/rules-extraction-findings.md § S12.2`). (Not "panic check of 73" — that's the Mothership **0e** d100 mechanic; the 1e PSG this pipeline ingests uses a d20 table. See Done When 3.)

### 4.4 The seeded rows are not committed

`rules_chunk` is populated per-environment. Alex's local run populates his local DB; CI runs against an empty test DB; self-hosted users run the pipeline against their own PDFs. No seed data lives in version control.

Specified in full as Part 8, not here — it's TypeScript, not part of the Mothership seeding workflow this Part covers, and it's substantial enough to warrant its own Part rather than a subsection.

## Part 6: Post-Ingestion Validation — superseded, moved to M7.5

**This section no longer describes M7.2's Done-When criteria.** It's retained below because the reasoning is still correct and still needs a home — just not this one. See the second sequencing note at the top of this document for why: M7.5 (Rules Retrieval Quality) now sits between M7.2 and this validation, and the chunking rebuild, query preprocessing, and similarity floor it owns are all things that would change these numbers if this validation ran first. `docs/roadmap.md` M7.5 carries "Re-baseline both models against the final index" and "Dedicated playtest against the final index" as its own bullets, using "final" deliberately — this content, unmodified, is what those bullets inherit.

Both activities here are TypeScript-and-play, not Python. They are relevant to the ingestion milestone only in the sense that they are the only way to know the pipeline did something useful: a chunk count proves the table has rows, not that the Warden is better off.

**Run 6.1 before 6.2's fixtures land.** `corpusVersion` is a SHA-256 content hash over every file in `eval/fixtures/` (`eval/corpus-version.ts`), and `eval:compare` warns on any cross-corpus pairing — deliberately, because that is the silent-poisoning case the content hash was introduced to prevent. New fixtures from the playtest change the hash. Re-baseline first, against the corpus as it stands (`88fa84bd8329`), then capture.

### 6.1 Eval re-baseline

Full corpus, uniform N, both models (`claude-sonnet-4-6` and `claude-sonnet-5`), compared against the re-scored `88fa84bd8329` runs. N is 10 as of the 2026-07-29 calibration; keep it uniform rather than adaptive, per `docs/eval-methodology.md`'s adaptive-N hazard.

Why it is owed: three `docs/decisions.md` entries — `§ Warden model upgraded to claude-sonnet-5`, `§ Agentic graph decomposition stays deferred`, and `§ rollType / gatedByRollId / actingEntityId on roll_dice stay deferred` — each note that every existing baseline executed against an empty `rules_chunk` index, and each defers a conclusion until this measurement exists. Rates measured against the empty index are provisional, not wrong.

Prerequisites and hazards:

- **The index must be populated in the database the harness points at.** Per Part 4.4, `rules_chunk` is per-environment. Seeding Alex's dev Postgres does not seed whatever `DATABASE_URL` the eval run uses, if they differ. A re-baseline against an empty index measures nothing new and looks exactly like a successful run.
- **The comparison is not model-vs-model, it is index-vs-index.** Same prompt hash, same corpus, same N, same grader — the populated index is the only intended variable. If the `roll_dice` schema fields are going to land (see the third decisions entry, which wants them to land *with* this re-baseline rather than forcing a second one), that decision has to be made before the run, not after: adding them changes the tool schema, which changes what reaches the Warden, which invalidates the frozen artifacts.
- **Update `Current baseline N` in `docs/eval-methodology.md`** if applicability or variance shifted. Rules availability plausibly changes reach-for-dice behaviour, which is exactly the kind of shift that moves applicability denominators on the roll-shaped checks.

### 6.2 Dedicated playtest

A real Mothership session against the populated index, reviewed with the M7.1 tooling (`task playtest:review`). It answers two different questions, and neither is answerable from the harness alone:

- **Did the index actually help?** The harness replays frozen turns from adventures that ran without rules. It can show whether the Warden's behaviour on those turns changed; it cannot show whether a live session goes better. Harness-only validation of this milestone stays provisional.
- **Does it supply the fixtures M7.4 is still waiting on?** `MISSING-CANON-CAPTURE`, `UNSURFACED-CHECK`, `OVER-RESOLUTION`, and `SCENE-JUMP` each sit at a single fixture. The M7.4 spec flags the first three as needing a second confirmed instance before the category counts as adequately covered; `SCENE-JUMP` was added after that spec and inherits the same bar. Capture with `task eval:capture-fixture`, which wraps M7.3's `reconstructStateAsOfTurn`.

One caution: a single session is not guaranteed to exhibit all four failure modes, and a fixture authored from a turn that did not actually exhibit its tag is worse than a missing fixture — it pins a check to behaviour that was never wrong. If a tag stays at one instance after the playtest, that is evidence about how rare the mode is, and M7.4's fixture bullet stays open rather than being closed by a manufactured instance.

## Part 7: Query Preprocessing for `rules_lookup`

**TypeScript, not Python.** Lives in `apps/zoltar-be`, wherever `RulesLookupService` currently sits — not `ingestion/`. Included here because it's decided and roadmap-tracked under M7.2, but it's a genuinely different stack and lifecycle from Parts 1–4, same reasoning the Goal section gives for why M7 and M7.2 were split in the first place. Keep that boundary visible rather than let it blur.

### 7.1 Mechanism

Per `docs/decisions.md § Query preprocessing for rules_lookup promoted from optional to critical path`: a document-frequency ceiling computed from the index itself, not a hand-authored stopword list. The latter would need per-system authoring and tuning; the former is derived automatically from whatever `rules_chunk` content actually exists for the active system, so it generalizes to UVG, OSE, and 5e without a new list per system.

1. Tokenize the incoming query with `to_tsvector('english', query)` — the same lexeme approach already used throughout the investigation to measure corpus term coverage (`docs/rules-extraction-findings.md § S3.6`, `§ S8`, `§ S9`), so "is this term high-frequency" is measured the same way "is this term in the corpus at all" was measured.
2. For each lexeme, compute its document frequency within `rules_chunk` for the active `system_id` — the share of chunks whose content contains it.
3. Drop any lexeme whose document frequency exceeds a threshold (7.3).
4. **Rebuild the query from surviving original words, not surviving lexemes.** The lexeme is what decides whether a word survives; what gets embedded is the original word from the query text. Passing Voyage a bag of stemmed lexemes (`"perceiv notic environ"`) is not natural language and wasn't what any of the retrieval investigation tested — every measured improvement in `docs/rules-extraction-findings.md § S4`/`§ S5.3` came from trimming a real sentence to its distinctive words, not from stemming it.
5. If dropping would leave fewer than a floor count (proposed: 2 surviving words — see 7.3), keep the least-frequent remaining words instead of stopping at zero. A query preprocessed into an empty string is worse than one that skipped preprocessing entirely.

### 7.2 Where the frequency computation runs — no new schema

No new table, no migration. Document frequency is computed live via a query against `rules_chunk` filtered to `system_id`, either with `to_tsvector('english', content) @@ to_tsquery('simple', lexeme)` or a simpler `ILIKE` count — implementation's call, both are single indexed-or-not table scans over a few hundred rows for Mothership. This keeps "no changes to `docs/schema.md`" true for this Part too, matching the rest of M7.2.

This is a live-computation choice, not a caching one, and it's deliberately the simpler option: Voyage's own round trip is ~98% of the query latency budget (`docs/rules-extraction-findings.md § S5.4`), so a few extra small table scans for term frequency don't compete for the budget that matters. **This may need revisiting once a larger corpus lands** — a Phase 3 system like the 5e PHB could produce thousands of chunks, and computing frequency per query term against thousands of rows on every turn is a different cost profile than against Mothership's 65. Same shape of caveat as the existing "Batch ingestion rate limits for larger rulebooks" deferral; see the new deferral entry below.

### 7.3 Threshold and floor — proposed starting values, not measured ones

Nothing in the findings pins an exact document-frequency percentage; the investigation showed the qualitative effect (dropping high-frequency terms helps retrieval, sometimes substantially), not a tuned cutoff. Proposed starting point: drop lexemes present in more than **40% of the active system's chunks**, with a floor of **2 surviving words**. Both are constants (env var or config, not hardcoded inline), because Part 8's harness is exactly the tool that should sweep this value once it exists — treating the 40% as settled would waste the harness's first and easiest use.

### 7.4 Safety and testing

- A query where every word clears the threshold (all high-frequency) must still produce a non-empty embeddable string — the floor in 7.1.5 exists for this case.
- Unit test: a synthetic small `rules_chunk` corpus (a handful of rows with known content) plus a verbose test query, asserting the high-frequency words get dropped, the distinctive ones survive, and the floor holds when tested against an all-high-frequency query.
- No end-to-end test against real Voyage calls is required for this Part specifically — Part 8's harness, run with and without preprocessing, is the real measurement of whether this works, not a unit test of the trimming logic alone.

## Part 8: Retrieval Eval Harness

**TypeScript, not Python.** Lives alongside the existing `eval:*` family (`scripts/eval-run.ts` and siblings), not `ingestion/` — it needs to exercise the same `RulesLookupService`/Voyage path the Warden and Part 7 use, the same reasoning Part 4.3 already gives for why that's the closest thing to a production check.

### 8.1 Purpose and metrics

Recall@3, recall@5, and MRR (mean reciprocal rank), scored deterministically against page-labeled fixtures. Voyage calls only — no judge, no second LLM call — so it's cheap enough to run on every chunking or preprocessing change during M7.5's iteration. Without this, "did that chunking change help?" has no answer but hand-judgment on a handful of queries, which is exactly the gap S3–S5's qualitative gut-checks left open.

### 8.2 Fixture format

One JSON object per line, `eval/retrieval-fixtures/<system>.jsonl` — **deliberately not under `eval/fixtures/`**, which is the M7.4 Warden-turn fixture directory `corpusVersion` hashes (`docs/decisions.md § checkId does not encode checkMode` and neighbors). Retrieval fixtures and Warden-turn fixtures are different things scored by different tools; letting them share a directory would make retrieval-fixture edits silently bump `corpusVersion` and trigger `eval:compare`'s cross-corpus warning on unrelated M7.4 runs.

```json
{
  "id": "rq-001",
  "system": "mothership",
  "query": "perception check looking around environment, noticing details",
  "expected_pages": [17],
  "answerable": true,
  "source": "sampled from turn19 fixture family (UNSURFACED-CHECK)",
  "notes": ""
}
```

- `expected_pages` — an array because a topic can span more than one page; recall counts a hit if **any** listed page appears in the top-K, not all of them.
- `answerable: false` pairs with `expected_pages: []` for the deliberately-unanswerable set (8.3).
- `source` — provenance back to the M7.4 fixture/tag this query was sampled from, or "hand-authored" for the unanswerable set. Not used by scoring; kept for anyone auditing why a fixture reads the way it does, same rationale as `capture-fixture`'s existing placeholder convention.

### 8.3 Sampling and labeling workflow

1. A one-off script (`scripts/sample-retrieval-fixtures.ts`, Node — the source data is JSON eval-run output in `unicorn-artifacts`, the same shape the existing `eval:*` scripts already read) extracts distinct `rules_lookup` query strings, tagged by the M7.4 fixture they came from.
2. Cap sampling at a fixed count per fixture tag (proposed starting point: 5) rather than sampling proportional to raw invocation count — the direct fix for the combat-skew `docs/rules-extraction-findings.md § S8.1` flagged in the eval-run sample.
3. The script emits stub fixtures with `query` and `source` filled in, `expected_pages` and `answerable` left as an explicit `null`/TODO placeholder — the same fail-closed convention `capture-fixture` already uses for `applies: false, TODO reason`, so an unedited stub can never silently score as answerable.
4. A human (not the harness, not an LLM in the scoring loop) labels each stub with the correct page(s) by checking the PSG directly.
5. Separately, author a deliberately-unanswerable set (proposed starting point: 10 fixtures) drawn from the concept-absent bucket `docs/rules-extraction-findings.md § S9.3` already identified: suppressive fire, flanking, opposed rolls, difficulty numbers, android shutdown. These don't need sampling from real queries — the point is coverage of "the book genuinely has nothing to say here," and S9 already named the mechanics that qualify.

Both counts (5 per tag, 10 unanswerable) are starting points to get the harness populated with something real, not derived from a target precision calculation. Revisit once the harness has run a few times and it's clear whether the fixture count is actually discriminating between chunking changes.

### 8.4 Scoring

`task eval:retrieval [--system <slug>] [--fixtures <path>] [--no-preprocess]`

For each fixture: apply Part 7's preprocessing (unless `--no-preprocess`, which exists specifically to let this harness measure preprocessing's own effect — run the fixture set with and without it and diff the recall numbers), embed via Voyage, run the same cosine-similarity query `rules_lookup` runs, take the top 5 chunks' pages.

- **recall@K** (K = 3, 5): over *answerable* fixtures only, 1 if any `expected_pages` entry appears in the top-K returned pages, else 0. Averaged.
- **MRR**: reciprocal rank of the first expected-page hit within the considered results, 0 if absent. Averaged over answerable fixtures.
- **Applicability**: answerable fixtures scored vs. unanswerable fixtures excluded from the recall/MRR denominator — reusing the same discipline `docs/decisions.md § Applicability is reported alongside every rate` already established for the M7.4 harness, not a new convention.
- **Unanswerable fixtures are not scored for recall/MRR** — their top-1 cosine similarity is recorded and reported as its own distribution, separate from the answerable set's correct-hit similarities. This is the raw material `docs/rules-extraction-findings.md § S5.5`'s three-point observation needs to become a real sample: whether answerable-correct and unanswerable top-1 scores actually separate cleanly enough to derive a floor is M7.5's question, but this harness is what produces the numbers to ask it with.

### 8.5 Output

A report in the same spirit as `eval:report`: overall recall@3/@5/MRR, a per-fixture-tag rollup (so a chunking change that helps combat queries but hurts investigation queries is visible, not averaged away), applicability, and the answerable-vs-unanswerable similarity distribution. Exact output location and format (console vs. file, where under `ZOLTAR_EVAL_ROOT` it might write) is an implementation detail for whoever builds this — proposed rather than fixed here, since the existing `eval:*` conventions are the better reference to match against at implementation time.

### 8.6 What this does not do

- No judge, no LLM grading call, anywhere in the scoring loop — purely deterministic.
- Does not derive or set the M7.5 similarity floor itself. It produces the score distributions M7.5's floor decision consumes.
- Does not replace the M7.4 Warden-turn harness. Different question — this asks whether retrieval finds the right page; M7.4 asks whether the Warden behaves correctly once it has what retrieval returned.

## Testing Summary

The ingestion pipeline is Python, runs offline, and calls external services (Voyage) with disk-heavy dependencies (marker's extraction models). Full end-to-end testing in CI is not practical. Testing coverage is deliberately partial. **This section covers Parts 1–4 (the Python pipeline) only** — Part 7's unit test is specified inline at 7.4, and Part 8's harness is itself a testing tool rather than something with its own separate test suite specified here.

**Unit test (in CI):**

- `ingestion/tests/test_chunk.py` — runs `pipeline/chunk.py`'s pure functions against small synthetic block lists (dicts shaped like marker's `chunks` output: `id`, `block_type`, `bbox`, `page`) with known reading order, known chapter boundaries, and known table-block positions, and asserts:
  - The reading-order sort recovers correct left-then-right order on a synthetic two-column page, and leaves an already-correct single-column page unchanged — the same case the real sort was validated against (`docs/rules-extraction-findings.md § S7`), at unit-test scale.
  - A chapter change forces a chunk boundary regardless of token count.
  - A `Table` block is never split across a chunk boundary, even when it pushes a chunk over the ~400-token target.
  - Overlap between adjacent chunks from the same chapter is within the 50–100 token band.
  - Chunks carry the correct footer-derived `source` string and chapter-level `section_path`, given synthetic page/footer inputs — not marker's `page` field or `section_hierarchy`, neither of which the module reads for this purpose.

Page-and-chapter attribution is tested against synthetic footer strings passed directly to the attribution function, not against a real PDF — keeping `pypdfium2`'s actual file I/O out of the unit test the same way `extract.py` and `embed.py` are kept out.

This is the only ingestion test that runs in CI, and it earns that by needing nothing: no marker models, no Voyage key, no database, no real PDF. It requires a new Python job in `.github/workflows/ci.yml` alongside the existing `backend` and `frontend` jobs — `actions/setup-python`, install `pytest` plus whatever `chunk.py` imports, run `pytest ingestion/tests/`. Installing the full `requirements.txt` (marker and its extraction models) in CI would defeat the purpose; the chunking module must therefore not import anything from `extract.py` or `embed.py` at module scope.

**Manual verification (not in CI):**

- Alex runs the full pipeline locally against the Mothership PSG and records the outcome in the PR description: chunk count, a sample query, and the top similarity score for a known-good question.

This section covers testing the pipeline *code*. Whether the pipeline produced something worth having is Part 6's question, and neither the unit test nor the manual run answers it.

**Not tested:**

- Marker extraction accuracy — covered by marker's own upstream tests.
- Voyage embedding — external service, not meaningful to mock end-to-end.
- Postgres insert — standard SQL, covered indirectly by the manual verification.

## Deferrals Introduced in M7.2

### Batch ingestion rate limits for larger rulebooks

The Mothership PSG produces 65 chunks (measured — see Done When 2). Voyage's embeddings endpoint accepts up to 1,000 texts per request, so this is a single call — no rate limit concerns, with more headroom than the original 100–400 estimate assumed. Larger rulebooks (D&D 5e PHB, Pathfinder Core) may produce thousands of chunks and hit per-minute rate limits. Revisit when a Phase 3 system lands.

### PDF hash stability across printings

TKG has released multiple printings of the Mothership 1e Player's Survival Guide. Different printings have different hashes even when content is identical. The hash file records Alex's printing; users with different printings see a warning on every run. Acceptable for M7.2 — the fixup file is empty, so warnings don't block anything. Revisit if fixups grow and the warning becomes meaningful noise.

### Chunk quality evaluation — resolved

~~There is no automated metric for "how good is this chunking" in M7.2. The manual sanity query is the only quality check.~~ **Resolved: Part 8 now designs the retrieval eval harness in full** — recall@3/@5, MRR, page-labeled fixtures sampled from the 596 real queries in `unicorn-artifacts` (`docs/rules-extraction-findings.md § S8`), plus deliberately-unanswerable fixtures for the similarity-floor question. What was originally deferred here — an automated metric beyond the manual sanity query — now ships as real scope, not roadmap aspiration. Kept as an entry rather than deleted, so the reasoning that shaped Part 8's design (M7.1's playtest evidence, the 596-query sample, the combat-skew problem in how those queries were recorded) stays attached to why the harness looks the way it does.

### Empty `Table` blocks not resolved by M7.2

14 of 32 `Table` blocks in the PSG extraction carry no text at all (`<p></p>`), taking the pages they cover — physical 11 and 12 (FIREARMS, INDUSTRIAL EQUIPMENT) — out of the index entirely (`docs/rules-extraction-findings.md § S3.2`). Equipment stats are a plausible Warden query, so this isn't a cosmetic gap. Not scoped for M7.2: whether the fix is a fixup-file entry per defective block, or a second extraction pass targeted at table regions, is still an open decision (`docs/roadmap.md` M7.2). M7.2 ships with these pages absent from the index rather than blocking on a decision that needs its own investigation.

### Fallback chapter attribution for footer-less pages

5 pages don't resolve a chapter from the running footer (physical 0, 1, 2, 10, 43 as measured against the PSG 1e — the exact set is edition-specific). Page 10 (equipment continuation) is reachable body content and is the one most likely to matter for retrieval; pages 1 and 43 duplicate live body rules as reference cards; 0 and 2 are cover/credits and plausible candidates to drop the way the character-creation spread was, but not yet checked with the same rigor (`docs/rules-extraction-findings.md § Open questions`). M7.2 attributes these chunks with a page-derived `source` and a null chapter rather than failing the run, but doesn't implement any of the real fallback options (nearest `SectionHeader`, a synthetic chapter label). Revisit once it's clear whether any of these pages actually gets queried — page 10 is the one worth watching for in the eventual M7.5 playtest.

### Query preprocessing's threshold and live frequency computation are unvalidated defaults

Part 7.3's 40% document-frequency threshold and 2-word floor are proposed starting points, not measured ones — nothing in the findings pins an exact cutoff, only the qualitative direction (dropping high-frequency terms helps, sometimes substantially). Part 8's harness, once built, is the tool that should sweep this value; treating 40% as settled before then would waste the harness's first and easiest use.

Part 7.2's live-SQL frequency computation is sized for Mothership's 65-chunk corpus (measured; the original estimate was 100–400). A Phase 3 system with thousands of chunks (D&D 5e PHB) changes the cost of computing frequency per query term against the full table on every turn — same shape of concern as "Batch ingestion rate limits for larger rulebooks," above. Revisit together when a Phase 3 system's actual corpus size is known, rather than guessing at a caching strategy now against a corpus that doesn't exist yet.

### Re-ingestion without dropping resolved `rules_chunk` references

M7.2's idempotency strategy is `DELETE FROM rules_chunk WHERE system_id = <id>` before insert. No table currently references `rules_chunk.id`, so this is safe. If Phase 2 adds a table that cites specific chunks (e.g. a review queue for adjudication quality), re-ingestion needs a gentler update path. Revisit when that table first needs to exist.
