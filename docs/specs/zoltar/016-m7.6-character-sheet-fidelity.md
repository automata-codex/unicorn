**Status:** ready for implementation

**Inputs:** `m7.6-psg-character-sheet-inventory.md` (rules side, PSG v1.2 by section) ·
`m7.6-code-inventory.md` @ `e1cdaac` (code side, `path:line`) ·

---

## Why this milestone exists

The Mothership character sheet does not describe Mothership. Against the Player's Survival
Guide, of 20 leaf fields 5 are correct, 4 have no referent in the rules at all, and 11 are
the wrong shape or in the wrong place. Fourteen rules concepts have no representation —
including **Wounds**, which is the game's death condition.

Two of the four unreferenced fields are 5e mechanics: a `level` field in a game with no
levels, and an `HP_DEFINITION` threshold sending 0 HP straight to a Death Save, which is
the 5e rule standing in for Mothership's wounds cycle. See
`decisions.md § The D&D-5e-bias hypothesis has a confirmed instance, in the schema rather
than in retrieval`.

This is closer to a rewrite than an edit. Sizing it as an edit is how it stayed broken
through M2, M3, M5, M6 and M7.

## Ordering, and why

Six Parts. The order is load-bearing: built in another order, several are built twice.

1. **Schema and migration** — everything else reads these shapes.
2. **Tool schema and Warden prompt** — instructions must ship with the schema, or a second
   re-baseline is owed.
3. **Wounds** — needs `damageType` from Part 2 and the wounds pool from Part 1.
4. **Renders** — need the data sources Parts 1–3 create.
5. **Frontend** — last consumer; changed earlier, changed twice.
6. **Eval** — measures the result.

## Non-goals

Skill Training, pets, and High Score are out (diff §7). Cryosickness, exhaustion, food and
water, radiation level, and temporary roll modifiers are out (PSG inventory §5.5).
Adventure-scoped state separation is Phase 2 behind the single-adventure constraint
(`decisions.md § Adventure state gets its own row…`). The rules-engine arithmetic layer is
Phase 3 — every computation here is Warden-side.

# Part 1 — Schema and migration

## 1.1 The sheet

Reduce `MothershipCharacterSheetSchema` to immutable creation data, per
`decisions.md § State placement is decided by the lifetime of the referent, not the
lifetime of the value` (axis 1: does the value change during play?).

**Retained:** `entityId`, `name`, `pronouns`, `class`, `notes`, `trinket`, `patch`,
`traumaResponse`, `creationRolls`.

**Removed:** `level`, `stats`, `saves`, `maxHp`, `maxStress`, `skills`, `equipment`.

`traumaResponse` is stored, not derived from `class`: Military Training grants the
Marine's response to any class (PSG §25.1). `class` itself is unchanged —
`MothershipClassEnum` is already exactly the four PSG classes.

**Retain the creation rolls as rolled**, in a `creationRolls` object. Not read by any
mechanic; an immutable record of an event that happened.

Store the **dice as rolled, not the sums** — `strength: [7, 4]`, not `36`. Same storage,
and it preserves the doubles information a sum discards. Cover every roll made at
creation:

| Key | Roll |
|---|---|
| `strength` `speed` `intellect` `combat` | `2d10` (the `+25` and class adjustment are arithmetic, not rolls) |
| `sanity` `fear` `body` | `2d10` |
| `maxHp` | `1d10` |
| `credits` | `2d10` |
| `trinket` `patch` | `d100` |

**This cannot become the second authority §1.1 otherwise guards against**, and the
distinction is worth stating because it looked the same at first glance. A `maxHp` field
on the sheet was a *duplicate* of the pool's ceiling — the same fact in two places, free to
diverge, and it did. A creation roll is a *different fact* from the current value: it
records what the dice showed, which no later event can change. Nothing can write it after
creation and nothing reads it as state.

Three uses, none of them mechanical:

- **Distinguishing bad luck from attrition.** Strength 27 means one thing if it was rolled
  and another if it was rolled 42 and drained by fifteen. `reason` explains individual
  deltas; the creation roll anchors the whole sequence. Together they close the PSG
  inventory's §5.7 question completely rather than partially.
- **Auditing the class adjustments** added in Part 5 — rolls plus class arithmetic should
  reconcile to the starting ceiling, and that is checkable.
- **Character history**, once self-hosters can run a second adventure.

**Skills and equipment** move to campaign state (§1.3). Their reshaping — tiered skills
over a prerequisite graph with per-skill suppression, stateful equipment with charges and
rounds and doses — is specified in the diff §5 and is in scope here.

## 1.2 Pools

Ten pools per player character, all in `campaign_state.data.resourcePools`.

| Pool | `PoolDefinition.min` | `PoolDefinition.max` | Instance `max` | Notes |
|---|---|---|---|---|
| `hp` | `0` | `null` | `1d10+10` at creation | **`min` moves off `null`** — HP currently goes negative and stays there |
| `wounds` | `0` | `null` | 2, +1 Marine, +1 Android | New |
| `stress` | `0` | `null` | `null` | Seeded `current: 2`, not 0 |
| `strength` `speed` `intellect` `combat` | `0` | `null` | creation roll + class adj. | `2d10+25` |
| `sanity` `fear` `body` | `0` | `null` | creation roll + class adj. | `2d10+10` |
| `credits` | `0` | `null` | `null` | `2d10×10`, or `2d10×100` if forgoing a loadout (PSG §6.1) |

**Thresholds are empty for all ten.** None fires a mechanical event on crossing a number.
The wounds→Death Save transition is Warden-driven (Part 3), not a threshold.

**The per-instance `max` carries the mutable ceiling.** `ResourcePoolSchema` is
`{ current, max }`, distinct from `PoolDefinition`'s system-level `min`/`max`/`thresholds`.
Maximum Health is the hp pool's `max`; Maximum Wounds is the wounds pool's `max`. No
separate ceiling pools.

**Two ceilings are monotonically decreasing with no recovery path in the book:** Maximum
Health (Death table `00`, −`1d5`) and Maximum Wounds (Panic `19`, −1). This is deliberate
attrition design, not an omission — do not add a restoration path.

**Stress cannot get its correct floor or cap from this mechanism.** `PoolDefinition.min` is
a system constant; Mothership's floor is *Minimum Stress*, per-character and mutable
(PSG §20.2). And §20.1 does not reject overflow past 20 — it converts the excess into a
reduction of the most relevant Stat or Save, a cross-pool effect no validator supports.
Both are handled by prompt instruction in Part 2. Record this in code comments where
`min: 0` and `max: null` are set, or the next reader will "fix" them.

**Minimum Stress** is a per-character mutable value with no pool of its own (it is a floor,
not a resource). Store it in the conditions map's sibling scope — see §1.3.

## 1.3 Campaign state additions

- **Pools become nested by entity:**
  `resourcePools: { [entityId]: { hp: { current, max }, stress: {...}, … } }`, replacing
  the flat `{entity_id}_{pool_name}` composite key. `getMothershipPoolDefinition` receives
  the pool name directly — delete the suffix matching rather than extending it to ten
  cases. No identifier gains a dot, so
  `decisions.md § Entity and resource pool identifiers use underscores only` still holds
  for identifiers; only its composite-key pattern lapses, and it needs an amendment saying
  so.
- **Merges must become deep.** This is the sharp risk in the nesting change.
  `mergePlayerResourcePools` (preserve-on-conflict) and `applyValidatedTurn` (plain shallow
  spread) both operate at the top level today. Nested, a shallow spread at the entity level
  **clobbers every pool that entity owns** when one is written. Fix both, and add a test
  that writes one pool and asserts the other nine survive.
- **`CharacterService.delete` now removes pools.** Orphaned pools persisted because
  removing them meant a prefix scan; nested it is `delete pools[entityId]`. Fixing this
  also closes the adjacent defect where an empty player-entity set disables `actingEntityId`
  validation entirely (`session.service.ts:908-912`).
- **Conditions:** a dedicated map keyed by entity id. Entries are parameterised —
  *Frightened* stores what frightened the character, *Loss of Confidence* stores which
  skill loses its bonus. `entities[].status` is not sufficient: it is `string[]` and cannot
  hold the parameters, and the *Loss of Confidence* parameter is a link into the skills
  list.
- **Skills, equipment, worn armor, minimum stress, bleeding, pending Death Save:** per
  entity, shapes per diff §5 and §7.

**Worn armor** is `{ item, apBase, apCurrent, destroyed, dr, o2Remaining, features[] }`.
AP is consumed — damage ≥ AP destroys the armor (PSG §28.3) — and a patched vaccsuit is
AP 1. DR applies first and survives both destruction and Anti-Armor.

## 1.4 Migration

**Drop and recreate. Confirmed 2026-08-14.** No `character_sheet` rows exist that matter:
local dev is empty, the Droplet runs only the eval harness, and no fixture carries sheet
data. Do not write a defensive transform.

The pre-`v0.1.0` Flyway consolidation pass makes this migration disposable in any case.
Preserve any non-obvious reasoning in `decisions.md` before the consolidation discards the
file.

**`mergePlayerResourcePools` cannot overwrite** — re-running the derivation against changed
sheet data is a no-op whenever pools exist, which is always after creation. Any path that
changes a ceiling must write the pool directly. Sheet-only writes silently do nothing.

## 1.5 Do not add read-side validation

No read path currently parses `character_sheet.data`; the sheet is validated on write only.
The eval harness depends on this: `harness-runner.ts:326` deliberately seeds a row with
`{ entityId }` alone, one of nine required fields, because without it `getPlayerEntityIds`
returns `[]` and the run measures a code path production does not take.

Adding read-side validation breaks every eval run. If it is wanted, the harness seed
changes in the same milestone — but it is not in scope here.

# Part 2 — Tool schema and Warden prompt

## 2.1 The pool-delta object

```
resourcePools: [
  { entityId: string, pool: string, delta: number,
    maxDelta?: number, reason: string, damageType?: DamageType }
]
```

An array of self-describing entries rather than a keyed map. Nesting the state (§1.3) does
not force nesting the payload; the array avoids string parsing on ingest without asking
the Warden to generate nested JSON, and it makes `reason` and `damageType` read as
properties of a specific pool change.

`DamageType` is `'blunt_force' | 'bleeding' | 'gunshot' | 'fire_explosives' | 'gore_massive'`
(PSG §29.1).

All four land together with their prompt instructions. Splitting them costs a second
re-baseline for no benefit — the batching rationale in
`decisions.md § …roll_dice…measurement infrastructure`.

## 2.2 Validator rules

| Rule | Behaviour |
|---|---|
| Result below `PoolDefinition.min` | **Reject.** Not clamped. The Warden applies the floor |
| `maxDelta` on a pool whose instance `max` is `null` | **Reject.** A ceiling delta on an uncapped pool is meaningless; ignoring it would hide a Warden error |
| `max` would drop below `current` | **Both must be sent**, and `delta` carries the *actual* change, not merely enough to close the gap. Reject when `current + delta > max + maxDelta`. The validator does not clamp |
| `reason` absent | Reject |

The both-must-be-sent rule preserves `sum(deltas) == current − initial` with no state
change occurring outside the delta stream. That property is what makes `reason` useful;
clamping in the validator would break it.

**Worked example, because the obvious phrasing of this rule is wrong.** Death table `00`
(PSG §29.2) is the standard case and it does two things at once: the character takes real
damage *and* Maximum Health drops `1d5`. maxHp 20, current 18, roll of 4 → the ceiling
becomes 16. A rule reading "send enough to reach the new ceiling" would produce
`{ delta: -2, maxDelta: -4 }` and silently discard whatever damage exceeded 2. The two
obligations are independent: apply the actual change, *and* ensure `current` does not end
above the new ceiling. The validator's inequality already permits the larger delta —
only the instruction needed fixing.

## 2.3 Prompt instructions

Six, all new:

1. **Stress floors at the character's Minimum Stress, not at zero.** Read it from state.
2. **Stress caps at 20.** Excess reduces the most relevant Stat or Save — narrate the
   choice and send both deltas.
3. **Every pool delta carries a `reason`** naming the in-fiction cause.
4. **A ceiling change sends `maxDelta`**, and sends `delta` too when the new ceiling would
   fall below the current value. **`delta` is the change that actually occurred, not a
   number chosen to land on the new ceiling.** If the new ceiling would leave `current`
   above it, `delta` must be at least large enough to close that gap — that is a floor on
   the magnitude, not a target. Apply the damage that happened.
5. **Applying a Wound requires `damageType`** — see Part 3.
6. **Do not roll for player actions**, restated in the context of the new fields.

## 2.4 The `reason` field is a fabrication surface

Free text the Warden populates, in a taxonomy that already tracks `FABRICATION`. A
plausible-but-wrong reason is worse than none, because it reads as provenance. Judge-graded
check in Part 6.

# Part 3 — Wounds

The largest gap, and a mechanic rather than a field.

## 3.1 The chain

Replace `HP_DEFINITION`'s `{ value: 0, effect: 'death_save_required' }` — that is the 5e
rule. Mothership (PSG §28.2, §29.1–29.2):

1. Damage reduces `hp.current`.
2. At zero or below: gain a Wound (`wounds.current` +1).
3. Roll `1d10` on the Wounds Table **column selected by `damageType`**.
4. Apply the result — which may include Bleeding +N, a stat reduction, a limb loss, an
   on-fire counter, or a Death Save.
5. Reset `hp.current` to `hp.max` **minus carryover damage**.
6. Only when `wounds.current == wounds.max`: Death Save.

Armor and Damage Reduction resolve before step 1: DR first, then AP. Damage ≥ AP destroys
the armor and the remainder carries through. Anti-Armor ignores and destroys armor but not
DR (PSG §28.3).

## 3.2 The Wounds Table is not in the repo

TKG content. It cannot ship. The Warden retrieves it via `rules_lookup` against the
self-hoster's own ingested PDF, resolved per-turn at the point of application.
**Confirmed 2026-08-14.**

This makes M7.6 the first milestone whose *mechanical correctness* depends on retrieval
returning a specific table row rather than on the Warden reasoning from prose. M7.2 and
M7.5 are complete so the dependency is satisfied, but record it in the milestone note:
a flamethrower Wound returning a Gunshot result is an M7.5 regression surfacing in M7.6's
playtest, and undocumented it will be triaged as a Wounds bug.

## 3.3 Carryover arithmetic

"Reset Health to Maximum minus carryover" is a computed transition, not a table lookup.
Warden-computed, keeping it out of the Phase 3 arithmetic layer — at the cost of a new
failure mode. Structural check in Part 6: inputs and result are both in event and state
structure, so no prose classification is needed.

## 3.4 Wounds outputs

In scope because the Wounds Table writes to them; they cannot lag the mechanic producing
them.

- **Bleeding** — cumulative damage per round, +1 to +7 from the table, ignores armor and DR
  (PSG §32.2).
- **Pending Death Save** — the Lethal Injury row's "Death Save in 1d10 rounds" timer.

# Part 4 — Renders

## 4.1 Character attribute snapshot

Static build data into the snapshot — but **the values are not static**, and the roadmap
bullet's own title says otherwise. Stats and Saves move: Wounds reduce Strength and Body
Save, Level 2 radiation reduces all seven per round, Stress overflow reduces the most
relevant one. **Render current values from pools, never creation rolls from the sheet.**
A render built on the static assumption hands the Warden a stale target number after any
wound, silently, because the number still looks plausible.

## 4.2 `<character_attributes>`

Deferred two milestones past its own stated trigger because no data source existed. Parts
1–3 create it. Three fields:

- **Armor mode** — worn item, current AP, destroyed flag, O2 remaining.
- **Weapon loadout** — readied weapon and shots remaining.
- **Active conditions** — from the conditions map, with parameters.

`formatMothershipCharacterProse` is the widest reader of the sheet and needs rewriting
throughout. Two current defects to fix while there: it renders `INST` for a stat that does
not exist on player characters (Instinct is a Contractor stat, PSG §40.1), and it labels
`maxStress` "Stress Threshold", the only place in the codebase using that name.

# Part 5 — Frontend

## 5.1 Creation

Class Stat/Save adjustments are **not applied anywhere today** — creation is free-entry
with defaults. Implement them (PSG "Step 3"):

| Class | Adjustment |
|---|---|
| Marine | +10 Combat, +10 Body, +20 Fear, +1 Max Wounds |
| Android | +20 Intellect, −10 to one Stat, +60 Fear, +1 Max Wounds |
| Scientist | +10 Intellect, +5 to one Stat, +30 Sanity |
| Teamster | +5 all Stats, +10 all Saves |

The Android's −10 and the Scientist's +5 are player choices at creation, so the form needs
to collect which Stat.

**Capture the raw dice into `creationRolls`** (§1.1) as they are entered or generated —
the pairs, before the `+25` / `+10` and before the class adjustment. If creation offers
manual entry rather than rolling, the field records what the player entered; the point is
a record of the starting position, not proof that dice were used.

## 5.2 Defaults that are wrong on their own terms

| Location | Current | Correct |
|---|---|---|
| `CharacterCreate.svelte:37` | `maxHp = 20` | `1d10+10` → 11–20. A fixed 20 is the maximum possible roll |
| `CharacterCreate.svelte:38`, `CharacterEdit.svelte:44` | `maxStress = 3` | No referent in the book. Minimum Stress starts at 2 |
| `CharacterEdit.svelte:68-80` | `?? 30` on every stat and save | Stats `2d10+25` → 27–45. Saves `2d10+10` → 12–30. The single fallback is below the stat floor and at the save ceiling |

## 5.3 Type divergence

`apps/zoltar-fe/src/lib/types.ts:25-40` is a hand-written `CharacterSheet` with
`Record<string, number>` for stats and saves, `class` as `string`, and `level` absent. It
is not imported from `@uv/game-systems`, so it catches none of this at compile time.
Import the real type.

`CharacterView.svelte` iterates `Object.entries(stats)`, so dropped fields disappear from
the UI automatically and added ones appear with their raw key as a label. Convenient for
the drop, wrong for the add.

`Play.svelte:124-130` passes `fallbackMaxHp` / `fallbackMaxStress` into
`deriveCharacterStatus`, sourced from the sheet. Those sheet fields no longer exist —
source them from pools.

# Part 6 — Eval

## 6.1 Fixtures

**Corrected 2026-08-15: `FIXTURE_SCHEMA_VERSION` does not bump.** That constant means
`capture-fixture` has started recording a field it did not record before
(`eval/fixture.schema.ts:205-211`); re-keying already-captured content is not that. What
bumps is `corpusVersion`, automatically — it is a content hash over fixture bytes — and the
bump is **input-affecting** under `docs/eval-methodology.md:548-562`, subsumed by the
re-baseline §6.3 already schedules.

The corpus is coupled to `MothershipCampaignStateSchema`, not to the sheet — no fixture
carries sheet data — but every pool key changes format and ten pools appear, so
`campaignState` changes for all 15.

Checkers branch on field presence so `eval:rescore` still grades frozen artifacts, per the
`rollType` precedent. The cost is a permanent compatibility branch, not a dead corpus.

## 6.2 Three new measurements

Made necessary by Part 2's decisions, not optional:

- **Rejection counts per pool.** Ten rejecting pools instead of two widens the
  correction-loop surface, and the loop is bounded at one re-prompt — a persistent Warden
  error fails the turn rather than degrading. This converts "the Warden will apply the
  floor" from an assumption into a number. Watch the both-deltas rule (§2.2) hardest: it
  asks for conditional arithmetic, which is a harder ask than the floor case.
- **Judge-graded check on `reason`** (§2.4).
- **Structural check on carryover arithmetic** (§3.3). Event and state structure only — no
  prose classification, per `decisions.md § A structural check may read event and state
  structure; it may not classify prose`.

## 6.3 Re-baseline

One attributable run. Do not combine with the `<entities>` run — four snapshot changes
measured together leave any tag movement unattributable, which is why these bullets were
separated in the first place.

**Expected movement, stated in advance so a surprise is legible:**

- `FABRICATION` may rise — `reason` is a new free-text surface.
- `UNAUDITABLE-MAPPING` should fall — `reason` is what it was missing.
- `MISSING-CANON-CAPTURE` may move in either direction — `<character_attributes>` adds
  material to capture.
- Anything pinned at 1.00 after this run is a harness suspect, not a finding.

## 6.4 M7.8 candidate

Flag while the work is fresh: the Wounds Table is a near-ideal known-answer fixture —
deterministic table, unambiguous correct row per damage type and `1d10` result, and both
the damage type and the applied result live in event structure, so the check is structural
rather than judge-graded.
