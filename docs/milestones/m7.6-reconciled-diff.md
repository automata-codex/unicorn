# M7.6 — Reconciled Diff

PSG target against the schema as it actually stands. This is the direct input to the spec.

**Sources.** Rules side: `m7.6-psg-character-sheet-inventory.md`, citing *Mothership
Player's Survival Guide* v1.2 by section. Code side: `docs/plans/m7.6-code-inventory.md`
at commit `e1cdaac`. Placement: `decisions.md § State placement is decided by the lifetime
of the referent, not the lifetime of the value`.

**Dispositions.** `KEEP` · `DROP` (no referent in the rules) · `RESHAPE` (right concept,
wrong type) · `MOVE` (right value, wrong container within the sheet) · `→STATE` (leaves the
sheet under the placement rule) · `ADD` (rules concept with no representation at all).

**Counts.** 20 leaf fields exist. 5 survive unchanged. 4 are dropped outright. 11 are
reshaped, moved, or relocated. 14 rules concepts have no representation and would need
adding. **The schema is closer to a rewrite than an edit**, which is worth knowing before
the spec is sized.

---

## 0. A defect in the recorded placement rule, found by applying it

`decisions.md` **lines 471–476**, the bullets under "**The rule.**" in
`### State placement is decided by the lifetime of the referent, not the lifetime of the
value` (heading at 461). The rule mixes two axes across three bullets:

> - The referent never changes after creation → character sheet
> - The referent outlives the adventure → campaign state
> - The referent is created and destroyed with the adventure → adventure state

The first bullet says *referent* and means *value*. A character's Strength and a
character's name have the same referent — the character — so the first two bullets both
match every character field and the rule can't discriminate. It reads fine until you try
to apply it field by field. The lead-in at 471 has the same problem: "State lives at the
scope of the thing it is *about*" describes only the second axis.

**Replacement for 471–476:**

> **The rule**, two axes applied in order:
>
> 1. **Does the value change during play?** No → **character sheet**. Name, pronouns, class, the creation rolls as rolled.
> 2. **For values that do change, how long does the thing they describe last?** Outlives the adventure → **campaign state** (anything attached to a character, a recurring NPC, or the party's ship). Created and destroyed with the adventure → **adventure state** (a derelict's reactor integrity, a synthesized threat's HP, a countdown timer, initiative order, scenario flags).

The entry title survives unchanged — referent lifetime is still what the entry is *for*,
it just isn't the only axis. The worked examples and the Mothership and 5e conclusions are
unaffected.

**The consequence is larger than it looked when we recorded it.** Under the corrected
rule, the sheet retains only immutable creation data — 6 fields. Everything numeric leaves.
That is shape (a) from the inventory's Open Question 1, which was marked resolved on the
narrower claim that *newly added* fields land on the campaign side. **Confirmed
2026-08-14** as intended for the existing fields too; see §6, including the
end-of-adventure write-back that was considered and rejected.

## 4. →STATE — leaves the sheet under the placement rule (7 + 2 ceilings)

All seven Stats and Saves mutate in play, so under the corrected rule none of them is
sheet data. Each needs a **current** value in state and a **ceiling** that restore effects
clamp against — and the ceiling is itself mutable, so it can't be recomputed from the
creation roll.

| Value | Moves because | Ceiling needed because |
|---|---|---|
| Strength | Wounds `-1d10` (Fire 04, Gore 04); radiation L2; Stress overflow >20 | Pseudoflesh restores 2d10 |
| Speed | Same | Pseudoflesh restores 2d10 |
| Intellect | Radiation L2; Stress overflow | Psychosurgery restores **to maximum** |
| Combat | Radiation L2; Stress overflow; Military Training `+10` | Slicksim restores 1d10 — **no restore-to-max exists anywhere** |
| Sanity Save | Radiation L2; Stress overflow; Slicksim mishap `-1d5` | Counselor restores 1; Psychosurgery to max; **Shore Leave raises the ceiling** |
| Fear Save | As Sanity | Slicksim restores 1d10; Shore Leave raises the ceiling |
| Body Save | Wounds `-2d10` (Fire 05, Fire 06); radiation L2 | Pseudoflesh restores 2d10 |

| Ceiling | Current field | Change |
|---|---|---|
| Maximum Health | `maxHp` | →STATE. Mutable: Death table `00` takes `1d5` (§29.2). No recovery path exists |
| Maximum Wounds | *(absent — see §7)* | →STATE. Mutable: Panic `19` takes 1 (p. 21). No recovery path exists |

**Container: `resourcePools`. Decided 2026-08-14.** Consistent with
`§ HP and all numeric resources in resourcePools`. Thresholds stay empty for all nine —
none of these values fires a mechanical event on crossing a number, so the threshold
machinery is simply unused rather than worked around.

**The per-instance `max` is already the right home for the mutable ceilings.**
`ResourcePoolSchema` is `{ current, max }` per pool, distinct from `PoolDefinition`'s
system-level `min`/`max`/`thresholds`. So a stat pool is `{ current: 27, max: 42 }`,
Maximum Health is the hp pool's `max`, Maximum Wounds is the wounds pool's `max`. No
separate ceiling pools, and the mutability comes free.

**But nothing can write `max`.** `state_changes.resource_pools` is
`Record<string, { delta: number }>`. Death-table `00` reducing Maximum Health by `1d5`
(§29.2) and Panic `19` reducing Maximum Wounds by 1 (p. 21) have **no write path at all**.

### 4.1 The pool-delta object — three fields, one change, one re-baseline

**Decided 2026-08-14.** All three land together, with matching Warden prompt
instructions, ahead of this milestone's re-baseline. Splitting them would cost a second
re-baseline for no benefit.

```
{ delta: number, maxDelta?: number, reason: string }
```

| Field | Purpose | Rules |
|---|---|---|
| `delta` | Unchanged | Below-`min` result is **rejected**, not clamped (§4) |
| `maxDelta` | Writes the per-instance ceiling, both directions — Death `00` and Panic `19` decrement; Shore Leave increments a Save's ceiling (§39.1) | **Rejected** when the pool's instance `max` is `null`. A ceiling delta on an uncapped pool is meaningless, and silently ignoring it would hide a Warden error |
| `reason` | Makes "how did I lose 15 Strength" answerable by query rather than by reading narration. Closes the PSG inventory's §5.7, and the `UNAUDITABLE-MAPPING` gap for HP and Stress as well as for Stats | — |

**`max` dropping below `current`: the Warden sends both.** maxHp 20, current 18, Death
`00` rolls 4 → the Warden must send `{ delta: -2, maxDelta: -4 }`, not `maxDelta` alone.
The validator does not clamp. This preserves the audit property that
`sum(deltas) == current − initial` with no state changes occurring outside the delta
stream — the property `reason` exists to make useful. The cost is conditional arithmetic
in the Warden's head, which is a harder ask than the floor case and belongs in the
rejection telemetry at §10.7.

**Note on `reason` and fabrication.** It is a free-text field the Warden populates, in a
system whose failure taxonomy already tracks `FABRICATION`. A plausible-but-wrong reason
is worse than none, because it reads as provenance. Worth a judge-graded check at the
re-baseline rather than assuming the field is self-evidently safe.

**Below-`min` deltas stay rejected rather than clamped. Decided 2026-08-14** — the Warden
sets these values and should apply the floor itself. Two places where that is not a
philosophical choice but the only option available, worth recording as such so they don't
read as consistent with the general policy:

- **Stress cannot get its correct floor from the mechanism.** `PoolDefinition.min` is a
  system constant selected by string suffix. Mothership's floor is *Minimum Stress*, which
  is per-character and mutable (§20.2). The definition mechanism cannot express it.
- **Nor its cap.** §20.1 does not reject overflow past 20; it converts the excess into a
  reduction of the most relevant Stat or Save — a cross-pool effect no validator supports.
  `max: null` plus a prompt instruction is the only available shape.

**One empirical caveat.** A rejection triggers the correction loop, bounded at one
re-prompt, so a persistent Warden mistake fails the turn. Going from two rejecting pools to
ten widens that surface. "Should be smart enough" is the same class of assumption as
`SYSTEM-ROLLED-PLAYER-ACTION`, which sat at 0.45 until the prompt was fixed and measured.
Cheap insurance: count rejections per pool in telemetry during the re-baseline, so the
assumption is measured rather than trusted.

**Pool key format: `{entityId}.{pool}`. Decided 2026-08-14.** `lt_alvarez_hp` becomes
`lt_alvarez.hp`. This answers the selector question rather than working around it: key
identity stops being a convention enforced by suffix matching and becomes a structural
parse — split on the dot and entity-vs-pool is exact. Today `lt_alvarez_hp` is unambiguous
only because no entity id ends in `_hp`; with ten pools per character that guarantee
thins, and any future `_max_hp`-shaped key breaks it outright. Same argument as a separate
adventure-state row over tagging (`§ Adventure state gets its own row…`), one level down.

Honest accounting: it does **not** prevent the `alvarez` / `lt_alvarez` class of defect,
which was two entity ids rather than a parse failure. It changes every key in every
fixture's `campaignState` — free now because M7.6 bumps `FIXTURE_SCHEMA_VERSION` anyway,
not free afterwards. And whether dotted keys are more reliable for the Warden to *generate*
is unknown; object-path notation is at least a more familiar shape than underscore
concatenation, and the re-baseline measures it either way.

## 6. Sheet contents after the diff

**Confirmed 2026-08-14.** The near-empty sheet is intended.

| Stays | Leaves |
|---|---|
| `entityId`, `name`, `pronouns`, `class`, `notes`, plus `trinket` and `patch` from §7 | Everything numeric, every mutable list |

Optionally also the **creation rolls as rolled** — an immutable record of what was rolled
at creation, distinct from the current values and from the mutable ceilings. Useful for
audit and character-history display; not read by any mechanic.

**Considered and rejected: writing state back to the sheet at adventure end**, so the next
adventure could start from a fresh state derived from the sheet. Rejected because the
derivation it would avoid does not exist. Campaign state is campaign-scoped and nothing
clears it, so pools already persist across the boundary —
`deriveMothershipCharacterResourcePools` has two call sites, both in `CharacterService`,
and a character at 7/20 HP already begins adventure 2 at 7/20. A write-back would copy
values that are already in the right place, and if the copy ever diverged there would be
two authorities for one number, which is the drift the placement rule exists to prevent.

It would also serve no system on the roadmap. 5e resets at *rests*, Feng Shui 2's Fortune
per *session*, Infinity's Momentum per *scene* — none of these is an adventure boundary.
That is `§ State placement…`'s "reset is a rule, not a lifecycle" one level down. Two
further problems with no obvious answers: adventures terminate as `completed`, `aborted`
*or* `failed`, so a write-back needs a policy per terminal status, and a dead character
has nothing to carry forward.

**A different thing worth having later, under a different name:** an append-only snapshot
of character state at the end of each adventure, for character history and for the "how
did I lose 15 Strength" question in the PSG inventory's §5.7. That adds a row rather than
replacing an authority, and it composes with the `reason` field in §4 rather than
competing with it. Not Phase 1.

**Shape (c) — sheet mirrors current values, state authoritative — was rejected earlier**
by the placement rule's own rationale ("drifted from the authoritative pool values the
moment play began"), and the code inventory shows that drift already happening:
`mergePlayerResourcePools` cannot overwrite, so raising `maxHp` on a sheet today never
reaches the pool.

### 7.1 Wounds — in scope, and it's a mechanic rather than a field

**Decided 2026-08-14: Wounds land in M7.6.** Three costs that aren't visible from the
field list:

**Damage type is a fourth tool-schema field.** The Wounds Table has five columns — Blunt
Force, Bleeding, Gunshot, Fire & Explosives, Gore & Massive (§29.1) — and nothing in
`state_changes` currently carries which one applies. It joins `maxDelta` and `reason` in
§4.1: four fields, one change, one set of prompt instructions, one re-baseline.

**The Wounds Table is TKG content and cannot ship in the repo.** Same constraint as the
rules glossary — Tuesday Knight Games runs an approval-based licensing programme, not an
SRD. The table has to reach the Warden through the self-hoster's own ingested PDF via
`rules_lookup`, or be locally generated under the hash-and-log pattern already used for
oracle tables and Warden prompts. M7.2 and M7.5 being complete means this is available
rather than blocking, but it makes M7.6 the first milestone whose *mechanical correctness*
depends on retrieval returning a specific table row — see §10.2.

**Carryover arithmetic is a computed transition.** "Reset Health to Maximum minus
carryover" (§28.2) is not a delta the Warden can read off a table. Warden-computed keeps
it out of the rules-engine arithmetic layer the roadmap doesn't build until Phase 3, at
the cost of a new failure mode — worth a structural check, since the inputs and result
are all in event and state structure and no prose classification is needed.

Replacing `HP_DEFINITION`'s `{ value: 0, effect: 'death_save_required' }` threshold is
part of this: the correct chain is 0 HP → Wound → Wounds Table roll by damage type →
Health resets to Maximum minus carryover, and the Death Save arrives only at Maximum
Wounds. `HP_DEFINITION.min` also moves off `null`, since HP currently goes negative and
stays there instead of triggering the cycle.

### 7.2 Conditions — campaign state, dedicated map

**Decided 2026-08-14.** Not the sheet, and not `entities[playerEntityId].status`.

**The sheet has no write path for them.** Sheet writes go through the character REST
endpoint; turn state changes go through `submit_gm_response`. No tool lets a turn write
the sheet, so a Panic result granting *Coward* or *Spiraling* would have nowhere to land —
the Warden would narrate a Condition it could not record. It also fails the placement
rule (Conditions mutate in play) and contradicts the near-empty sheet in §6. And
`<character_attributes>`, one of this milestone's own bullets, needs active conditions
from a snapshot that renders campaign state rather than the sheet.

**`entities[].status` is free but lossy.** It exists as `string[]`, but Conditions are
parameterised — *Frightened* stores what frightened you, *Loss of Confidence* stores which
skill loses its bonus. That second one is a link into the Skills list (§5), not a label.
A dedicated map holds the parameters; `status` cannot.

The §5.5 states from the PSG inventory — cryosickness, exhaustion, food and water,
radiation level, temporary roll modifiers — remain out of scope. Bleeding and the pending
Death Save moved *in* because the Wounds Table writes to both, so they cannot lag behind
the mechanic that produces them.

### 10.1 Carried into the re-baseline

Three measurements the decisions above make necessary rather than optional:

- **Rejection counts per pool.** Ten rejecting pools instead of two widens the
  correction-loop surface, and the loop is bounded at one re-prompt — so a persistent
  Warden error fails the turn rather than degrading. Converts "the Warden will apply the
  floor" from an assumption into a number.
- **A judge-graded check on `reason`.** Free text the Warden populates, in a taxonomy that
  already tracks `FABRICATION`. A plausible-but-wrong reason is worse than none, because
  it reads as provenance.
- **A structural check on carryover arithmetic.** Inputs and result are all in event and
  state structure, so no prose classification is needed — this stays on the correct side
  of `§ A structural check may read event and state structure; it may not classify prose`.

### 10.2 Dependency on the retrieval work, satisfied but worth recording

§7.1's Wounds Table is TKG content, cannot ship in the repo, and must reach the Warden via
`rules_lookup` against the self-hoster's own ingested PDF. **M7.2 and M7.5 are complete, so
the dependency is satisfied** — but it should be recorded in the M7.6 section note rather
than dropped, for two reasons.

**Triage.** A Wounds Table lookup is a five-column retrieval keyed on damage type
(§29.1). If a flamethrower Wound comes back with a Gunshot result, that is an M7.5
regression surfacing inside M7.6's playtest, and without the dependency written down it
will be triaged as a Wounds bug. This is the first mechanic in the system whose *correct
operation* depends on retrieval returning a specific table row rather than on the Warden
reasoning from prose.

**M7.8 candidate.** For the same reason it makes a near-ideal known-answer fixture:
deterministic table, unambiguous correct row per damage type and d10 result, and the
failure is structurally checkable — both the damage type and the applied result are in
event structure, so no prose classification is needed. Worth flagging to M7.8 while the
Wounds work is fresh, rather than rediscovering it when known-answer coverage is being
authored.
