# M7.6 — Character Sheet Fidelity: Implementation Plan

Multipart implementation plan for
`../specs/zoltar/016-m7.6-character-sheet-fidelity.md`. Each part is sized for a
manual code review and a single commit. Pause after each part for review before
starting the next.

**Grounding.** Written 2026-08-14 against `main` at `a3fc5e0`. Code claims below
were re-verified in the working tree rather than copied from
`../milestones/m7.6-code-inventory.md` (which was written at `e1cdaac`); where
this plan cites a `path:line` it was read, not inherited.

**Invariant for every part: the repo is green at each commit.** `npm run build`,
`npm test`, and `npm run lint` pass. This is not a formality here — the sheet
schema, the campaign-state schema, and `getMothershipPoolDefinition` all live in
`@uv/game-systems`, and every one of their consumers is in a different workspace
package. A schema change and its consumers therefore land in the same commit;
that constraint, not the spec's section boundaries, is what fixes part sizes
below.

## Ordering

The spec's six Parts are load-bearing and this plan preserves their order. It
splits them into ten commits, and moves two things:

| Spec | Plan | Why moved |
|---|---|---|
| Part 1 (schema + migration) | Parts 1–3 | Three independent shape changes with three different blast radii. Nesting the pools alone touches nine files and every fixture; folding the sheet rewrite into it makes one unreviewable commit |
| Part 4 (`formatMothershipCharacterProse` rewrite) | Part 2 | It reads the *sheet*, and the sheet changes in Part 2. Left in Part 4 it is written twice — once to compile, once to be correct. `<character_attributes>` reads *state* and genuinely belongs in Part 6 |

**The re-baseline is a shipping boundary, not a commit boundary.** The spec's
"instructions must ship with the schema" (§Ordering, item 2) is satisfied as long
as no baseline run happens between Part 4 and Part 5. Splitting them across two
commits costs nothing; running `eval:run` in between costs a run.

Parts 1–3 are shape. Parts 4–5 are the Warden contract, and together they force
exactly one re-baseline. Part 6 is renders, 7–8 frontend, 9–10 eval and closeout.

## Pre-flight: six decisions the spec leaves open

Each of these changes what gets built. Recommendations are given; **all six want
a yes/no before Part 1 starts**, because four of them land in Parts 1–4.

### D1 — What is the owner key of a nested pool?

§1.3 says `resourcePools: { [entityId]: { hp, stress, … } }`. Five of the fifteen
pool keys in every fixture are not entities:
`station_power_reserve`, `station_power_integrity`, `hull_breach_timer`,
`contamination_spread_timer`, `signal_pattern_shift_timer`. Nesting needs a rule
for them.

- **Option A (minimal).** The top-level key is an opaque *owner* string, entity
  or not. `station_power: { reserve, integrity }`, `hull_breach: { timer }`.
  Cheap; keeps an adapted version of the impersonation heuristic; leaves owner
  ids unconstrained, which is the soil the `alvarez` / `lt_alvarez` defect grew
  in.
- **Option B — recommended.** `resourcePools` is **entity-owned only**. A write
  to an owner id outside `playerEntityIds ∪ knownEntityIds` is rejected. Non-
  entity numerics go to `scenarioState`, which already exists for exactly that
  ("Non-entity numeric state: oxygen, reactor power, countdown timers" —
  `campaign-state.schema.ts:26`) and already rejects keys not defined at
  synthesis (`session.validator.ts:311-317`).

Option B deletes `impersonatesPlayerPool` (`session.validator.ts:113-136`) and
`playerPoolSuffixes` (`synthesis.write.ts:70-80`) outright — two suffix-matching
heuristics whose whole job was inferring an owner from a flat string. Nesting
makes the owner explicit, so the inference has no reason to survive. It also
closes the duplicate-pool defect structurally rather than heuristically
(`MEMORY.md § Duplicate player resource pools`). Its cost is that the five
scenario pools move sections in the fixture corpus — a Part 9 edit that is
already rewriting all fifteen `campaignState` blobs anyway.

#### Q2 — `scenarioState` has no producer. D1-B's destination is currently write-only-by-nobody

This is the finding that most affects D1-B.

`submitGmContextSchema.structured` has exactly four members — `entities`,
`flags`, `initialState`, `worldFacts` (`synthesis.schema.ts:33-38`). There is **no
`scenarioState` channel in the synthesis tool schema.** `buildCampaignStateData`
sets `scenarioState: existingScenarioState` (`synthesis.write.ts:193`) — a
carry-forward of a value nothing ever populates. Every `initialState` entry is
routed to `buildResourcePools` (`:176-183`) and becomes a resource pool.

Consistent with that, `scenarioState` is `{}` in all 15 fixtures, in every
`campaign_state` row in all five dumps, and in both
`adventure_synthesis_snapshots.campaign_state_data` rows.

At play time, `applyScenarioState` rejects any key not already present:
"Scenario state key does not exist — these are defined at synthesis time and
cannot be introduced during play" (`session.validator.ts:309-317`). Since
synthesis cannot define one, **no key can ever enter `scenarioState` by any code
path that exists today.**

So D1-B as written would move five (or six) keys into a section that synthesis
cannot seed and play cannot write — permanently frozen at whatever the migration
put there. Making D1-B viable requires first adding a `scenarioState` member to
the synthesis tool schema and its write path, which is itself a tool-schema
change and therefore rides the same re-baseline as Part 4.

#### Q3 — Field-level lossless; semantically not a relocation

`ScenarioStateEntrySchema` is `{ current, max: nullable, note }`
(`shared.ts`), a superset of `ResourcePoolSchema`'s `{ current, max }`. All five
keys carry a non-null `max`, all representable. **No field is dropped.**

Two things that are not fields, and are lost:

1. **The write idiom flips from delta to absolute.**
   `stateChanges.resourcePools` carries `{ delta }` (`session.schema.ts:16`);
   `stateChanges.scenarioState` carries `{ current }` (`session.schema.ts:42`).
   Anything moved leaves the delta stream — so Part 4's `reason` and `maxDelta`,
   the `sum(deltas) == current − initial` audit property, and Part 9's
   per-pool rejection-count measurement do not apply to it. For
   `contamination_spread_timer`, the one key of the five that actually moved
   during play (6/6 → 3/6 over 28 turns), that is a real loss of exactly the
   auditability this milestone is buying.
2. **Definition-based enforcement is lost.** `applyResourcePool` consults
   `PoolDefinition` for `min`, `max`, and thresholds
   (`session.validator.ts:189-229`); `applyScenarioState` consults nothing and
   writes `change.current` verbatim (`:319-323`), so a moved entry can go
   negative or exceed its own `max` with no rejection. All five resolve to
   `DEFAULT_DEFINITION` today (`min: null`, no thresholds), so nothing is lost
   *at present* — but `station_power_integrity` is the one key in the corpus with
   `current < max` at synthesis (6/10), which is the shape a floor or threshold
   would eventually want.

### D2 — How does the class-adjustment choice survive to audit time?

Acceptance says "rolls plus class arithmetic reconcile to each starting ceiling."
Two of the four classes make that arithmetic player-dependent: the Android's
−10 to one Stat and the Scientist's +5 to one Stat (§5.1). Without recording
which Stat, the reconciliation the acceptance criterion asks for cannot be
computed.

**Recommendation:** add `creationChoices: { adjustedStat?: MothershipStatEnum }`
to the sheet. It is immutable creation data by the same argument that admits
`creationRolls`, and it is the missing input to the audit, not a second copy of
a value that lives elsewhere.

### D3 — Where do conditions, bleeding, armor AP, and the pending Death Save get *written*?

§1.3 and §3.4 place them in campaign state. Nothing in the spec gives them a
write path. `submit_gm_response.stateChanges` (`session.schema.ts:13-47`) has
five members — `resourcePools`, `entities`, `flags`, `scenarioState`,
`worldFacts` — and none of them can carry a parameterised condition or an armor
destruction flag.

This is the same argument §7.2 of the reconciled diff used to reject putting
Conditions on the sheet ("the Warden would narrate a Condition it could not
record"), and it applies unchanged to state the tool cannot address.

**Recommendation:** `stateChanges` gains a sixth member, `characterState`, in the
**same commit as the pool-delta object** (Part 4). One tool-schema change, one
prompt revision, one re-baseline — the batching rationale the spec applies to the
four pool fields applies with equal force here. Shape sketched in Part 4.

### D4 — Are multiple deltas against one pool in one turn legal?

They have to be. The wounds chain (§3.1) drives `hp.current` to 0, then resets it
to `hp.max` minus carryover — two changes to one pool in one turn, with different
`reason` values. Today `stateChanges.resourcePools` is a *map*, so one entry per
pool is all that is expressible; §2.1 changes it to an array, which makes two
entries expressible but does not say what the validator does with them.

**Recommendation:** the validator folds array entries **in order against a running
state**, not each independently against `currentData`. This is what preserves
§2.2's `sum(deltas) == current − initial` property, and it is what lets the Part 9
carryover check read the whole transition out of event structure. It is a real
rework of `applyResourcePool` (`session.validator.ts:138-230`), which currently
reads `currentData.resourcePools[poolName]` once per entry.

### D5 — When do the fixtures get re-keyed?

Between Part 1 and Part 9 the corpus is unrunnable if left alone: seeding an
old-shape `campaignState` into a nested-pool world produces a snapshot the
renders cannot build.

**Recommendation:** the mechanical re-key (flat key → nested, plus D1's scenario
moves) lands **in Part 1**, with `FIXTURE_SCHEMA_VERSION` bumped 2 → 3 there.
`eval:rescore` never reads `campaignState` (it re-grades frozen
`warden-output.json` artifacts — `scripts/eval-rescore.core.ts:163`), and the two
checks gated at `>= 2` still pass at 3, so the bump is inert on its own. Part 9
adds the ten-pool content and the checker compatibility branches. One bump, one
re-key, eval runnable throughout.

### D6 — Is the Mothership PDF ingested in dev?

Part 5's acceptance ("Wounds Table reaches the Warden via `rules_lookup`, correct
column per damage type") cannot be verified without a populated `rules_chunk`
table for the Mothership system. **Confirm before Part 5 starts** that local dev
and the enceladus eval host both have the PSG ingested; if not, ingesting it is a
Part 5 prerequisite, not a Part 5 task.

## Part 2 — Sheet reduction, creation rolls, migration, ten-pool derivation

**Schema (`character-sheet.schema.ts`)**

- Remove `level`, `stats`, `saves`, `maxHp`, `maxStress`, `skills`, `equipment`.
- Retain `entityId`, `name`, `pronouns`, `class`, `notes`.
- Add `trinket`, `patch`, `traumaResponse` (stored, not derived — Military
  Training grants the Marine's response to any class, §1.1), `creationRolls`, and
  D2's `creationChoices`.
- `creationRolls` stores **dice as rolled**: `strength: [7, 4]`, not `36`. Keys
  per the §1.1 table — four stats and three saves at `2d10`, `maxHp` at `1d10`,
  `credits` at `2d10`, `trinket` and `patch` at `d100`.
- Comment recording why this is not a second authority (§1.1): a creation roll is
  a different fact from a current value, not a duplicate of one. This is the
  distinction that `maxHp`-on-the-sheet got wrong.

**Derivation (`character-pools.ts`)**

`deriveMothershipCharacterResourcePools` grows from three fields to a real
function: creation rolls + class adjustments → ten pools.

| Pool | Instance `max` | Seeded `current` |
|---|---|---|
| `hp` | `1d10+10` roll | `= max` |
| `wounds` | 2, +1 Marine, +1 Android | `0` |
| `stress` | `null` | **`2`**, not 0 |
| `strength` `speed` `intellect` `combat` | roll + 25 + class adj. | `= max` |
| `sanity` `fear` `body` | roll + 10 + class adj. | `= max` |
| `credits` | `null` | `2d10×10`, or `×100` if forgoing a loadout |

Class adjustments per §5.1, applied here rather than on the frontend: this is the
arithmetic the acceptance criterion wants reconcilable, and it belongs where it
is unit-testable. Tests assert the reconciliation directly — rolls plus class
arithmetic equal each starting ceiling, for all four classes and both choice
cases.

**Migration (`V19__character_sheet_m76_reset.sql`)**

Drop and recreate, per §1.4 — no defensive transform. `DELETE FROM character_sheet;`
and `DELETE FROM campaign_state;`, with a comment recording the 2026-08-14
confirmation (local dev empty, Droplet runs the eval harness only, no fixture
carries sheet data) and a pointer to the pre-`v0.1.0` Flyway consolidation that
makes the file disposable. Preserve the reasoning in `decisions.md` in this
commit, before consolidation discards the file.

**Verify from a wiped volume.** `docker compose down -v` first, then migrate and
seed. A warm volume hides exactly the ordering problems this migration can have.

- `character.service.ts:45`, `:73` — derivation call sites take the new shape.

## Part 3 — Per-entity character state

The remaining §1.3 additions, as shapes and seed values only. No write path yet —
that is Part 4, and separating them keeps the tool-schema commit reviewable as a
contract change rather than a contract change plus six new shapes.

Per entity, in `campaign_state.data`:

- **`conditions`** — a dedicated map keyed by entity id, entries parameterised.
  *Frightened* stores what frightened the character; *Loss of Confidence* stores
  which skill loses its bonus, which is a link into the skills list.
  `entities[].status` cannot serve: it is `string[]` and holds no parameters
  (§1.3).
- **`skills`** — `{ skill, tier }[]` over the fixed prerequisite graph, with
  per-skill suppression (diff §5). Tiers are +10/+15/+20.
- **`equipment`** — stateful items with counts: charges, rounds, doses.
- **`wornArmor`** — `{ item, apBase, apCurrent, destroyed, dr, o2Remaining, features[] }`.
  AP is consumed; damage ≥ AP destroys the armor (PSG §28.3); a patched vaccsuit
  is AP 1. DR applies first and survives both destruction and Anti-Armor (§1.3).
- **`minimumStress`** — per-character, mutable, seeded 2. Not a pool: it is a
  floor, not a resource (§1.2).
- **`bleeding`** — cumulative damage per round, ignores armor and DR (§3.4).
- **`pendingDeathSave`** — the Lethal Injury timer (§3.4).

Seeding for these lands in `CharacterService.create` alongside Part 2's pools;
`delete` clears them with the pools.

**Done when:** shapes parse, seed at creation, clear at delete, and round-trip
through `applyValidatedTurn` untouched (nothing writes them yet, so the assertion
is that nothing *loses* them either).

## Part 4 — Tool schema, validator rules, and the pool prompt instructions

The re-baseline-forcing commit. Everything that changes the Warden's contract
about pools lands here.

**Tool schema (`session.schema.ts:15-17`)**

```
resource_pools: [
  { entityId, pool, delta, maxDelta?, reason, damageType? }
]
```

An array of self-describing entries, not a keyed map (§2.1). `DamageType` is
`'blunt_force' | 'bleeding' | 'gunshot' | 'fire_explosives' | 'gore_massive'`
(PSG §29.1). Nesting the *state* does not force nesting the *payload*.

Plus D3's `characterState` member, carrying condition add/remove with parameters,
armor AP consumption and destruction, bleeding, pending Death Save, minimum
stress, and skill suppression. Same commit — one tool-schema change, one
re-baseline.

**Validator (`session.validator.ts:138-230`)**

Reworked to D4's in-order fold. Rules per §2.2:

| Rule | Behaviour |
|---|---|
| Result below `PoolDefinition.min` | **Reject**, not clamp. The Warden applies the floor |
| `maxDelta` on a pool whose instance `max` is `null` | **Reject** — a ceiling delta on an uncapped pool would hide a Warden error |
| `max` would drop below `current` | Both must be sent; reject when `current + delta > max + maxDelta`. No clamping |
| `reason` absent | Reject |

The worked example in §2.2 is the test case to write first: Death table `00`,
maxHp 20, current 18, `1d5` of 4. `{ delta: -2, maxDelta: -4 }` is the *wrong*
answer — it discards whatever damage exceeded 2. The inequality already permits
the larger delta; the test exists so a later "simplification" does not narrow it.

**Prompt (`wardens/prompts/mothership-m7.txt`)**

The six new instructions from §2.3: stress floors at Minimum Stress read from
state (not zero); stress caps at 20 with overflow reducing the most relevant Stat
or Save as a second delta; every delta carries a `reason`; a ceiling change sends
`maxDelta` and, where the ceiling would fall below the current value, a `delta`
that is *the change that actually occurred* — a floor on magnitude, not a target;
`damageType` is required when applying a Wound (forward reference to Part 5); and
"do not roll for player actions" restated against the new fields.

Editing this file changes its hash (`wardens/prompt-paths.ts`), which is what
makes the baseline stale. That is expected and budgeted — once.

**Done when:** validator unit tests cover all four rules plus the worked example
plus multi-entry folds; correction-loop messages name the pool as
`{owner}.{pool}`; `session.correction.ts` round-trips a rejection.

**Do not run a baseline yet.** Part 5 edits the same prompt.

## Part 5 — Wounds

The largest gap in the spec and a mechanic rather than a field.

**The chain (§3.1)**

1. Damage reduces `hp.current`.
2. At zero or below: `wounds.current` +1.
3. Roll `1d10` on the Wounds Table, **column selected by `damageType`**.
4. Apply the result — Bleeding +N, a stat reduction, a limb loss, an on-fire
   counter, or a Death Save.
5. Reset `hp.current` to `hp.max` **minus carryover damage**.
6. Only at `wounds.current == wounds.max`: Death Save.

Armor resolves before step 1: DR first, then AP. Damage ≥ AP destroys the armor
and the remainder carries through. Anti-Armor ignores and destroys armor but not
DR (PSG §28.3).

**Code.** Remove `HP_DEFINITION`'s `{ value: 0, effect: 'death_save_required' }`
threshold — that is the 5e rule, and it is the confirmed instance of the
D&D-5e-bias hypothesis in the schema. `hp.min` is already `0` from Part 1, which
is what makes step 2 reachable instead of HP sliding negative and staying there.
The transition itself is Warden-driven; **no threshold replaces it**, because
none of the ten pools fires a mechanical event on crossing a number (§1.2).

**The table does not ship.** TKG content. The Warden retrieves it via
`rules_lookup` against the self-hoster's own ingested PDF, resolved per-turn at
the point of application (§3.2). Prompt instructions direct the lookup and name
the column by damage type.

**Record the retrieval dependency in the milestone note.** M7.6 is the first
milestone whose *mechanical correctness* depends on retrieval returning a
specific table row rather than on the Warden reasoning from prose. M7.2 and M7.5
being complete satisfies the dependency, but undocumented, a flamethrower Wound
that returns a Gunshot result will be triaged as a Wounds bug when it is an M7.5
regression (§3.2).

**Carryover is Warden-computed** (§3.3), which keeps it out of the Phase 3
arithmetic layer at the cost of a new failure mode. Part 9 adds the structural
check.

**Prerequisite:** D6 confirmed.

**Done when:** the chain resolves end to end in an integration test through
`submit_gm_response` — damage → wound → table roll with `damageType` → carryover
reset → Death Save at maximum wounds — and bleeding and the pending Death Save
are written by it.

## Part 9 — Eval

**Fixtures.** All 15 `campaignState` blobs carry the ten-pool shape and the Part 3
state blocks. The re-key and the version bump already happened in Part 1 (D5), so
this is content, not format. Checkers branch on **field presence** so
`eval:rescore` still grades frozen artifacts, per the `rollType` precedent — a
permanent compatibility branch, not a dead corpus (§6.1).

**Three new measurements**, made necessary by Part 4's decisions rather than
optional (§6.2):

1. **Rejection counts per pool.** Ten rejecting pools instead of two widens the
   correction-loop surface, and the loop is bounded at one re-prompt
   (`session.service.ts:328` — "single-shot, no inner loop"), so a persistent
   Warden error fails the turn rather than degrading. This converts "the Warden
   will apply the floor" from an assumption into a number. Watch the
   both-deltas rule hardest: it asks for conditional arithmetic, a harder ask
   than the floor case. Rejections are already carried into telemetry
   (`session.telemetry.ts:116`, `:196`), which is the read side to build on.
2. **Judge-graded check on `reason`** (§2.4). Free text the Warden populates, in
   a taxonomy that already tracks `FABRICATION`. A plausible-but-wrong reason is
   worse than none, because it reads as provenance.
3. **Structural check on carryover arithmetic** (§3.3). Event and state structure
   only — no prose classification, per
   `decisions.md § A structural check may read event and state structure; it may
   not classify prose`.

Each new check declares `applicabilitySource` explicitly; the registry hard-errors
at build time on a missing entry (`eval/checks/registry.ts:154-175`), which is the
intended forcing function.

**Done when:** `eval:rescore` grades the existing corpus unchanged; the three
checks are registered and unit-tested against hand-built `TurnExecutionResult`
fixtures.
