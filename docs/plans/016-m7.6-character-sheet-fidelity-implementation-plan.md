# M7.6 — Character Sheet Fidelity: Implementation Plan

Multipart implementation plan for
`../specs/zoltar/016-m7.6-character-sheet-fidelity.md`. Each part is sized for a
manual code review and a single commit. Pause after each part for review before
starting the next.

**Grounding.** Written 2026-08-14 against `main` at `a3fc5e0`. Code claims below
were re-verified in the working tree rather than copied from
`../milestones/m7.6-code-inventory.md` (which was written at `e1cdaac`); where
this plan cites a `path:line` it was read, not inherited.

**Invariant for every part: the repo is green at each commit.** `npm run build`,
`npm test`, and `npm run lint` pass. This is not a formality here — the sheet
schema, the campaign-state schema, and `getMothershipPoolDefinition` all live in
`@uv/game-systems`, and every one of their consumers is in a different workspace
package. A schema change and its consumers therefore land in the same commit;
that constraint, not the spec's section boundaries, is what fixes part sizes
below.

## Ordering

The spec's six Parts are load-bearing and this plan preserves their order. It
splits them into ten commits, and moves two things:

| Spec | Plan | Why moved |
|---|---|---|
| Part 1 (schema + migration) | Parts 1–3 | Three independent shape changes with three different blast radii. Nesting the pools alone touches nine files and every fixture; folding the sheet rewrite into it makes one unreviewable commit |
| Part 4 (`formatMothershipCharacterProse` rewrite) | Part 2 | It reads the *sheet*, and the sheet changes in Part 2. Left in Part 4 it is written twice — once to compile, once to be correct. `<character_attributes>` reads *state* and genuinely belongs in Part 6 |

**The re-baseline is a shipping boundary, not a commit boundary.** The spec's
"instructions must ship with the schema" (§Ordering, item 2) is satisfied as long
as no baseline run happens between Part 4 and Part 5. Splitting them across two
commits costs nothing; running `eval:run` in between costs a run.

Parts 1–3 are shape. Parts 4–5 are the Warden contract, and together they force
exactly one re-baseline. Part 6 is renders, 7–8 frontend, 9–10 eval and closeout.

## Pre-flight: six decisions the spec leaves open

Each of these changes what gets built. Recommendations are given; **all six want
a yes/no before Part 1 starts**, because four of them land in Parts 1–4.

### D1 — What is the owner key of a nested pool?

§1.3 says `resourcePools: { [entityId]: { hp, stress, … } }`. Five of the fifteen
pool keys in every fixture are not entities:
`station_power_reserve`, `station_power_integrity`, `hull_breach_timer`,
`contamination_spread_timer`, `signal_pattern_shift_timer`. Nesting needs a rule
for them.

- **Option A.** The top-level key is an opaque *owner* string, entity or not.
  Cheap; keeps an adapted version of the impersonation heuristic; leaves owner
  ids unconstrained.
- **Option B.** `resourcePools` is **entity-owned only**. A write to an owner id
  outside `playerEntityIds ∪ knownEntityIds` is rejected. Non-entity numerics go
  to `scenarioState`, which reads as existing for exactly that ("Non-entity
  numeric state: oxygen, reactor power, countdown timers" —
  `campaign-state.schema.ts:26`).

**Decided: Option A. `resourcePools` nests by owner; ownership is not
constrained.** Unowned pools take the reserved owner `_scenario`. No pools move
to `scenarioState`, and no rejection rule is added.

Four reasons, in descending weight:

1. **The destination does not exist.** `scenarioState` has no producer:
   `submitGmContextSchema.structured` has four members and none is
   `scenarioState` (`synthesis.schema.ts:33-38`), and play-time writes to
   undeclared keys are rejected (`session.validator.ts:309-317`). B moves five
   keys into a bucket nothing can write. Making it viable requires a synthesis
   tool-schema change — a third schema addition on the same re-baseline as the
   four pool-delta fields and D3's `characterState`.
2. **B would move actively-changing state out of the audit mechanism this
   milestone exists to build.** `resourcePools` records *changes*: a delta, a
   reason, an in-order fold, a rejection count. `scenarioState` records
   *values* — a replacement with no history. Field-level the move is lossless,
   but the write idiom flips from `{delta}` to `{current}`, so anything
   relocated leaves the delta stream: no `reason`, no `maxDelta`, no
   `sum(deltas)` audit property, no per-pool rejection telemetry.
   `contamination_spread_timer` is the one of the five that actually moved
   during play, which makes the loss real rather than theoretical.
3. **B reverses a recorded decision by name.** `decisions.md:830` already
   considered "every pool prefix must name a declared entity" and rejected it,
   on the grounds that it would reject `station_power_reserve` and
   `contamination_spread_timer`. Note the asymmetry: that entry supports B's
   factual premise for the two `station_power_*` keys while rejecting B's rule.
4. **The key inventory proved unreliable, and B builds a runtime rejection on
   top of it.** The verification found `android_memory_integrity` fails the same
   mechanical test the five were selected by, and has a confirmed entity
   referent — the non-resolving set is six, not five. A second adventure adds
   `flashlight_battery`, `maren_cooperation`, and `outrider_extraction_timer`.
   Under B each would fail at runtime rather than at authoring time.

**What A gives up, and what it keeps.** B's remaining benefit was surfacing
`hull_breach` vs `hull_breach_cascade` by rejection — worth having, but it
belongs in a milestone with its own attributable run, once `scenarioState` has a
producer or is retired. A still deletes the *reason* the suffix heuristics
exist: with the owner as an explicit key, `impersonatesPlayerPool` and
`playerPoolSuffixes` become set membership rather than string matching. They are
simplified, not deleted.

#### D1-A.1 — Addressing unowned pools

**Reserved owner key `_scenario`.** `hull_breach_timer` becomes
`resourcePools._scenario.hull_breach_timer`.

Rejected alternative: splitting the key at a plausible boundary
(`resourcePools.station.power_reserve`). That requires a human judgement per key
at re-key time, and `hull_breach_timer` is precisely where the judgement is
unsafe, given `hull_breach_cascade` exists as a declared entity. A reserved owner
needs no split and states honestly that these pools have no entity owner.

**Enforcement:** entity ids may not begin with `_`; reserved owner keys must, so
the namespace cannot collide.

**General identifier validation is out of scope.**
`decisions.md § Entity and resource pool identifiers use underscores only` is
stated and never enforced anywhere — grep finds only comments citing it
(`session.service.ts:962`, `session.schema.ts:152-154`), no regex, no schema
refinement, no check on any write path. Enforcing identifier format across entity
creation, synthesis, and the tool boundary is its own change with its own failure
modes, and nothing here depends on it: `_scenario` works as a convention whether
or not collisions are prevented. Recorded on the roadmap, not built here.

**One narrow assertion does land, in Part 1:** reject an owner key beginning with
`_` that is not a known reserved owner. One line, and it closes the specific hole
`_scenario` opens without taking on the general problem.

This also gives Phase 2 a clean handle — see
`decisions.md § Adventure state gets its own row…`, addendum: `_scenario` and
every synthesis-created owner relocate to the adventure row; player owners stay.

#### Q2 — `scenarioState` has no producer. D1-B's destination is currently write-only-by-nobody

This is the finding that most affects D1-B.

`submitGmContextSchema.structured` has exactly four members — `entities`,
`flags`, `initialState`, `worldFacts` (`synthesis.schema.ts:33-38`). There is **no
`scenarioState` channel in the synthesis tool schema.** `buildCampaignStateData`
sets `scenarioState: existingScenarioState` (`synthesis.write.ts:193`) — a
carry-forward of a value nothing ever populates. Every `initialState` entry is
routed to `buildResourcePools` (`:176-183`) and becomes a resource pool.

Consistent with that, `scenarioState` is `{}` in all 15 fixtures, in every
`campaign_state` row in all five dumps, and in both
`adventure_synthesis_snapshots.campaign_state_data` rows.

At play time, `applyScenarioState` rejects any key not already present:
"Scenario state key does not exist — these are defined at synthesis time and
cannot be introduced during play" (`session.validator.ts:309-317`). Since
synthesis cannot define one, **no key can ever enter `scenarioState` by any code
path that exists today.**

So D1-B as written would move five (or six) keys into a section that synthesis
cannot seed and play cannot write — permanently frozen at whatever the migration
put there. Making D1-B viable requires first adding a `scenarioState` member to
the synthesis tool schema and its write path, which is itself a tool-schema
change and therefore rides the same re-baseline as Part 4.

#### Q3 — Field-level lossless; semantically not a relocation

`ScenarioStateEntrySchema` is `{ current, max: nullable, note }`
(`shared.ts`), a superset of `ResourcePoolSchema`'s `{ current, max }`. All five
keys carry a non-null `max`, all representable. **No field is dropped.**

Two things that are not fields, and are lost:

1. **The write idiom flips from delta to absolute.**
   `stateChanges.resourcePools` carries `{ delta }` (`session.schema.ts:16`);
   `stateChanges.scenarioState` carries `{ current }` (`session.schema.ts:42`).
   Anything moved leaves the delta stream — so Part 4's `reason` and `maxDelta`,
   the `sum(deltas) == current − initial` audit property, and Part 9's
   per-pool rejection-count measurement do not apply to it. For
   `contamination_spread_timer`, the one key of the five that actually moved
   during play (6/6 → 3/6 over 28 turns), that is a real loss of exactly the
   auditability this milestone is buying.
2. **Definition-based enforcement is lost.** `applyResourcePool` consults
   `PoolDefinition` for `min`, `max`, and thresholds
   (`session.validator.ts:189-229`); `applyScenarioState` consults nothing and
   writes `change.current` verbatim (`:319-323`), so a moved entry can go
   negative or exceed its own `max` with no rejection. All five resolve to
   `DEFAULT_DEFINITION` today (`min: null`, no thresholds), so nothing is lost
   *at present* — but `station_power_integrity` is the one key in the corpus with
   `current < max` at synthesis (6/10), which is the shape a floor or threshold
   would eventually want.

### D2 — How does the class-adjustment choice survive to audit time?

Acceptance says "rolls plus class arithmetic reconcile to each starting ceiling."
Two of the four classes make that arithmetic player-dependent: the Android's
−10 to one Stat and the Scientist's +5 to one Stat (§5.1). Without recording
which Stat, the reconciliation the acceptance criterion asks for cannot be
computed.

**Recommendation:** add `creationChoices: { adjustedStat?: MothershipStatEnum }`
to the sheet. It is immutable creation data by the same argument that admits
`creationRolls`, and it is the missing input to the audit, not a second copy of
a value that lives elsewhere.

### D3 — Where do conditions, bleeding, armor AP, and the pending Death Save get *written*?

§1.3 and §3.4 place them in campaign state. Nothing in the spec gives them a
write path. `submit_gm_response.stateChanges` (`session.schema.ts:13-47`) has
five members — `resourcePools`, `entities`, `flags`, `scenarioState`,
`worldFacts` — and none of them can carry a parameterised condition or an armor
destruction flag.

This is the same argument §7.2 of the reconciled diff used to reject putting
Conditions on the sheet ("the Warden would narrate a Condition it could not
record"), and it applies unchanged to state the tool cannot address.

**Decided: `stateChanges` gains a sixth member, `characterState`, landing in the
same commit as the pool-delta object (Part 4).** One tool-schema change, one
prompt revision, one re-baseline. Full contract in Part 4.

**Decided also: these stay outside the delta stream.** Bleeding, minimum stress,
and the pending Death Save are numeric counters that change during play, so each
would fit the pool mechanism and would inherit `reason`, in-order folding, and
rejection telemetry for free. They are deliberately not pools. Nobody has asked
to audit a bleeding counter, and building an audit path for a hypothesis is the
thing this project does not do. **They were identified as candidates and left
out, not overlooked** — recorded so that whoever hits an explanation gap later
finds a decision rather than an oversight.

Two consequences of that, which are the price of the deferral:

- **The M7.6 re-baseline measures nothing about `characterState`.** §6.2's
  rejection telemetry is per-pool. The milestone establishes a floor for
  pool-delta behaviour and no floor at all for these five families — including
  whether the Warden writes bleeding reliably. Part 9 must say so, or a clean run
  reads as broader coverage than it is. No signal is easy to mistake for good
  signal.
- **Reversal trigger, stated because "if interest is expressed" never fires:** *a
  playtest produces a bleeding, minimum-stress, or armor value nobody can
  explain.* That is the same shape as the Strength question that motivated
  `reason`, and it will arrive in a playtest report rather than as a feature
  request.

### D4 — Are multiple deltas against one pool in one turn legal?

They have to be. The wounds chain (§3.1) drives `hp.current` to 0, then resets it
to `hp.max` minus carryover — two changes to one pool in one turn, with different
`reason` values. Today `stateChanges.resourcePools` is a *map*, so one entry per
pool is all that is expressible; §2.1 changes it to an array, which makes two
entries expressible but does not say what the validator does with them.

**Recommendation:** the validator folds array entries **in order against a running
state**, not each independently against `currentData`. This is what preserves
§2.2's `sum(deltas) == current − initial` property, and it is what lets the Part 9
carryover check read the whole transition out of event structure. It is a real
rework of `applyResourcePool` (`session.validator.ts:138-230`), which currently
reads `currentData.resourcePools[poolName]` once per entry.

**Rejection is all-or-nothing per turn. Decided 2026-08-14.**

The in-order fold raises a question neither the spec nor the recommendation
answers: if entry three of five is rejected, are entries one and two applied?

**No. A rejected entry aborts the whole `resourcePools` array; no entry in that
`submit_gm_response` is applied, and the correction loop re-prompts against
unchanged state.**

Three reasons:

1. **Partial application breaks the property the fold exists to preserve.**
   §2.2's `sum(deltas) == current − initial` holds only if the recorded deltas
   and the applied deltas are the same set. Applying one and two while rejecting
   three leaves state that no complete delta stream explains, which is the audit
   gap `reason` was added to close.
2. **The correction re-prompt would otherwise fire against state the Warden has
   not seen.** The loop is bounded at one re-prompt
   (`decisions.md § Correction loop bounded at one re-prompt`). If entries one
   and two have already landed, the Warden is asked to fix entry three against a
   world that moved underneath it — and it has no way to know that, because the
   snapshot it reasoned from is stale. That is a fabrication surface, not just an
   inconvenience.
3. **The wounds chain is the motivating case and it is not decomposable.** Drive
   `hp` to zero, roll the Wounds Table, reset to `max` minus carryover — a
   half-applied chain leaves a character at 0 HP with no Wound recorded, which is
   a state Mothership has no rule for. Whether it is recoverable by re-prompt is
   exactly the kind of thing that should not depend on which entry failed.

**Scope of the abort:** the whole `resourcePools` array. Whether a rejection
there should also abort `entities`, `flags`, and the other `stateChanges` members
is a wider question about turn atomicity that this decision does not settle — but
note that `applyTurnAtomic` already applies the turn as one transaction, so the
machinery for it exists. **Narrowed since:** Part 4 settles one pair of that
wider question — `characterState` ↔ `resourcePools` must abort together. It does
not settle `entities`, `flags`, `scenarioState`, or `worldFacts`, which remain
open here.

**Test to write first:** a three-entry array whose second entry violates the
`min` rule. Assert that the first entry's pool is unchanged after the rejection,
and that the correction message names the failing entry rather than the whole
array.

### D5 — When do the fixtures get re-keyed?

Between Part 1 and Part 9 the corpus is unrunnable if left alone: seeding an
old-shape `campaignState` into a nested-pool world produces a snapshot the
renders cannot build.

**Recommendation:** the mechanical re-key (flat key → nested, unowned pools under
`_scenario`) lands **in Part 1**. Part 9 adds the ten-pool content and the checker
compatibility branches.

**`FIXTURE_SCHEMA_VERSION` does not move.** It means *`capture-fixture` has
started recording a field it did not record before*
(`eval/fixture.schema.ts:205-211`), and re-keying already-captured content is not
that. Spec §6.1 asks for the bump and spec §6.1 is wrong; the code's doc comment
is the authority. Correction noted in Part 10's closeout so the spec is amended
rather than silently diverged from.

**What does move is `corpusVersion`**, automatically — it is a content hash over
fixture bytes (`eval/corpus-version.ts:11-33`), so any edit changes it with no
manual step. That is an **input-affecting** bump under
`eval-methodology.md:548-562`: `seededState.campaignState` is what the turn
executes against, so every `warden-output.json` on disk was produced under
different conditions. **The plan's action is unchanged and correct; the reasoning
was wrong.** "The only valid response is a fresh run" is already what Part 10
does, so the input-affecting bump is *subsumed by a re-baseline that was
scheduled anyway* — not inert, and not an extra cost. Per `:569-570`, name the
kind in the bump note: **input-affecting**.

**Between Part 1 and Part 10 there is no valid baseline.** Operationally fine —
nothing compares during implementation — but it has one consequence worth

## Part 3 — Per-entity character state

The remaining §1.3 additions, as shapes and seed values only. No write path yet —
that is Part 4, and separating them keeps the tool-schema commit reviewable as a
contract change rather than a contract change plus six new shapes.

Per entity, in `campaign_state.data`:

- **`conditions`** — a dedicated map keyed by entity id, entries parameterised.
  *Frightened* stores what frightened the character; *Loss of Confidence* stores
  which skill loses its bonus, which is a link into the skills list.
  `entities[].status` cannot serve: it is `string[]` and holds no parameters
  (§1.3).
- **`skills`** — `{ skill, tier }[]` over the fixed prerequisite graph (diff §5).
  Tiers are +10/+15/+20. Suppression is **not** stored here.
  `loss_of_confidence` records which skill in its condition parameter, and the
  suppressed set is derived from the conditions list at read time. Storing it too
  would be a second representation of one fact, free to disagree with the first —
  see Part 4, where `skill_suppress` is excluded for the same reason.
- **`equipment`** — stateful items with counts: charges, rounds, doses.
- **`wornArmor`** — `{ item, apBase, apCurrent, destroyed, dr, o2Remaining, features[] }`.
  AP is consumed; damage ≥ AP destroys the armor (PSG §28.3); a patched vaccsuit
  is AP 1. DR applies first and survives both destruction and Anti-Armor (§1.3).
- **`minimumStress`** — per-character, mutable, seeded 2. Not a pool: it is a
  floor, not a resource (§1.2).
- **`bleeding`** — cumulative damage per round, ignores armor and DR (§3.4).
- **`pendingDeathSave`** — the Lethal Injury timer (§3.4).

Seeding for these lands in `CharacterService.create` alongside Part 2's pools;
`delete` clears them with the pools.

**Done when:** shapes parse, seed at creation, clear at delete, and round-trip
through `applyValidatedTurn` untouched (nothing writes them yet, so the assertion
is that nothing *loses* them either).

## Part 4 — Tool schema, validator rules, and the pool prompt instructions

The re-baseline-forcing commit. Everything that changes the Warden's contract
about pools lands here.

**Tool schema (`session.schema.ts:15-17`)**

```
resourcePools: [
  { entityId, pool, delta, maxDelta?, reason, damageType? }
]
```

An array of self-describing entries, not a keyed map (§2.1). `DamageType` is
`'blunt_force' | 'bleeding' | 'gunshot' | 'fire_explosives' | 'gore_massive'`
(PSG §29.1). Nesting the *state* does not force nesting the *payload*.

**`characterState`**

An array of self-describing entries, matching `resourcePools`' shape (§2.1)
rather than a keyed map. Six operation types, discriminated on `op`.

```
characterState: [
  { entityId: string, op: <one of the six below>, ... }
]
```

Every entry carries `entityId`. **No `reason` field** — see D3's deferral; adding
one here would be half of an audit mechanism, which is worse than none.

*`condition_add` / `condition_remove`*

```
{ op: 'condition_add', entityId, condition: MothershipConditionEnum, parameter?: string }
{ op: 'condition_remove', entityId, condition: MothershipConditionEnum }
```

`MothershipConditionEnum` is closed, from the Panic table (PSG p. 21): `coward`,
`frightened`, `nightmares`, `loss_of_confidence`, `deflated`, `doomed`,
`haunted`, `spiraling`. A closed enum rather than free text — the set is fixed by
the rules, and an open string is a fabrication surface.

`parameter` is required for exactly two: *Frightened* stores what frightened the
character (free text, narrative), *Loss of Confidence* stores which skill loses
its bonus (**must match a skill the character holds**). Validate both: reject
`parameter` on the other six, reject a `loss_of_confidence` parameter that names
a skill the character does not have.

`condition_remove` is the treatment path (Cognitive Defragmentation, p. 35).
Removing `loss_of_confidence` removes the suppression, because the suppression
was never stored separately — the condition entry is the derivation's only input.

*`armor_damage`*

```
{ op: 'armor_damage', entityId, apDelta: number, destroyed?: boolean }
```

Not a generic setter. AP is consumed and only ever decreases outside of repair,
so `apDelta` must be negative; reject a positive value. `destroyed: true` when
the hit met or exceeded AP (PSG §28.3) — the Warden asserts it, the validator
checks consistency against `apCurrent + apDelta <= 0`, and rejects a mismatch.
Rejecting rather than deriving keeps the Warden's understanding and the recorded
state in agreement, and surfaces the case where it has misread the rule.

`armor_repair` is deliberately absent. A Patch Kit sets a vaccsuit to AP 1 and
replacement swaps the item — both are equipment operations, and equipment has no
write path in M7.6. Out of scope; noted in Part 10's closeout.

*`bleeding_set`*

```
{ op: 'bleeding_set', entityId, value: number }
```

Absolute, not a delta — deliberately, since these are outside the delta stream
and a delta field would imply an audit trail that does not exist. `value >= 0`;
`0` clears it. The Wounds Table grants +1 through +7 (PSG §29.1) and the Warden
computes the sum, consistent with every other Warden-side computation in this
milestone.

*`death_save_pending`*

```
{ op: 'death_save_pending', entityId, roundsRemaining: number | null }
```

`null` clears. Set from the Lethal Injury row's "Death Save in 1d10 rounds". The
countdown is Warden-driven per round — nothing decrements it automatically,
because nothing in the system knows a round elapsed.

*`minimum_stress_set`*

```
{ op: 'minimum_stress_set', entityId, value: number }
```

Absolute, `value >= 2`. **This is a scope bound, not a rules invariant.** Nothing
in M7.6's scope lowers Minimum Stress below 2: creation seeds it at 2 (PSG
§20.1), Panic results raise it, and Psychosurgery resets it *to* 2 (p. 35). Deep
Tissue Nanogel Massage lowers it by 1 and is the one effect that could go below —
but no medical treatment has a write path in this milestone.

**Revisit when medical treatments land.** The RAW is genuinely ambiguous:
Psychosurgery's "reduces Minimum Stress *to* 2" implies 2 is the baseline, which
would make Nanogel at minimum-2 a no-op rather than a reduction to 1 — but the
book does not say. Resolving it means a house rule under the hash-and-log
pattern, not a reading.

**Interaction the prompt must state:** raising minimum stress does not by itself
raise current stress. If current is below the new minimum, the Warden sends a
`resourcePools` delta too. Same shape as the `maxDelta` both-must-be-sent rule
(§2.2), and the same failure mode if omitted — state that no rule explains.

*`skill_suppress` / `skill_restore`*

**Not included as operations.** Suppression is a consequence of
`loss_of_confidence`, and the condition already records which skill. A separate
operation would be a second way to express one fact, free to disagree with the
first. The validator derives the suppressed set from the conditions list.

**Validator (`session.validator.ts:138-230`)**

Reworked to D4's in-order fold. Rules per §2.2:

| Rule | Behaviour |
|---|---|
| Result below `PoolDefinition.min` | **Reject**, not clamp. The Warden applies the floor |
| `maxDelta` on a pool whose instance `max` is `null` | **Reject** — a ceiling delta on an uncapped pool would hide a Warden error |
| `max` would drop below `current` | Both must be sent; reject when `current + delta > max + maxDelta`. No clamping |
| `reason` absent | Reject |

The worked example in §2.2 is the test case to write first: Death table `00`,
maxHp 20, current 18, `1d5` of 4. `{ delta: -2, maxDelta: -4 }` is the *wrong*
answer — it discards whatever damage exceeded 2. The inequality already permits
the larger delta; the test exists so a later "simplification" does not narrow it.

`characterState` gets the same all-or-nothing rejection as `resourcePools` (D4):
a rejected entry aborts the `characterState` array and the correction loop
re-prompts against unchanged state.

**Cross-member atomicity: a `characterState` rejection must abort
`resourcePools` in the same turn**, and vice versa. The wounds chain writes both
— HP to zero, Wound recorded, bleeding set from the table, HP reset — and half of
that is a state Mothership has no rule for. The three arguments in D4 apply
unchanged at the array level.

**The likely finding is that this already holds, and the frame is wrong.**
Rejection happens in the validator, *before* `applyTurnAtomic` runs. If the
validator accumulates across all `stateChanges` members and returns a single
pass/fail, then nothing reaches the applier on rejection and transaction
atomicity never comes into it. The guarantee would be
**validate-all-then-apply**, which is stronger than the transactional property
and needs no code change.

Three questions to establish which it is. Answer them while
`session.validator.ts` and `session.applier.ts` are already open for the fold
rework — this is a verification item, not a separate pass.

1. Does the validator accumulate rejections across *all* `stateChanges` members
   and return one pass/fail, or does it validate and apply member by member?
2. On rejection, does `applyValidatedTurn` run at all?
3. **Does the in-order fold (D4) operate on a working copy, or does it mutate
   `currentData` as it goes?** This is the one to check hardest. The fold is new
   work in this commit, and "fold in order against a running state" is easy to
   implement by mutating the state being read. If it mutates, a rejection at
   entry three has already changed the object entries one and two were validated
   against — partial application becomes possible despite a clean abort, and D4's
   guarantee is void.

**Record the answer either way**, per `roadmap.md:333
§ Prerequisite — turn-path lock audit` ("`applyTurnAtomic` serializes concurrent
turns incidentally rather than deliberately"): a guarantee that holds by accident
is one refactor away from not holding, and that item exists because exactly this
went unrecorded once already.

If the property turns out to be emergent, make it explicit; if it is already
deliberate, cite the line.

**Prompt (`wardens/prompts/mothership-m7.txt`)**

The six new instructions from §2.3: stress floors at Minimum Stress read from
state (not zero); stress caps at 20 with overflow reducing the most relevant Stat
or Save as a second delta; every delta carries a `reason`; a ceiling change sends
`maxDelta` and, where the ceiling would fall below the current value, a `delta`
that is *the change that actually occurred* — a floor on magnitude, not a target;
`damageType` is required when applying a Wound (forward reference to Part 5); and
"do not roll for player actions" restated against the new fields.

Four instructions beyond §2.3's six, for `characterState`:

1. Conditions come from the closed list; `frightened` and `loss_of_confidence`
   require a parameter and the others must not carry one.
2. `armor_damage` carries a negative `apDelta`, and `destroyed: true` when the
   hit met or exceeded remaining AP.
3. Bleeding and minimum stress are sent as **absolute values**, not deltas —
   unlike pools.
4. Raising minimum stress above current stress requires a `resourcePools` delta
   in the same turn.

Instruction 3 is the one to watch. Every other numeric write in this milestone is
a delta, and two of these are not; that inconsistency is a consequence of D3's
audit deferral, and it is a plausible source of Warden error. Worth a rejection
count even though the general `characterState` telemetry is out of scope — one
number, and it tests the one place the contract is inconsistent with itself.

Editing this file changes its hash (`wardens/prompt-paths.ts`), which is what
makes the baseline stale. That is expected and budgeted — once.

**Done when:** validator unit tests cover all four pool rules plus the worked
example plus multi-entry folds; correction-loop messages name the pool as
`{owner}.{pool}`; `session.correction.ts` round-trips a rejection.

Plus, for `characterState`: parameter required/forbidden per condition; a
`loss_of_confidence` parameter naming a skill the character lacks; positive
`apDelta`; `destroyed` inconsistent with `apCurrent`; `minimum_stress_set` below
2; a `characterState` rejection leaving `resourcePools` unapplied in the same
turn.

Plus one test for the fold's isolation, which the others will not catch: a
`resourcePools` array whose third entry is rejected, asserting that the pool the
*first* entry targeted is byte-identical to its pre-turn value. This fails if the
fold mutates `currentData` rather than a working copy, and it is the only test in
the set that distinguishes a clean abort from an abort over already-modified
state.

And the three atomicity questions above answered in the commit message or the
plan, whichever survives — not left as an assumption that the transaction covers
it.

## Part 5 — Wounds

The largest gap in the spec and a mechanic rather than a field.

**The chain (§3.1)**

1. Damage reduces `hp.current`.
2. At zero or below: `wounds.current` +1.
3. Roll `1d10` on the Wounds Table, **column selected by `damageType`**.
4. Apply the result — Bleeding +N, a stat reduction, a limb loss, an on-fire
   counter, or a Death Save.
5. Reset `hp.current` to `hp.max` **minus carryover damage**.
6. Only at `wounds.current == wounds.max`: Death Save.

Armor resolves before step 1: DR first, then AP. Damage ≥ AP destroys the armor
and the remainder carries through. Anti-Armor ignores and destroys armor but not
DR (PSG §28.3).

**Code.** Remove `HP_DEFINITION`'s `{ value: 0, effect: 'death_save_required' }`
threshold — that is the 5e rule, and it is the confirmed instance of the
D&D-5e-bias hypothesis in the schema. `hp.min` is already `0` from Part 1, which
is what makes step 2 reachable instead of HP sliding negative and staying there.
The transition itself is Warden-driven; **no threshold replaces it**, because
none of the ten pools fires a mechanical event on crossing a number (§1.2).

**The table does not ship.** TKG content. The Warden retrieves it via
`rules_lookup` against the self-hoster's own ingested PDF, resolved per-turn at
the point of application (§3.2). Prompt instructions direct the lookup and name
the column by damage type.

**Record the retrieval dependency in the milestone note.** M7.6 is the first
milestone whose *mechanical correctness* depends on retrieval returning a
specific table row rather than on the Warden reasoning from prose. M7.2 and M7.5
being complete satisfies the dependency, but undocumented, a flamethrower Wound
that returns a Gunshot result will be triaged as a Wounds bug when it is an M7.5
regression (§3.2).

## Part 9 — Eval

**Fixtures.** All 15 `campaignState` blobs carry the ten-pool shape and the Part 3
state blocks. The re-key and the version bump already happened in Part 1 (D5), so
this is content, not format. Checkers branch on **field presence** so
`eval:rescore` still grades frozen artifacts, per the `rollType` precedent — a
permanent compatibility branch, not a dead corpus (§6.1).

**Three new measurements**, made necessary by Part 4's decisions rather than
optional (§6.2):

1. **Rejection counts per pool.** Ten rejecting pools instead of two widens the
   correction-loop surface, and the loop is bounded at one re-prompt
   (`session.service.ts:328` — "single-shot, no inner loop"), so a persistent
   Warden error fails the turn rather than degrading. This converts "the Warden
   will apply the floor" from an assumption into a number. Watch the
   both-deltas rule hardest: it asks for conditional arithmetic, a harder ask
   than the floor case. Rejections are already carried into telemetry
   (`session.telemetry.ts:116`, `:196`), which is the read side to build on.
2. **Judge-graded check on `reason`** (§2.4). Free text the Warden populates, in
   a taxonomy that already tracks `FABRICATION`. A plausible-but-wrong reason is
   worse than none, because it reads as provenance.
3. **Structural check on carryover arithmetic** (§3.3). Event and state structure
   only — no prose classification, per
   `decisions.md § A structural check may read event and state structure; it may
   not classify prose`.

Each new check declares `applicabilitySource` explicitly; the registry hard-errors
at build time on a missing entry (`eval/checks/registry.ts:154-175`), which is the
intended forcing function.

**What this run does not measure, stated in the report (per D3).** The rejection
telemetry is per-pool. `characterState`'s five families — conditions, armor AP,
bleeding, pending Death Save, minimum stress — get no floor at
all from this milestone, including whether the Warden writes bleeding reliably. A
clean run must not read as broader coverage than it is; no signal is easy to
mistake for good signal. The one exception is the absolute-vs-delta rejection
count from Part 4's prompt instruction 3, which is in scope precisely because it
tests where the contract is inconsistent with itself.

**Retrieval prerequisite (per D6).** The PSG is ingested in local dev and **not**
on enceladus, which is where the harness runs. Ingest it there before any run
that exercises Wounds — otherwise `rules_lookup` returns nothing, the Warden
cannot read the Wounds Table, and the fixtures fail for infrastructure reasons
indistinguishable from Warden failures in the scores.

**Harness preflight assertion.** Before a run starts, assert `rules_chunk` is
non-empty for the campaign's system and abort with a named error if it is not.
Nothing checks this today, and the failure mode is a full run of quietly wrong
scores — the failure mode `eval-methodology.md § Two kinds of corpus bump` names
as "silently produces numbers that look fine and mean nothing" (`:568`). Cheap,
and it generalises past this milestone.

**Done when:** `eval:rescore` still parses and grades the frozen pre-M7.6
`warden-output.json` artifacts — a checker-compatibility assertion; it says
nothing about the corpus, which has changed. Plus: the three checks are
registered and unit-tested against hand-built `TurnExecutionResult` fixtures; the
preflight assertion fails loudly against an empty index.
