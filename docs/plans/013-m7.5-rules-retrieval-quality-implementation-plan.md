Multipart implementation plan for
`../specs/zoltar/013-m7.5-rules-retrieval-quality.md`. Each part is sized
for a manual code review and a single commit (a few carry two or three,

**Execution mode for this run.** Parts A–G are implemented straight

## Decisions taken before implementation

Four questions were open when this plan was first drafted. All four are
now closed, and the spec carries the resolution.

### 1. `rollType` lands as a descriptive enum

There was no intended use to recover. `rollType` appears in
`docs/specs/zoltar/011-eval-harness-multi-run.md:269` only as *the
anticipated case* for the fixture-schema-compatibility mechanism — a
hypothetical example of a field some later check might need — is never
mentioned in the M7.4 spec at all, and is repeated as "anticipated" in
`eval/checks/registry.ts:61`. `docs/decisions.md:429` gives concrete jobs
to `gatedByRollId` and `actingEntityId` and none to this one.

**Decided:** `check` / `save` / `damage` / `panic_check` / `table` /
`other`. Read by no checker today; telemetry and a reporting axis. It
rides the baseline already being bought — discovering a use for it later
would mean paying for a third. Spec Part 4.5 amended.

### 2. The stopping rule is read on the metrics that can move

The spec's rule keyed the three-round no-progress test on `authored`
`recall@3`, which M7.2 measured at **100.0%**. It cannot improve by any
amount, so the condition would fire after round three regardless of what
happened elsewhere — including a round that took `warden-observed` from
91.3% to 100%.

**Decided:** the test is evaluated on `recall@3` over the answerable set
as a whole and on `warden-observed` specifically, with `authored` held as
a regression floor. Threshold (5 pp) and budget (three rounds) unchanged;
only the axis moves. Spec's *The stopping rule* section amended.

### 3. The two orphan roadmap bullets land in M7.5, as a new spec Part 4.6

`docs/roadmap.md` M7.5 listed vocabulary bridging and a mechanical-model
primer; the spec's first draft omitted both. Alex's call: land them here.
They are prompt-only changes, so they inherit Parts 4 and 4.5's
must-land-before-the-re-baseline ordering.

**The measurement problem this created, and how it is solved.**
`task eval:retrieval` scores *frozen fixture queries* — it structurally
cannot observe a change in the distribution of queries the Warden emits,
which is exactly what these two levers change. The instrument had to come
from somewhere else, and it turned out to already exist:

> `warden-output.json` is the full serialized `TurnExecutionResult`, whose
> `telemetry` field is the `adventure_telemetry` row, whose
> `payload.rulesLookups` records the query text of every `rules_lookup`
> call. **Verified on disk against
> `claude-sonnet-5__97feadbd__2026-07-29T15-40-17Z`: 146 artifacts, 134
> lookups, 102 distinct queries.**

The empty index of the M7 baselines is no obstacle —
`RulesLookupService.lookup()` embeds and queries regardless of whether the
index has rows, deliberately, "because every lookup attempt is telemetry
input for ingestion prioritization." So the before-number is already on
disk for both models, on the same fixtures, and the after-number falls out
of Part H's run. A genuine paired comparison rather than a cross-corpus
one against `§ S9`'s sample.

New spec Part 4.6 and Done When 10 added; Testing Summary, Documentation
PR Checklist, and Deferrals extended.

### 4. Claude runs the retrieval loop; Alex runs the expensive evals

`task ingest` and `task eval:retrieval` are Voyage-only and the PDF is on
disk and hash-verified, so Parts A and C run here. Everything in Part H —
`eval:run`, `eval:compare`, the playtest — is Alex's.

## Ordering, and why

```
A  set the bar                  (spec Part 1)        docs only
B  make the levers sweepable    (spec Part 2 infra)  python + tests
C  iteration rounds ×3          (spec Part 2)        1 commit per round
D  --markdown curated input     (spec Part 3.1)      python + tests + README
E  similarity floor             (spec Part 4)        TS + tests, or a decision
F  roll_dice fields             (spec Part 4.5)      TS + prompt + checkers
G  Warden query quality         (spec Part 4.6)      prompt + scorer
─────────────────────────── HAND OFF TO ALEX ───────────────────────────
H  re-baseline + playtest       (spec Parts 5, 6)    Alex runs
I  close-out                    (Done When 8)        docs, after H
```

The spec fixes three sequencing constraints and all three are honoured:
Parts E, F, and G land **before** H, because each changes what reaches the
Warden and landing any of them after the re-baseline means buying another.

Everything else is ordered by cost of being wrong. A is first because a
bar chosen after seeing the results is not a bar. B precedes C because
three rounds of hand-edited constants produce three unreproducible
measurements. D is independent of C and sits after it so that if C meets
the bar, D ships the capability and skips the curation experiment, which
is what the spec asks for. F precedes G only so the prompt file is touched
by the smaller change first; both land in the prompt Part H runs against.

`ingestion/tests/test_chunk.py`,
`apps/zoltar-be/eval/retrieval/report.ts`, `ingestion/README.md`.

**What lands:**

header requires): `drop_pages` excludes exactly the named physical pages

**This commit is inert by design.** No lever is pulled, the index is not

## Part D — `--markdown` curated input

**Commit:** `ingestion/pipeline/markdown.py` (new), `ingestion/ingest.py`,
`ingestion/tests/test_markdown.py` (new), `ingestion/README.md`.

### D.1 The capability

`python ingest.py --system mothership --markdown <path>` skips extraction,
hash verification, fixups, footer parsing, and the reading-order sort — a
curated file is already in reading order by construction — and feeds the
same chunk → embed → store path.

New module `pipeline/markdown.py`, **stdlib-only** for the same reason
`chunk.py` is: it must be importable and testable on a CI runner that
installs pytest and nothing else. One function:

```python
def parse_curated_markdown(
    text: str, *, page_offset: int
) -> tuple[list[Block], dict[int, str]]
```

returning the same `Block` list and `page_chapters` map the PDF path
produces, so `chunk_blocks` cannot tell the two apart.

**The format**, documented in `ingestion/README.md` precisely enough that
a self-hoster could produce one for their own book — that is the entire
shipped value of this part:

| Markdown | Becomes |
|---|---|
| `<!-- page: 21 -->` | Sets the current page for everything following. **Printed** page number, the one on the paper; converted to physical via the system's `page_offset` |
| `# CHAPTER NAME` | Sets the chapter for every page from here on — the curated equivalent of the running footer, and the `section_path` breadcrumb source |
| `## …`, `### …` | A `SectionHeader` block. Indexed or not according to `include_section_headers`, exactly as on the PDF path |
| Paragraph | A `Text` block |
| `- ` / `* ` run | One `ListGroup` block |
| `\|…\|` table | One `Table` block — atomic, never split, same as marker's |

A file with no `<!-- page: -->` marker before its first content block is a
**hard error, not a warning**: a curated index with no page provenance
produces `source` strings the retrieval scorer cannot parse page labels
out of, and every fixture would read as a miss for a reason that has
nothing to do with retrieval.

`--markdown` and `--pdf` are mutually exclusive, and `--pdf` stops being
unconditionally required. The manifest records `sourceType: "markdown" |
"pdf"`, `markerVersion: null` on the markdown path, and `markdownSha256`
in place of `pdfSha256`.

**Second consequence, taken:** this makes the pipeline end-to-end testable
without marker for the first time. `test_markdown.py` runs a small
synthetic curated file through `parse_curated_markdown` → `chunk_blocks`
and asserts on the resulting chunks — no model weights, no network, no
embedder. The embed/store half stays out of CI; mocking the embedder buys
little that `test_chunk.py` doesn't already cover.

**No curated Mothership Markdown is committed, now or ever.**
`docs/rules-ingestion.md § What ships in the repository` forbids it, and a
hand-curated PSG is the clearest possible case of enriched extracted text.
The test fixture is a few lines of invented sci-fi rules text, not book
content.

### D.2 The ceiling experiment — conditional

Runs **only if Part C ended below the bar.** If the bar was met, this part
records that the experiment was skipped and why, per the spec's "treat
curation as a fallback the pipeline supports, not the plan of record."

If it runs: curate two or three chapters only — `PANIC CHECKS`, `STAT
CHECKS & SAVES`, and one table-heavy chapter — score the fixtures
targeting those chapters against both the curated and automated versions,
and log the gap. That gap is the ceiling: it separates "our chunking is
bad" from "this book is hard to retrieve from," which is the only thing
that makes full curation a measured decision rather than a hopeful one.

**Comes back to Alex as a decision if it triggers** — it is transcription
from a book, with the measured shortfall attached.

## Part E — The similarity floor

**Commit:** either `src/rules/rules-lookup.service.ts` +
`rules-lookup.service.spec.ts` + `docs/tools.md` + `docs/decisions.md`, or
`docs/decisions.md` + `docs/rules-extraction-findings.md` alone.

Read the top-1 similarity distributions off the **final Part C index** —
not the M7.2 numbers — and decide:

- **If they separate:** the floor goes between them, implemented in
  `RulesLookupService.lookup()` and not in the SQL, per the spec. Keeping
  it in TypeScript makes it testable without a database and visible to
  anyone reading the service. Unit tests cover above-floor, below-floor,
  all-below-floor (empty result), and the boundary value exactly. The
  derivation goes in the code comment and in `docs/decisions.md`;
  `docs/tools.md` updates because `rules_lookup`'s observable behaviour
  changed.
- **If they overlap:** *do not invent a threshold.* Record the overlap and
  leave the behaviour unchanged.

**The likely outcome, stated in advance so it is not mistaken for
laziness:** `§ S15.4` measured both distributions on 49 fixtures and found
them overlapping in both preprocessing configurations — unanswerable max
~0.416 sitting above answerable min 0.342. Part C's rounds mostly *remove
pages*; that is not obviously the kind of change that separates two
distributions. "No honest floor exists yet" is the probable finding, and
it is one the milestone can close on. The empty-result path the Warden
already handles correctly is the safe default either way.

## Part F — The `roll_dice` schema fields

Three commits. The largest code change in the milestone, and the one with
the most surface area outside its own files.

### F.1 — Schema, tool loop, and persistence

**Commit:** `src/session/session.schema.ts`, `session.tools.ts`,
`session.service.ts`, `session.events.ts`, plus specs.

`rollDiceInputSchema` gains:

| Field | Shape | Required? |
|---|---|---|
| `actingEntityId` | `string` — entity identifier, underscores only per CLAUDE.md (`dr_chen`, `corporate_spy_1`) | **required** |
| `rollType` | `check` / `save` / `damage` / `panic_check` / `table` / `other` | **required** |
| `gatedByRollId` | `string`, must name a `rollId` already returned **this turn** | optional |

`rollDiceOutputSchema` gains `rollId: string`. `gatedByRollId` is unusable
without one: nothing in the tool result today identifies a roll, and
`game_events.id` is a UUID minted at write time, *after* the turn ends —
Claude cannot reference an id that does not exist while it is choosing its
next call.

`rollId` is therefore a **per-turn synthetic** — `roll_1`, `roll_2`, …
allocated by `handleRollDice` in issue order, matching the repo's
underscores-only identifier convention. Persisted into the payload so the
checker can resolve links after the fact.

**Required-vs-optional is deliberate.** `actingEntityId` and `rollType`
are required because an omitted field reads identically to a missing one
at scoring time — the exact failure the spec's *Schema and prompt land
together* paragraph is about. The tool loop already returns an `is_error`
`tool_result` on a Zod parse failure, so a malformed call is corrected
in-loop rather than failing the turn; that is the same retry path
`docs/decisions.md` records for `gmUpdates`. `gatedByRollId` is optional
because most rolls genuinely have no gate, and requiring a sentinel would
make "ungated" indistinguishable from "the model filled the required field
with something."

`gatedByRollId` naming an unknown or not-yet-issued `rollId` is an
`is_error` `tool_result` listing the ids actually available this turn —
not a silent drop. A dangling link is worse than no link: it would make
the in-turn ordering case look decidable while pointing at nothing.

`PendingSystemRoll` and `DiceRollEventPayload` (`session.events.ts`) each
gain `rollId`, `rollType`, `actingEntityId`, and optional `gatedByRollId`.
**No migration** — `dice_roll` events are `game_event` rows with `payload
jsonb`, so these are new keys in an untyped column
(`docs/schema.md § Game Events`). `docs/schema.md` is not touched.

**Tests:** `session.schema.spec.ts` for the new required/optional shapes
and the enum; `session.tools.spec.ts` for the emitted JSON schema;
`session.tool-loop.spec.ts` for `rollId` allocation order, the
dangling-reference error path, and the fields surviving into the persisted
payload.

### F.3 — Teach the two checkers to read the fields

**Commit:** `eval/checks/structural/out-of-order-resolution.ts`,
`system-rolled-player-action.ts`, `attribution.ts`, their specs,
`docs/decisions.md`.

**`out-of-order-resolution` — the in-turn case.** Today, with no
`dice_request` pending, the check returns `NOT_APPLICABLE` carrying
`actualCode: 'no pending dice_request; in-turn ordering undecidable
without gatedByRollId'`. With the field present it becomes decidable: a
roll naming a `gatedByRollId` whose target has a **higher** sequence
number than itself resolved ahead of its gate. That is a FAIL read purely
off structure. A turn whose rolls all name gates preceding them, or name
none, is a PASS.

The deferred-gate path is untouched. The documented residual false FAIL —
a stress/panic check triggered by NPC fire that resolved earlier in the
same turn, indistinguishable from a pre-rolled damage roll — is exactly
what `gatedByRollId` resolves, and the spec assertion that currently reads
"if `gatedByRollId` ever lands, it should flip to PASSED" becomes an
assertion that it does.

**`system-rolled-player-action` — attribution.** `attribution.ts`'s
`isAttributedTo` is the last prose dependency in the structural checks.
When `actingEntityId` is present it is used directly, compared against the
fixture-authored `applicability[checkId].playerEntity`; the prose match is
never consulted. When absent — a frozen pre-M7.5 artifact under
`eval:rescore` — the current prose path runs unchanged, including
`unbindableVerdict`.

## Part G — Warden query quality (spec Part 4.6)

Two commits.

### G.1 — The two prompt blocks

**Commit:** `src/wardens/prompts/mothership-m7.txt`, `docs/tools.md` if
`rules_lookup`'s described usage changes.

- **Vocabulary bridging** — guidance steering `rules_lookup` phrasing
  toward book vocabulary and toward fewer, more distinctive terms.
  `§ S5.3` measured both axes moving a target monotonically: swapping
  `perception`→`intellect` took a query from 9th to 4th, and cutting to
  core terms took it to 1st. The prompt already says *"Query in natural
  language. 'panic check result of 73' outperforms 'panic 73'"* — which is
  the verbosity half, stated once and weakly. This extends it and adds the
  vocabulary half.
- **The mechanical-model primer** — Mothership's actual resolution model:
  roll-under-stat, no DC or target number, no opposed rolls, no flanking,
  no initiative in the D&D sense. Targets the concept-absent bucket, which
  no retrieval fix can reach at any chunking quality.

**Not the same lever.** `§ S9`'s headline is that the wrong-word (45.6%)
and concept-absent (37.8%) buckets "are not substitutes for each other."
Bridging rephrases a question the book can answer; the primer prevents a
question the book cannot.

**Prompt-side only. The per-system synonym/thesaurus table does not ship**
— it is real ongoing per-system authoring cost, and G.2's number is what
decides whether it is still wanted. Recorded as a deferral in the spec.

### G.2 — The out-of-corpus query scorer, and the before-number

**Commit:** `scripts/query-vocab.ts` + `query-vocab.core.ts` + spec,
`src/rules/rules.repository.ts` (one lexeme query), `Taskfile.yml`,
`docs/rules-extraction-findings.md`.

`task eval:query-vocab -- <run-dir>` harvests every `rules_lookup` query
out of a run directory's `warden-output.json` artifacts
(`telemetry.payload.rulesLookups[].query`) and reports the share carrying
at least one term absent from the `rules_chunk` corpus, with the distinct
absent terms listed for the hand audit.

**`§ S9.1`'s double-stemming bug is a specified hazard, not one to
rediscover.** Check presence with `to_tsquery('simple', …)` or by
comparing lexeme sets directly — never by re-stemming a lexeme
`websearch_to_tsquery` already stemmed, which reported `surpris` → `surpri`
as absent from its own tsvector and cost S8 three false absents.

Run it immediately against both frozen `88fa84bd8329` runs to establish
the before-number, and log that as a `docs/rules-extraction-findings.md`
session — a successor to `§ S9`, on the same fixtures the after-number
will come from. The after-number waits for Part H.

**Tests:** the scoring function against a fixed lexeme set — an
all-in-corpus query, a query with one absent term, an empty query set
(which must report an *undefined* rate, not zero), and a regression case
pinning the double-stemming bug. The artifact harvester is tested the way
`eval:rescore`'s reader is. The Postgres lexeme query is not unit-tested.

**The automated rate is the headline; the wrong-word / concept-absent
split is a paragraph of judgement** over the distinct absent terms, as it
was in `§ S9.3`. `§ S9` found 100 distinct terms across 596 queries, so
the audit is small.
