# M7.2 — Rules Ingestion Pipeline: Implementation Plan

Multipart implementation plan for
`../specs/zoltar/012-m7.2-rules-ingestion.md`. Each plan part is sized for
a manual code review and a single commit. Pause after each part for review
before starting the next.

Ordering is roughly dependency order, with one deliberate departure: the
chunker lands before the extractor (Part 2 before Part 3) even though the
pipeline runs them the other way round. The chunker is the only module in
this milestone with a real algorithm, the only one covered by an automated
test, and the only one that must stay importable without marker's model
weights. Getting it reviewed on its own, against a synthetic Markdown
string, is worth more than matching runtime order.

**Part 1** (scaffolding + pins) → **Part 2** (chunker + CI) → **Part 3**
(hash/extract/fixup + `--dry-run` CLI) → **Part 4** (embed/store + full
run) → **Part 5** (docs + `task ingest`) → **Part 6** (eval re-baseline)
→ **Part 7** (playtest + fixtures).

Parts 1–5 are the Python milestone. Parts 6–7 are Part 6 of the spec —
TypeScript-and-play validation, no Python — and are what turn "the table
has rows" into "the Warden is better off."

Resolved up front by reading the actual code, so each part can execute
rather than re-derive.

  `.env.example:35`). The spec's requirement that `--voyage-model`'s
  default stay in sync with the backend is satisfied by defaulting to the
  same literal. The `voyage-3-lite` 512-dimension mistake recorded in

  `main` — do not "fix" it again.
- **`rules_chunk` needs no migration.** `infra/db/migrations/V7__rules_index.sql:8-16`
  gives exactly four writable columns: `source text`, `section_path
  text[]`, `content text`, `embedding vector(1024)`. There is no
  `token_count`, `chunk_index`, `page`, or `created_by` column — do not

- **`apps/zoltar-be/scripts/one-off/` already exists** (M7.3 created it
  for `import-legacy-synthesis-snapshot.ts`). The spec's Part 4.3 option

  established home and an established file layout (`.ts` wrapper +
  `.core.ts` + `.spec-int.ts`) to copy.
- **The eval harness points at the same DB Alex seeds.**
  `Taskfile.yml:72` runs `eval:run` with `--env-file=.env`, and
  `eval/harness-runner.ts:52-56` reads `DATABASE_URL` from `process.env`.
  Its scratch adventure resolves `game_system` by `slug = 'mothership'`
  (`harness-runner.ts:188-194`) and tags the adventure with that
  `systemId` (`:234`) — the same `system_id` ingestion writes under. So
  the spec's "re-baseline against an empty index measures nothing and
  looks like success" hazard is structurally handled, provided `.env`'s

  explicitly at the top of Part 6** — the hazard is cheap to check and
  expensive to discover afterwards.
- **CI has exactly two jobs** (`backend`, `frontend`), both Node 24

- **`.gitignore` has no Python entries** and `Taskfile.yml` has no
  `ingest` task. Both additions are new, not edits.

### Decisions the spec leaves to implementation

**1. Page provenance: `source` is the only citation the Warden ever
sees.** `findByCosineSimilarity` returns `source` and `content` only —
`section_path` is stored but never surfaced (`rules.repository.ts:45-53`,
`rules-lookup.service.ts:36-42`). So `source` has to carry the whole
citation, and the design doc's example format is `"Mothership Player's
Survival Guide p.34"`. See decision 6 for what to do about the missing
hierarchy.

Marker's plain Markdown output does not reliably carry page numbers.
Resolution: **`extract.py` emits page sentinels into the Markdown it hands
downstream** — an HTML comment line, `<!-- page: 34 -->`, at each page
boundary — and `chunk.py` tracks the most recent sentinel it has passed,
attaching that page to each chunk. Two properties this buys:

- `chunk.py` stays a pure function of a Markdown string. The synthetic
  fixture in `test_chunk.py` can include sentinels; nothing about page
  attribution requires marker to be installed.
- If marker's chosen output format turns out not to expose page
  boundaries at all (check `--output_format json` / its chunk metadata in
  Part 3 before committing to Markdown), the fallback degrades cleanly:
  emit no sentinels, and have the `source` builder fall back to
  `"Mothership Player's Survival Guide — Combat › Panic Checks"` (title
  plus section path) rather than dropping to a bare book title. A section
  citation is still useful to a player checking the Warden's work; a
  bare title is not.

**2. `chunk.py` must not import `tiktoken` at module scope.** The spec
says the CI test "touches no network." `tiktoken` downloads its BPE files
from the network on first encoder construction, so a module-level
`tiktoken.get_encoding(...)` would make the test network-dependent and
flaky in CI. Resolution: the chunking entry point takes an injectable
`count_tokens: Callable[[str], int]` whose default is a lazily
constructed tiktoken encoder, built on first call, not at import.
`test_chunk.py` passes a trivial deterministic counter instead. The
~400-token target is a retrieval heuristic with no hard boundary (spec
Part 3), so testing the splitting logic against an approximate counter
loses nothing. This is also what satisfies the spec's "the chunking
module must not import anything from `extract.py` or `embed.py` at module
scope" — same constraint, one wider.

Consequence: CI installs a small `ingestion/requirements-dev.txt`
(`pytest` only, pinned), never the full `requirements.txt`. Marker's
extraction models must not land on a CI runner.

**3. `argparse` collides with the spec's exit codes.** `argparse` exits
`2` on a usage error; the spec assigns `2` to "marker extraction failed"
and `5` to "invalid arguments." Resolution: subclass `ArgumentParser` and
override `error()` (and `exit()`) to exit `5`. Without this, a typo in a
flag reports as an extraction failure.

**4. `--database-url` should also read `$DATABASE_URL`.** The spec lists
it as required. Proposed minor deviation: keep it required *in effect*,
but let it default from the `DATABASE_URL` environment variable exactly
as `--voyage-api-key` defaults from `VOYAGE_API_KEY`. The spec's own
usage example (4.2) already exports `DATABASE_URL` and then passes it
back in as a flag, which is pure ceremony. Missing from both flag and env
→ exit `5`. Flag this in the Part 3 PR description; revert to
strictly-required if the reviewer prefers the spec's literal reading.

**5. ivfflat index quality after a bulk load — the one real database
gotcha in this milestone.** `rules_chunk_embedding_idx` is an ivfflat
index created in `V7__rules_index.sql:19-21`, at migration time, against
an empty table. ivfflat computes its cluster centroids at build time from
the rows present; built on zero rows there are no meaningful centroids,
and pgvector's own guidance is to create an ivfflat index *after* the
table has data. Every re-ingestion (`DELETE` + re-`INSERT`) also churns
the index against stale centroids.

Resolution: **`store.py` runs `REINDEX INDEX rules_chunk_embedding_idx;`
after the insert commits**, as a final step, logged. Ingestion is an
offline job — the lock is free. This is also the first thing to try if
Part 4's sanity query returns nothing or returns obviously irrelevant
chunks despite a healthy row count: the failure mode of a degenerate
ivfflat index is poor or empty recall, not an error. Note that
`ORDER BY embedding <=> ...` remains *correct* under a bad index only
because Postgres may fall back to a sequential scan; do not rely on
that.

**6. Continuation chunks lose their heading — fix it in the embedding,
not the tool result.** The paragraph-boundary split in `chunk.py` produces
chunks that begin mid-section, whose text may contain no heading at all: a
continuation of "### Panic Checks" can easily never say "panic." Such a
chunk is retrieved on vector similarity alone and arrives at the Warden as
orphaned prose.

Resolution: **`chunk.py` prepends a breadcrumb line — `Combat › Panic
Checks` — to every chunk's `content`.** Because it lands in `content` it
is part of the embedded text *and* part of what the Warden reads, so it
improves retrieval rather than only presentation. This is the standard
contextual-chunk-header technique, and it is the reason to prefer it over
the alternative below.

The alternative — surfacing `section_path` through the tool result — is
deliberately *not* in scope by default. It would be small (`section_path`
into the SELECT and `RulesChunkMatch` in `rules.repository.ts:34-59`, one
line in `rules-lookup.service.ts`, one in `rulesLookupOutputSchema` at
`session.schema.ts:113`, plus fixture updates in the two existing specs —
roughly 20 lines across 6 files), and it would *not* change the tool
schema Claude sees, since `session.tools.ts:19` derives the JSON schema
from `rulesLookupInputSchema` only and the output shape is undeclared. But
it is presentation-only: by tool-result time the embedding is already
computed, so it cannot fix the retrieval half. Take it up only if Part 3
finds that marker *does* supply page numbers — in that case `source` reads
`"…PSG p.34"` and the hierarchy is genuinely absent from the payload. If
marker does not, decision 1's fallback already puts the section path into
`source`, and adding the field would write the same string twice.

Either change alters what reaches the Warden on turns that get index hits,
so **both must land before Part 6**, not after. This is a weaker
constraint than the `roll_dice` one: they affect only turns that call
`rules_lookup` and receive results, which is precisely the population the
re-baseline studies. But adding either afterwards leaves it unmeasured
until the next baseline.

### Resolved with Alex — the `roll_dice` fields do not land here

The deferred `roll_dice` schema fields (`rollType`, `gatedByRollId`,
`actingEntityId`) stay deferred through M7.2. Part 6 re-baselines the
index change alone, and the project accepts paying for a third full
baseline whenever those fields land. Reasoning in Part 6; `docs/decisions.md
§ rollType / gatedByRollId / actingEntityId on roll_dice stay deferred`
needs updating to say so when Part 6's documentation lands — it currently
reads as though the fields would ride along with this re-baseline.

## Part 2 — Heading-aware chunking, its unit test, and the CI job

The algorithmic heart of the milestone and the only part with automated
coverage. Reviewed against a synthetic string, with a manual eyeball
against Part 1's real extraction output.

**`ingestion/pipeline/chunk.py`.** Canonical algorithm is
`docs/rules-ingestion.md § Step 4`; the spec restates it in Part 2 step 4.
Target shape:

```python
@dataclass(frozen=True)
class Chunk:
    content: str
    section_path: list[str]   # heading ancestry, e.g. ["Combat", "Panic Checks"]
    page: int | None          # from the most recent page sentinel, if any

def chunk_markdown(
    markdown: str,
    *,
    target_tokens: int = 400,
    overlap_tokens: tuple[int, int] = (50, 100),
    count_tokens: Callable[[str], int] | None = None,
) -> list[Chunk]:
    ...
```

Behavior, in the order the test asserts it:

- Walk the heading tree; each `###` section is a candidate chunk, with
  `section_path` carrying full ancestry from `#` down.
- Sections over `target_tokens` split further at paragraph boundaries,
  never mid-sentence.
- **Every chunk's `content` opens with a breadcrumb line** built from its
  `section_path` — `Combat › Panic Checks` — per Pre-flight decision 6.
  This is what keeps a mid-section continuation chunk retrievable on its
  own topic when its body never names it.
- Adjacent chunks split out of the *same* section overlap by 50–100
  tokens. Chunks from *different* sections do not overlap. **Measure
  overlap on the body, not on the prefixed content** — the breadcrumb is
  byte-identical across every chunk in a section, so an overlap check
  computed over `content` would count the prefix and pass for the wrong
  reason. This is the easiest bug in this part to ship green.
- Page sentinels (`<!-- page: N -->`, Pre-flight decision 1) are consumed
  as metadata and stripped from `content` — a sentinel must never reach
  the embedding or the text the Warden reads.
- `count_tokens` defaults to a lazily built tiktoken encoder. No
  `import tiktoken` at module scope; no import from `extract.py`,
  `embed.py`, `store.py`, or `fixup.py` at all.

**`ingestion/tests/test_chunk.py`** — the four assertions the spec's
Testing Summary names, against a small synthetic Markdown string with
known heading structure, plus a deterministic injected `count_tokens`:

1. Chunk boundaries respect `###` headings.
2. An oversized section splits at paragraph boundaries without breaking
   mid-sentence.
3. Overlap between adjacent chunks from the same section is within the
   50–100 token band.
4. Chunks carry correct `section_path` ancestry.

Add two more while the fixture is in hand: page sentinels are stripped
from `content` and reflected in `page`; and a continuation chunk (the
second half of an oversized section) opens with the same breadcrumb as its
first half.

`ingestion/tests/` is a sibling of `pipeline/`, deliberately departing
from `CLAUDE.md`'s adjacent-tests convention — that convention is written
for the TypeScript apps, and a top-level `tests/` package is the pytest
idiom (spec Part 1). Note this in the PR description so the divergence
reads as intentional in review.

**`.github/workflows/ci.yml`** — a third job alongside `backend` and
`frontend`:

```yaml
  ingestion:
    name: Ingestion (pytest)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip
      - name: Install dev dependencies
        run: pip install -r ingestion/requirements-dev.txt
      - name: Unit tests
        run: pytest ingestion/tests/
```

`requirements-dev.txt`, not `requirements.txt` — installing marker in CI
would defeat the point (spec Testing Summary). If `pytest ingestion/tests/`
fails on a missing `tiktoken`, Pre-flight decision 2's lazy-import
constraint has been violated somewhere; fix the import, do not add
`tiktoken` to the CI install.

**Review gate.** `pytest ingestion/tests/` green locally with only
`requirements-dev.txt` installed in a clean venv — this is the check that
actually proves the hermeticity claim, and it is easy to pass accidentally
in a venv that already has the full requirements. Push the branch and
confirm the `ingestion` job runs and passes on GitHub. Manually run
`chunk_markdown` over Part 1's real PSG extraction and eyeball the output:
chunk count in the 100–400 range the spec expects, section paths that look
like real PSG structure, no chunk that is a bare table fragment or a
heading with no body. Commit.

## Part 3 — Hash verification, extraction, fixups, and the `--dry-run` CLI

The input half of the pipeline: PDF → Markdown → patched Markdown →
chunks. Ends with a working `python ingest.py ... --dry-run`, which is
Done When 5 and half of Done When 6, before a single byte goes to Voyage.
Deliberately structured so the expensive-and-external half (Part 4) is
reviewed separately from the cheap-and-local half.

**`ingestion/pipeline/hash.py`** — SHA-256 the input PDF, compare against
`ingestion/<system>/hashes/<edition>.txt`. File format is one line,
`<hash>  <filename>`; read only the hash portion (spec 4.1). Mismatch
warns and proceeds — never blocks. Missing hash file warns and proceeds
(a Phase 2 system with no recorded edition is not an error). No
`--require-hash`; the spec explicitly defers it.

**`ingestion/mothership/hashes/mothership-psg-1e.txt`** — generated from
Alex's reference PDF:

```bash
shasum -a 256 mothership_players_survival_guide.pdf > \
  ingestion/mothership/hashes/mothership-psg-1e.txt
```

(macOS ships `shasum -a 256`, not GNU `sha256sum`; the README should give
both.) Strip the absolute path from the filename column before committing
— the hash file should record a bare filename, not Alex's home directory
layout.

**`ingestion/pipeline/extract.py`** — invoke marker into a temp directory,
return Markdown (with page sentinels per Pre-flight decision 1). Decide
here, against the real tool, whether page provenance comes from marker's
Markdown, its JSON output, or not at all — and record which in the PR
description. It determines two things: the `source` format every chunk in
the index carries, and whether the optional `sectionPath` tool-result
change in Pre-flight decision 6 is worth doing at all (it is worth doing
only if pages *are* available, and it has to land before Part 6 if it
lands). Clean up the temp directory on both success and failure. Marker
failure → exit `2`.

**`ingestion/pipeline/fixup.py`** — apply `ingestion/<system>/fixups.json`
against the extracted Markdown, per the entry format in
`docs/rules-ingestion.md § Step 2` (`description`, `match.section`,
`match.contains`, `replace_with_template`). Mothership's file is `[]` in
M7.2, so this is plumbing exercised only by the empty case — keep it
correspondingly simple, and make an entry that matches nothing a loud
warning rather than a silent no-op, since a fixup that stops applying
after a marker bump is exactly the failure this file exists to survive.
Templates resolve from `ingestion/<system>/templates/`.

**`ingestion/ingest.py`** — full argument surface (all seven flags from
spec Part 2, so the CLI's shape is reviewed once), pipeline steps 1–4
wired, `--dry-run` exiting after chunking with a chunk count and
first-chunk preview. Steps 5–7 (`embed`, dimension check, `store`) are
`NotImplementedError` placeholders landing in Part 4 — state this
explicitly in the PR description so a reviewer does not read them as an
oversight. Exit codes `1`, `2`, `5` implemented; `3` and `4` land with
their code paths in Part 4. `ArgumentParser.error` overridden to exit `5`
(Pre-flight decision 3). `--database-url` defaults from `$DATABASE_URL`
(Pre-flight decision 4 — flag for the reviewer).

**Review gate.** Against the real PSG:
`python ingest.py --system mothership --pdf <psg> --dry-run` prints a
chunk count in 100–400 and a first-chunk preview, exit `0` (Done When 5).
A deliberately corrupted copy of the hash file produces a warning and
still completes; `--skip-hash-check` produces its own warning and skips
verification (Done When 6). A nonexistent `--pdf` exits `1`; a bogus flag
exits `5`; pointing `--system` at a slug with no directory produces a
clear error rather than a traceback. Confirm no temp directory survives a
successful run. Commit.

## Part 4 — Embedding, the dimension guard, storage, and the first real seed

The part that spends money and writes rows. Everything before it was
rehearsal.

**`ingestion/pipeline/embed.py`** — `voyageai.Client().embed(texts,
model=..., input_type="document")`. Batch even though a PSG-sized book
fits in one call (spec Part 2 step 5): the endpoint caps at 1,000 texts
per request, and batching now means the code does not need revisiting for
a larger rulebook. Chunk order must be preserved across batch boundaries
— the embedding at index *i* must belong to chunk *i*, and a reordering
bug here produces an index that looks healthy and returns nonsense.
Non-transient Voyage errors → exit `3`.

**Dimension check** — before deleting or inserting anything: read
`game_system.embedding_dim` for the target slug, assert every returned
vector's length equals it. Mismatch → exit `3` with a message naming both
the configured model and both numbers. This is the guard that would have
caught the `voyage-3-lite` 512-dimension mistake (`docs/decisions.md §
Embedding model`); the ordering matters as much as the check — running it
after the `DELETE` would trade a caught bug for an emptied index.

**`ingestion/pipeline/store.py`** — psycopg, one transaction:

1. `SELECT id, embedding_dim FROM game_system WHERE slug = %s` — no row →
   clear error, exit `4`.
2. `DELETE FROM rules_chunk WHERE system_id = %s` (idempotency, Done
   When 4).
3. Insert one row per chunk: `source`, `section_path` (a Python list maps
   to `text[]` natively under psycopg 3), `content`, `embedding`. Never
   NULL on `embedding` — see Pre-flight. Use `executemany`/`copy` rather
   than a per-row round trip.
4. Commit.
5. `REINDEX INDEX rules_chunk_embedding_idx;` after the commit, logged
   (Pre-flight decision 5).

Database errors → exit `4`.

**`ingest.py`** — replace the Part 3 placeholders; wire exit codes `3` and
`4`. Log a one-line summary on success: chunk count, model, dimension,
system, elapsed time.

**Sanity check (Done When 3).** Add
`apps/zoltar-be/scripts/one-off/rules-lookup-probe.ts`, following the
existing `one-off/import-legacy-synthesis-snapshot.ts` layout — instantiate
`RulesLookupService` (or call `VoyageService.embed(query, 'query')` +
`RulesRepository.findByCosineSimilarity` directly, whichever is less
ceremony outside Nest's DI), print each hit's `source`, `similarity`, and
a content excerpt. This is the spec's second-listed 4.3 option, chosen
over the eval-harness option because it costs one Voyage call instead of a
full turn and isolates retrieval from Warden behavior — Part 6 exercises
the full harness path anyway, so nothing is lost. Keep it out of
`Taskfile.yml`: it is a probe, not tooling.

**Review gate.** Done When 1, 2, 3, and 4, in that order:

- Full run against the local Postgres exits `0`.
- `SELECT COUNT(*) FROM rules_chunk WHERE system_id = (SELECT id FROM
  game_system WHERE slug = 'mothership')` returns 100–400.
- `SELECT COUNT(*) FROM rules_chunk WHERE embedding IS NULL` returns 0.
- The probe, run with "what happens on a panic check of 73", returns
  chunks from the Panic section with top-hit similarity > 0.5. If it
  returns nothing or nonsense at a healthy row count, `REINDEX` first —
  that is the degenerate-ivfflat signature.
- Re-run the whole pipeline unchanged; the count is identical, not
  doubled.
- Spot-check three `source` values against the physical book: the page or
  section citation is actually right. A confidently wrong citation is
  worse than none.

Record chunk count, sample query, and top similarity score in the PR
description (spec Testing Summary). Commit.

## Part 5 — Documentation and `task ingest`

No behavior change; the part where the pipeline becomes usable by someone
who is not Alex. Landing it separately keeps Part 4's review focused on
correctness rather than prose.

**`ingestion/README.md`** (new, spec 5.1). Must stand alone — Done When 7
is "sufficient for a new self-hosted user ... without consulting other
docs":

- Prereqs: Python 3.11+, `pgvector` enabled in the target Postgres, a PDF
  the user owns.

  when `--skip-hash-check` is right, re-ingestion after fixup changes,

  results" → `REINDEX INDEX rules_chunk_embedding_idx`.
- Known limitations: no pre-built SRD indexes in Phase 1, Mothership only.

**`docs/rules-ingestion.md`** (spec 5.2) — cross-link at the top:

## Part 7 — Dedicated playtest and fixture capture (spec 6.2)

The last part, and the only one that answers "did the index actually
help?" The harness replays frozen turns from adventures that ran without
rules; it can show whether behavior on those turns changed, not whether a
live session goes better.

- Play a real Mothership session against the populated index.
- Review it with `task playtest:review -- <adventure-id>` (M7.1 tooling).
  Read the `rulesLookups` telemetry specifically: which queries the
  Warden made, what came back, and what the similarity scores were. This
  is the first session in the project's history where those lookups
  returned anything, and it is also the evidence the deferred
  chunk-quality work (spec's "Chunk quality evaluation" deferral) has been
  waiting on. Note what you find even if nothing is actionable.
- Capture fixtures with `task eval:capture-fixture` for any turn that
  exhibits `MISSING-CANON-CAPTURE`, `UNSURFACED-CHECK`,
  `OVER-RESOLUTION`, or `SCENE-JUMP` — the four tags still sitting at one
  instance each (`docs/roadmap.md:250`, M7.4's open fixture bullet).

**The caution is the point, not boilerplate.** One session is not
guaranteed to exhibit all four modes. A fixture authored from a turn that
did not actually exhibit its tag is worse than a missing fixture — it pins
a check to behavior that was never wrong, and it does so permanently and
invisibly. If a tag stays at one instance after the playtest, that is
evidence about how rare the mode is: record it, leave M7.4's fixture
bullet open, and do not manufacture an instance.

**Documentation:**

- `docs/roadmap.md` — check off the playtest bullet. Update M7.4's
  fixture bullet to reflect which tags reached two confirmed instances and
  which did not, rather than closing it wholesale.
- Note in the M7.4 bullet (or `docs/decisions.md`) that the corpus version
  has changed, so any future comparison against Part 6's baseline is
  cross-corpus and will warn.

**Review gate.** Playtest played and reviewed. Any captured fixtures pass
`eval:replay` against their own checks and are honestly tagged. Roadmap
reflects reality, including the parts that did not happen. Commit. This
closes M7.2.
