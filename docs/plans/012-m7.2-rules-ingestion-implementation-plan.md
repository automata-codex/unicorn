**Ordering.** Parts 2–5 are the Python pipeline, in dependency order except
that the chunker precedes the extractor for the same reason as before: it
is the only module with a real algorithm, the only one covered by an
automated test, the only one that must stay importable without marker's
model weights — and Part 1 already produced real `chunks` JSON to develop
against, so the extractor's absence costs nothing.

**Part 2** (reading-order sort + attribution + CI) → **Part 3** (block
merge) → **Part 4** (hash/extract/fixup + `--dry-run` CLI) → **Part 5**
(embed/store + first real seed) → **Part 6** (query preprocessing, TS) →
**Part 7** (retrieval harness code, TS) → **Part 8** (fixture set + first
measured run) → **Part 9** (docs, `task ingest`, roadmap/decisions).

## Pre-flight: verified facts and decisions the spec leaves open

  (`apps/zoltar-be/src/config/env.schema.ts:19`). `--voyage-model`'s

- **`rules_chunk` needs no migration.** `infra/db/migrations/V7__rules_index.sql:8-16`
  gives four writable columns: `source text`, `section_path text[]`,
  `content text`, `embedding vector(1024)`. No `token_count`,
  `chunk_index`, or `page` column — do not invent one. Latest migration is
  `V17__pending_canon_sequence_number.sql`; M7.2 adds none, Parts 6–8
  included.

  `RulesRepository.findByCosineSimilarity` filters `AND embedding IS NOT

- **`RulesLookupService.lookup()` is the single query-path chokepoint**
  (`src/rules/rules-lookup.service.ts:25-45`) — one `voyage.embed(query,

- **`scripts/one-off/` exists** with an established layout (`.ts` wrapper +
  `.core.ts` + `.spec-int.ts`), from M7.3's

- **`ingestion/requirements.txt` pins `marker-pdf==2.0.0`,

### Carried forward from the previous plan, still correct

**1. `chunk.py` must not import `tiktoken` at module scope.** `tiktoken`
downloads BPE files on first encoder construction, so a module-level
`get_encoding(...)` makes the CI test network-dependent. The chunking entry
point takes an injectable `count_tokens: Callable[[str], int]` whose
default is a lazily constructed encoder. `requirements-dev.txt` already
encodes this constraint in a comment; CI installs it and never
`requirements.txt`.

**2. `argparse` collides with the spec's exit codes.** `argparse` exits `2`
on usage error; the spec assigns `2` to "marker extraction failed" and `5`
to "invalid arguments." Subclass `ArgumentParser` and override `error()`
and `exit()` to exit `5`.

**3. `--database-url` should also read `$DATABASE_URL`.** Required *in
effect*, but defaulting from the environment exactly as `--voyage-api-key`
defaults from `VOYAGE_API_KEY`. The spec's own 4.2 example exports
`DATABASE_URL` and then passes it back as a flag, which is ceremony.
Missing from both → exit `5`. Flag in the Part 4 PR description; revert to
the spec's literal reading if the reviewer prefers.

**4. ivfflat index quality after a bulk load.**
`rules_chunk_embedding_idx` is an ivfflat index built at migration time
against an empty table (`V7__rules_index.sql:19-21`), so its centroids are
meaningless, and every re-ingestion churns it against stale ones.
`store.py` runs `REINDEX INDEX rules_chunk_embedding_idx;` after the insert
commits, logged. Ingestion is offline; the lock is free. This is also the
first thing to try if Part 5's probe returns nothing or nonsense at a
healthy row count — the failure mode of a degenerate ivfflat index is poor
recall, not an error.

**5. Continuation chunks lose their heading — fix it in the embedding, not
the tool result.** Every chunk's `content` opens with a breadcrumb line
built from the **footer chapter**, never from marker's `section_hierarchy`
(`§ S1.7` — that field turns siblings into parents). Because the breadcrumb
lands in `content`, it is embedded *and* read by the Warden, so it improves
retrieval rather than only presentation. Surfacing `section_path` through
the tool result remains out of scope — it is presentation-only, and by
tool-result time the embedding is already computed.

### New decisions this revision makes

**6. Per-system metadata gets a small file, not a constant in pipeline
code.** `source` must read `"Mothership Player's Survival Guide p.34"`
(`docs/rules-ingestion.md § Step 4`), and the `printed = physical + 1`
offset is edition-specific (`§ S1.8`, `docs/decisions.md § Chunk extraction
is block-based…`). Neither belongs hardcoded in `chunk.py`, and the spec's
own Part 1 promise is that "Phase 2 adds sibling directories without
touching pipeline code."

Proposed: `ingestion/<system>/system.json` —

```json
{
  "source_label": "Mothership Player's Survival Guide",
  "page_offset": 1,
  "footer_format": "psg-1e"
}
```

Small addition beyond the spec's directory listing; flag it in the Part 3
PR description. The alternative — a `--source-label` flag plus a
`--page-offset` flag — pushes edition facts onto every invocation, which is
exactly the thing the `<system>/` pattern exists to avoid.

**7. The character-creation exclusion is decided but does not ship here.**
`docs/decisions.md § Character-creation content is excluded from the rules
index` settles that physical pages 4, 41, 42 are excluded. The spec lists
that exclusion under "M7.5 scope, not touched here," and `roadmap.md` M7.5
carries the bullet. **Do not implement it in M7.2** — it changes the index
before the baseline that M7.5's iteration is measured against. Chunking
should expose page filtering as a one-line policy point (a
`drop_pages: set[int]` parameter defaulting to empty) so M7.5's lever 5 is
a config change, not a refactor.

**8. Index provenance is written by the pipeline, read by the harness.**
M7.5's Part 2 requires marker version, chunking parameters, embed model,
and chunk count in every retrieval run's manifest, and there is no
ingestion-metadata table (no migration allowed). `ingest.py` writes
`ingestion/.ingest-manifest.json` (gitignored) on success; Part 7's harness
copies it into its run manifest when present and records
`"indexProvenance": null` when absent. Addition beyond the spec, justified
by M7.5 Part 2's "a score compared across different provenance is not a
comparison." Lands in Part 5, consumed in Part 7.

## Part 2 — Reading-order sort, page/chapter attribution, and the CI job

The correctness-critical half of the chunker, split out from the merge
because it is validated against a different thing: a real objective oracle
over the actual PSG extraction, not synthetic fixtures alone.

**Why this is its own part.** `§ S6.2` established that marker's emitted
block order is not reading order — 8 of the 16 pages carrying two or more
numbered section headers emit them out of order, including full reversals.
A chunker that merges in emitted order concatenates roughly half the book's
body pages backwards, and it does so *silently*: the chunk count looks
right, the token counts look right, and the text is scrambled. `§ S7`
already tested the fix and scored it (8/16 → 15/16, nothing regressed).
This part implements a probe that has already been proven, against an
oracle that already exists.

**Files:**

- `ingestion/pipeline/chunk.py` — new, sort and attribution only. Standard
  library only at module scope. No import of `extract.py`, `embed.py`,
  `store.py`, `fixup.py`, or `tiktoken`.
- `ingestion/tests/test_chunk.py` — new.
- `.github/workflows/ci.yml` — third job.

**The block model:**

```python
@dataclass(frozen=True)
class Block:
    id: str          # '/page/11/Table/5' — fixup match key AND page source
    block_type: str  # 'Text' | 'Table' | 'ListGroup' | 'SectionHeader' | ...
    text: str        # html reduced to plain text by extract.py
    bbox: tuple[float, float, float, float]
    page: int        # physical index, parsed from `id`
```

`page` is parsed from the `/page/N/` prefix of `id` — **never** from
marker's own `page` field, which is an internal id whose values look like
page numbers and are not (physical 0 → `'7'`, 1 → `'512'`; `§ S1.6`, and a
tabulated Dead end). Parse it in `physical_page_from_id(block_id)` so the
mistake has exactly one place it could be made.

**The sort** — `sort_reading_order(blocks, page_width)`, per `§ S7.2`,
applied per page:

1. A block is **full-width** when its width ≥ 60% of page width.
2. Walk blocks in `y0` order. A full-width block flushes the current band
   and is emitted alone; everything else accumulates into the band.
3. Within a band, split by bbox x-centre against the page midline; emit
   left column top-to-bottom, then right.

Page dimensions come from `page_info[N].bbox` in marker's output (396×612
pt for this book), so no new dependency and no new data.

**The known residual, and a check worth running before "fixing" it.**
`§ S7.3`'s one remaining failure is physical page 17: a boxed callout whose
`SectionHeader` is 41% of page width while its body is 89%, so the body
triggers a band break and the heading does not. **But `SectionHeader`
blocks are dropped from the corpus entirely** (spec Part 2 step 6), and the
breadcrumb comes from the footer chapter, not from headings. So verify
first: re-score the oracle counting only `Text`/`Table`/`ListGroup` order.
If page 17's defect lives entirely in a block type that never reaches a
chunk, it is cosmetic for M7.2 and the sort ships at 15/16 with the finding
recorded. If body blocks are misordered too, implement the
`SectionHeader`-binding refinement `§ S7.3` describes. Record which it was.

**Attribution** — pure, string-in:

```python
def parse_footer_line(line: str) -> tuple[int | None, str | None]:
    """Parse '[<digits>, <CHAPTER>]' from one running-footer candidate."""
```

Per `§ S1.8`, check the **first two and last two** non-empty lines of a
page: the footer alternates verso/recto, and a tail-only check loses two
pages. The function takes strings, not a PDF — `pypdfium2`'s file I/O stays
out of the unit test, the same way `extract.py` and `embed.py` do (spec
Testing Summary).

Attribution consumes `page_chapters: dict[int, str]` (physical index →
chapter) and `page_offset` from `system.json` (Pre-flight 6).

**`ingestion/tests/test_chunk.py`** — this part's assertions:

1. The sort recovers left-then-right order on a synthetic two-column page.
2. The sort leaves an already-correct single-column page unchanged.
3. A full-width block flushes the band and stands alone between the columns
   above and below it.
4. `physical_page_from_id` parses `/page/11/Table/5` → `11`, and raises on
   a malformed id rather than returning a plausible wrong number.
5. `parse_footer_line` extracts page and chapter from synthetic footer
   strings in both verso and recto forms, and returns `(None, None)` for a
   line that isn't a footer.

**`.github/workflows/ci.yml`** — a third job alongside `backend` and
`frontend`:

```yaml
  ingestion:
    name: Ingestion (pytest)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip
      - name: Install dev dependencies
        run: pip install -r ingestion/requirements-dev.txt
      - name: Unit tests
        run: pytest ingestion/tests/
```

`requirements-dev.txt`, never `requirements.txt`. If `pytest
ingestion/tests/` fails on a missing `tiktoken`, the lazy-import constraint
was violated somewhere — fix the import, do not add the package.

**`ingestion/tests/` is a sibling of `pipeline/`**, deliberately departing
from `CLAUDE.md`'s adjacent-tests convention: that convention is written
for the TypeScript apps, and a top-level `tests/` package is the pytest
idiom (spec Part 1). Note it in the PR description so the divergence reads
as intentional.

**Review gate.**

- `pytest ingestion/tests/` green in a clean venv with **only**
  `requirements-dev.txt` installed. This is the check that proves
  hermeticity, and it is easy to pass accidentally in a venv that already
  has the full requirements.
- Push the branch; confirm the `ingestion` job runs and passes on GitHub.
- **Re-run `§ S6.2`'s numbered-header oracle** over Part 1's saved `chunks`
  JSON, before and after the sort. Expect 8/16 → 15/16. Record both numbers
  and the page-17 finding (above) in the PR description — this is the one
  objectively scoreable claim in the whole milestone.

Commit.

## Part 3 — Block merge into chunks

The rest of `chunk.py`: sorted, attributed blocks → `Chunk` objects ready
to embed. Reviewed against synthetic fixtures plus an eyeball over Part 1's
real extraction.

**Files:** `ingestion/pipeline/chunk.py` (extend), `ingestion/tests/test_chunk.py`
(extend), `ingestion/mothership/system.json` (new, Pre-flight 6).

```python
@dataclass(frozen=True)
class Chunk:
    content: str            # breadcrumb line + body
    section_path: list[str] # chapter-level only; [] when unresolved
    source: str             # 'Mothership Player's Survival Guide p.34'
    page: int | None        # printed page number, offset-corrected

def chunk_blocks(
    blocks: list[Block],
    *,
    page_chapters: dict[int, str],
    source_label: str,
    page_offset: int = 1,
    drop_pages: frozenset[int] = frozenset(),   # Pre-flight 7 — empty here
    target_tokens: int = 400,
    overlap_tokens: tuple[int, int] = (50, 100),
    count_tokens: Callable[[str], int] | None = None,
) -> list[Chunk]:
```

Behavior:

- **Keep `Text`, `Table`, `ListGroup`; drop `SectionHeader`, `PageHeader`,
  `PageFooter`, `Picture`, `PictureGroup`** (spec Part 2 step 6). Dropping
  by block type rather than by regex is one of the reasons `chunks` beat
  `markdown` as an output format.
- Merge in sorted order toward `target_tokens`.
- **A chapter change forces a boundary** regardless of token count. Chapter
  is the one reliable structural signal this book has — it is the analogue
  of the heading boundary the original design wanted.
- **A `Table` block is never split.** A table that alone exceeds
  `target_tokens` becomes its own oversized chunk. Half a panic table is
  worse than a long chunk, and tables are the most mechanically
  load-bearing content in the book.
- Non-table runs over target split at block boundaries first, and only
  within a block at paragraph boundaries — never mid-sentence.
- **Every chunk's `content` opens with a breadcrumb line** built from the
  footer chapter (Pre-flight 5).
- **Adjacent chunks from the same chapter overlap by 50–100 tokens; chunks
  from different chapters do not. Measure overlap on the body, not on
  `content`** — the breadcrumb is byte-identical across every chunk in a
  chapter, so an overlap check computed over `content` counts the prefix
  and passes for the wrong reason. This is the easiest bug in this part to
  ship green.
- **Footer-less pages** (physical 0, 1, 2, 10, 43 — 5, not 8; pages 4/41/42
  are a separate settled exclusion that M7.2 does *not* implement, see
  Pre-flight 7) produce a chunk with `section_path: []`, no breadcrumb, and
  a `source` carrying the page number alone. This is the spec's stated
  placeholder, not a decision about the right fallback (spec's "Fallback
  chapter attribution for footer-less pages" deferral). Keep it a one-line
  policy so M7.5's lever 5 can change it without restructuring.
- `count_tokens` defaults to a lazily built tiktoken encoder (Pre-flight 1).

**Tests added:**

6. A chapter change forces a boundary even well under `target_tokens`.
7. An oversized non-table run splits at block/paragraph boundaries, never
   mid-sentence.
8. Overlap between adjacent same-chapter chunks is within 50–100 tokens,
   **measured on the body**; cross-chapter neighbours have zero overlap.
9. A `Table` block is never split, even when it alone exceeds the target.
10. Chunks carry the correct footer-derived `source` and chapter-level
    `section_path` — not marker's `page` or `section_hierarchy`.
11. `page` is offset-corrected (`physical + 1`); a block on a page missing
    from `page_chapters` still produces a chunk rather than raising.
12. A continuation chunk opens with the same breadcrumb as its first half.
13. Dropped block types never appear in any chunk's content.

**Review gate.** `pytest` green (still `requirements-dev.txt` only). Then
run `chunk_blocks` over Part 1's saved real extraction — no marker re-run
needed — and eyeball:

- chunk count near the measured 65 (`§ S11.1`) — **not** the spec's
  original 100–400, which Done When 2 now corrects;
- chapter paths matching the 27 real chapter names in `§ S1.8`;
- no chunk that is a split table, and none that is a breadcrumb with an
  empty body;
- spot-read three multi-column body pages end to end and confirm the prose
  reads forwards. Part 2's oracle covers ordering on 16 pages; this covers
  whether merging preserved it.

Record the chunk count in the PR description. Commit.

## Part 4 — Hash verification, extraction, fixups, and the `--dry-run` CLI

The input half: PDF → typed blocks + page chapters → patched blocks →
chunks. Ends at a working `python ingest.py … --dry-run`, which is Done
When 5 and half of Done When 6, before a byte goes to Voyage.

**`ingestion/pipeline/hash.py`** — SHA-256 the PDF, compare against
`ingestion/<system>/hashes/<edition>.txt`. Format is one line, `<hash>
<filename>`; read only the hash. Mismatch warns and proceeds — never
blocks. Missing hash file warns and proceeds (a Phase 2 system with no
recorded edition is not an error). No `--require-hash`; the spec defers it
explicitly.

**`ingestion/mothership/hashes/mothership-psg-1e.txt`** — generated from
Alex's reference PDF. macOS ships `shasum -a 256`, not GNU `sha256sum`;
the README gives both. **Strip the absolute path from the filename column
before committing** — the file should record a bare filename, not Alex's
home-directory layout.

**`ingestion/pipeline/extract.py`** — two passes, returning the two things
`chunk_blocks` needs.

*Pass 1, marker:*

```
marker_single <pdf> --output_dir <tmp> --output_format chunks \
  --disable_ocr --disable_image_extraction
```

`--disable_ocr` is not optional on a stock install — marker's default path
dies with `SpawnError: llama-server binary not found` (`§ S1.2`). **Guard
it:** with no usable text layer, `--disable_ocr` silently yields near-empty
blocks, so check total extracted text against a floor and fail loudly
naming OCR as the likely cause rather than emitting three chunks. Reduce
each block's `html` to plain text, keeping tables legible.

*Pass 2, footers:* read the running footer with `pypdfium2` to build
`page_chapters: dict[int, str]` and confirm the offset, using Part 2's pure
`parse_footer_line` over the first two and last two non-empty lines of each
page. **Log how many pages resolved** — 36/44 on the PSG, and a sharp drop
on a future PDF is the signal the heuristic stopped applying. Marker's own
`PageFooter` blocks are a tabulated Dead end: it detects them and emits
them empty.

Clean up the temp directory on success *and* failure. Marker failure →
exit `2`.

**`ingestion/requirements.txt`** — add `pypdfium2==<resolved>`. It arrives
transitively via marker today, but pass 2 imports it directly, and a direct
import deserves a direct pin (spec Part 3). Pin what is actually installed
in Alex's venv, not a guess.

**`ingestion/pipeline/fixup.py`** — apply `ingestion/<system>/fixups.json`
against extracted blocks, **matched on block `id`**:

```json
[
  {
    "description": "Panic table extracted with no text (empty Table block)",
    "match": { "block_id": "/page/11/Table/5" },
    "replace_with_template": "panic_table.md"
  }
]
```

This is the schema `docs/decisions.md § Fixup match schema keyed on block
id` settles and `docs/rules-ingestion.md § Step 2` already documents (the
design doc is current here — the working tree carries the correction).
Templates resolve from `ingestion/<system>/templates/`. Mothership's file
is `[]`, so this is plumbing exercised only by the empty case — keep it
correspondingly simple, and **make an entry that matches nothing a loud
warning, not a silent no-op**: a fixup that stops applying after a marker
bump is precisely the failure this file exists to survive.

*Not built here:* the reordering escape hatch (a hand-blessed block order
recorded in `fixups.json`, spec Part 2's boundary note). The sort resolves
15/16 pages and the 16th is understood; building an escape hatch nothing
uses is speculative. Note the intended shape in the README so the option
stays visible.

**`ingestion/ingest.py`** — the full argument surface (all seven flags from
spec Part 2, so the CLI's shape is reviewed once), pipeline steps 1–6
wired, `--dry-run` exiting after chunking with a chunk count and
first-chunk preview. Embedding, the dimension check, and storage are
`NotImplementedError` placeholders landing in Part 5 — **say so explicitly
in the PR description** so a reviewer doesn't read them as an oversight.
Exit codes `1`, `2`, `5` implemented; `3` and `4` land with their code
paths. `ArgumentParser.error` overridden to exit `5` (Pre-flight 2).
`--database-url` defaults from `$DATABASE_URL` (Pre-flight 3 — flag for the
reviewer).

**Review gate.** Against the real PSG:

- `python ingest.py --system mothership --pdf <psg> --dry-run` prints a
  chunk count near 65 and a first-chunk preview, exit `0` (Done When 5).
- A deliberately corrupted hash file warns and still completes;
  `--skip-hash-check` warns and skips verification (Done When 6).
- A nonexistent `--pdf` exits `1`; a bogus flag exits `5`; `--system` with
  no matching directory gives a clear error, not a traceback.
- Footer resolution logs 36/44.
- No temp directory survives a successful run.

Commit.

## Part 5 — Embedding, the dimension guard, storage, and the first real seed

The part that spends money and writes rows. Everything before it was
rehearsal.

**`ingestion/pipeline/embed.py`** — `voyageai.Client().embed(texts,
model=…, input_type="document")`. Batch even though a PSG-sized book fits
in one call (spec Part 2 step 7): the endpoint caps at 1,000 texts, and
batching now means not revisiting this for a larger rulebook. **Chunk order
must be preserved across batch boundaries** — the embedding at index *i*
must belong to chunk *i*, and a reordering bug here produces an index that
looks healthy and returns nonsense. Non-transient Voyage errors → exit `3`.

**Dimension check** — before deleting or inserting anything: read

mistake (`docs/decisions.md § Embedding model`), and **the ordering matters
as much as the check** — running it after the `DELETE` trades a caught bug
for an emptied index.

**`ingestion/pipeline/store.py`** — psycopg, one transaction:

1. `SELECT id, embedding_dim FROM game_system WHERE slug = %s` — no row →

2. `DELETE FROM rules_chunk WHERE system_id = %s` (Done When 4).
3. Insert one row per chunk: `source`, `section_path` (a Python list maps
   to `text[]` natively under psycopg 3), `content`, `embedding`. Never
   NULL on `embedding`. Use `executemany`/`copy`, not per-row round trips.
4. Commit.
5. `REINDEX INDEX rules_chunk_embedding_idx;` after the commit, logged
   (Pre-flight 4).

Database errors → exit `4`.

**`ingest.py`** — replace the Part 4 placeholders; wire exit codes `3` and

## Part 6 — Query preprocessing for `rules_lookup`

Spec Part 7. **TypeScript, in `apps/zoltar-be`** — a different stack and
lifecycle from Parts 2–5, kept visibly separate for the same reason M7 and
M7.2 were split at all. Sequenced after the seed because its manual
verification wants a real corpus, and before Part 7 because the harness's
`--no-preprocess` flag exists to measure this.

This is the largest retrieval-quality effect measured in the whole
investigation — larger than the FTS-vs-embeddings choice itself
(`docs/decisions.md § Query preprocessing for rules_lookup promoted from
optional to critical path`, `§ S4`, `§ S5.3`).

**Files:**

- `src/rules/query-preprocess.ts` + `.spec.ts` — new, pure.
- `src/rules/rules.repository.ts` — one new method.
- `src/rules/rules-lookup.service.ts` — wire it in.
- `src/session/session.telemetry.ts` — one optional field (below).

**The mechanism** (spec 7.1):

1. Tokenize with `to_tsvector('english', query)` — the same lexeme approach
   every corpus measurement used (`§ S3.6`, `§ S8`, `§ S9`), so
   "is this term high-frequency" is measured the way "is this term in the
   corpus" was.
2. Per lexeme, compute document frequency within `rules_chunk` for the
   active `system_id`.
3. Drop lexemes above the threshold.
4. **Rebuild the query from surviving original words, not surviving
   lexemes.** The lexeme decides survival; the original word gets embedded.
   `"perceiv notic environ"` is not natural language and is not what any
   measured improvement came from — every gain in `§ S4`/`§ S5.3` came from
   trimming a real sentence to its distinctive words.
5. If fewer than the floor would survive, keep the least-frequent remaining
   words. An empty query is worse than an unprocessed one.

**Step 4 is the implementation crux, and it needs the token→lexeme
mapping.** `ts_debug('english', $query)` returns one row per token carrying
both the original `token` text and its `lexemes`, which is exactly the
mapping step 4 needs; `to_tsvector` alone discards it. One SQL statement
does tokenization and frequency together:

```sql
WITH tokens AS (
  SELECT ordinality AS pos, token, lexemes
  FROM ts_debug('english', $1) WITH ORDINALITY
  WHERE array_length(lexemes, 1) > 0
),
total AS (SELECT count(*)::float AS n FROM rules_chunk WHERE system_id = $2)
SELECT t.pos, t.token, t.lexemes[1] AS lexeme,
       (SELECT count(*) FROM rules_chunk c
         WHERE c.system_id = $2
           AND to_tsvector('english', c.content) @@ plainto_tsquery('english', t.lexemes[1])
       )::float / NULLIF((SELECT n FROM total), 0) AS df
FROM tokens t;
```

Exact shape is the implementation's call — `ILIKE` counting is an
acceptable alternative (spec 7.2) — but **the repository returns
`{position, word, lexeme, documentFrequency}` and the decision logic lives
in a pure TypeScript function with injected frequencies.** That is what
makes it testable without a database, matching `CLAUDE.md`'s "prefer thin
integration tests over heavily mocked unit tests" by keeping the SQL in a
repository the integration spec exercises and the logic in a pure function
the unit spec does.

**Threshold and floor** (spec 7.3): drop lexemes present in more than
**40%** of the active system's chunks, floor of **2** surviving words.
Both are *proposed starting values, not measured ones*. Export them as
named constants from `query-preprocess.ts` (`DEFAULT_DF_THRESHOLD = 0.4`,
`MIN_SURVIVING_WORDS = 2`) rather than env vars: M7.5 sweeps them through
Part 7's harness flags, not by restarting the server, and an env var
implies an operator knob nobody should be turning. Flag the env-var
alternative for the reviewer.

**Cases that must not break:**

- **An empty index** (zero chunks for the system) — every frequency is
  `0/0`. Preprocessing must be a no-op, not a divide-by-zero and not a
  query trimmed to nothing. This is the state on any fresh database,
  including CI's.
- **An all-high-frequency query** — the floor keeps the two least-frequent
  words (spec 7.4, Done When 11).
- **A single-word query** — below the floor already; pass through
  untouched.
- **Latency** — this adds table scans to the turn hot path. Voyage's round
  trip is ~98% of the budget (`§ S5.4`) so a few hundred rows don't
  compete, but log the preprocessing duration alongside the lookup so the
  Phase 3 concern (spec's deferral entry) has data when it arrives.

**Telemetry — one small addition, recommended.** `RulesLookupRecord`
(`src/session/session.telemetry.ts:45-51`) records `query`. Add
`preprocessedQuery?: string`. It lands in `adventure_telemetry.payload`
(JSONB — no migration), and without it neither playtest review nor M7.5 can
tell from telemetry *why* a lookup missed: whether the Warden asked badly
or preprocessing trimmed the wrong word. Additive and optional, so existing
rows stay readable. Check `scripts/playtest-review.render.ts` for whether
the lookup section should surface it. Flag as an addition beyond the spec.

**Tests** (spec 7.4): a synthetic frequency map plus a verbose query,
asserting high-frequency words drop and distinctive ones survive; the floor
holds on an all-high-frequency query; word order and original spelling are
preserved in the rebuilt query; the empty-index no-op. Plus a repository
integration spec (`.spec-int.ts`) for the SQL against a seeded test corpus,
following `rules.repository.spec-int.ts`.

**Review gate.** `tsc --noEmit` clean, `npm test --workspace zoltar-be`
green. Against the Part 5 index: run the probe with a deliberately verbose
query and confirm a real high-document-frequency term is dropped while the
distinctive terms survive (Done When 11) — the three recorded queries in
`§ S3.6` are the obvious material. No Voyage-level measurement here; Part 8
is what actually answers whether this helps. Commit.

## Part 7 — Retrieval eval harness

Spec Part 8. **TypeScript, alongside the existing `eval:*` family.** This is
the deliverable that makes M7.2 hand M7.5 a ruler rather than a hunch, and
it is what makes deferring the re-baseline safe rather than merely
postponed (`docs/decisions.md § Rules ingestion pipeline and retrieval
quality are separate milestones`).

It goes through `RulesLookupService`'s real path — real `input_type:
'query'` embedding, real pgvector SQL, real `limit` semantics, and now real
preprocessing. A reimplementation would let a divergence between ingestion
and runtime hide, which is the exact failure `docs/decisions.md § Embedding
model` already got bitten by once.

### 7.1 What this part exists to measure

**`rules_lookup` has no similarity floor.** `lookup()` returns whatever
`findByCosineSimilarity` gives back, and the SQL is `ORDER BY … LIMIT n`
unconditionally (`rules.repository.ts:44-53`). On an empty index that is
harmless. On a *populated* one the Warden receives three chunks for every
question, including the 130-of-344 out-of-corpus queries `§ S9.4` measured
as concept-absent — questions the PSG genuinely cannot answer. A
confidently irrelevant chunk is worse than nothing, because the empty path
degrades gracefully and this one does not.

This part produces the distributions M7.5's floor decision consumes. It
does **not** add a floor. Note that the spec's `> 0.5` (Done When 3) is an
unmeasured guess; do not promote it to a constant in code.

### 7.2 Fixture format

`apps/zoltar-be/eval/retrieval-fixtures/mothership.jsonl` — one JSON object
per line, **deliberately not under `eval/fixtures/`**.
`computeCorpusVersion` hashes every `.json` file in that directory
(`eval/corpus-version.ts:29-33`), so a retrieval fixture landing there would
bump the Warden `corpusVersion` and trigger `eval:compare`'s cross-corpus
warning on unrelated runs. JSONL gives a second layer of protection — the
glob is `.json` — but the directory separation is the real one; do not rely
on the extension.

```json
{"id":"rq-001","system":"mothership","query":"perception check looking around environment, noticing details","queryStyle":"warden-observed","expectedPages":[17],"expectedChapter":"STAT CHECKS & SAVES","answerable":true,"sourceTag":"UNSURFACED-CHECK","source":"sampled from turn03 fixture family","notes":""}
```

**Label by page, not by chunk id.** This decides whether the fixture set
survives M7.5 at all. Chunk ids are regenerated every ingestion (`DELETE` +
re-`INSERT` against `gen_random_uuid()`), so an id-labeled set dies at the
first re-chunk — exactly when it is needed. Page numbers are stable across
chunking changes, and Part 4's footer work is what makes them reliable in
`source`. Scoring is "did any returned chunk's `source` cite an expected
page?"

**`queryStyle` is load-bearing, not decoration.** The spec's 8.2 example
omits it, but `roadmap.md` M7.5 and the M7.5 spec's Part 1 both require
separate targets for `authored` and `warden-observed`, and averaging them
hides the actionable finding: an index that scores well on tidy questions
and badly on real Warden phrasing. Carry both, tagged, and report
separately.

**`expectedPages` is an array** — a topic can span pages; recall counts a
hit if **any** listed page appears in top-K, not all.
**`answerable: false` pairs with `expectedPages: []`.** `sourceTag` is the
M7.4 failure-mode tag the query was sampled from, and drives 8.5's
per-tag rollup; `source` is free-text provenance, unused by scoring.

**Field naming deviates from the spec's snake_case example** —
`expected_pages` → `expectedPages`, etc. — to match
`eval/fixture.schema.ts` and every other TypeScript artifact in the repo.
Small, deliberate; flag it for the reviewer.

Fixtures are queries and page numbers, no rules text, so they belong in
version control under the same posture as the fixup files
(`docs/rules-ingestion.md § Licensing Posture`).

### 7.3 Scoring

Deterministic, no judge, no Anthropic call anywhere in the loop — that is
what makes it cheap enough to run on every chunking change, and the
sharpest difference from the M7.4 harness.

- **recall@3** and **recall@5** over *answerable* fixtures — 3 is
  `rules_lookup`'s default `limit`, 5 its schema maximum
  (`session.schema.ts:110`). The Warden usually gets 3.
- **MRR** over the answerable set — recall says a right chunk was in there;
  MRR says whether it was first or third.
- **Top-1 similarity distribution, split by `answerable`.** The gap between
  those two distributions *is* the floor. If they overlap, the honest
  conclusion is that no threshold separates them yet — which is a finding
  (`§ S5.5`'s three-point observation becoming a real sample).
- **Per-`queryStyle` and per-`sourceTag` breakdowns** of each of the above,
  so a change that helps combat queries and hurts investigation queries is
  visible rather than averaged away (spec 8.5).
- **Applicability reported with every rate** — answerable fixtures scored,
  unanswerable excluded from the denominator, both counts printed. Same
  discipline as `docs/decisions.md § Applicability is reported alongside
  every rate`.

### 7.4 Shape

- `apps/zoltar-be/eval/retrieval/fixture.schema.ts` — Zod, mirroring
  `eval/fixture.schema.ts`. **Fail closed:** `expectedPages` and
  `answerable` must be present and typed; an unedited stub with `null`
  placeholders is a load error, never a silently-scored fixture. Same
  convention `capture-fixture` uses for `applies: false, TODO reason`.
- `apps/zoltar-be/eval/retrieval/loader.ts` — JSONL reader, duplicate-`id`
  detection, `--system` filter.
- `apps/zoltar-be/eval/retrieval/score.ts` — pure. This is where the real
  test value is.
- `apps/zoltar-be/eval/retrieval/report.ts` — markdown, in the spirit of
  `eval:report`.
- `apps/zoltar-be/scripts/retrieval-eval.ts` + `.core.ts`, following the
  established CLI split. Plain `tsx` — construct `VoyageService` via
  `envOnlyConfigService()` and `RulesRepository` over a `pg` Pool, the way
  `eval-replay.ts` avoids the `@swc-node/register` requirement.
- `apps/zoltar-be/scripts/sample-retrieval-fixtures.ts` — the stub
  generator (used in Part 8, built here). Reads the eval-run JSON in
  `~/projects/unicorn-artifacts`, extracts distinct `rules_lookup` query
  strings tagged by the M7.4 fixture they came from, **caps at 5 per
  fixture tag** rather than sampling by raw frequency — the direct fix for
  the combat skew `§ S8.1` measured (one query string appears 181 times;
  read distinct, not invocation-weighted). Emits stubs with `query`,

- `Taskfile.yml` — `eval:retrieval`, inside the existing family so it is

  `task eval:retrieval [-- --system <slug>] [--fixtures <path>] [--no-preprocess] [--df-threshold <n>]`

- **Delete `apps/zoltar-be/scripts/one-off/rules-lookup-probe.ts`.** Two

**Tests:** scorer unit tests (recall@K boundaries, MRR with the hit at rank
