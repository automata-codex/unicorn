# M7.2 — Rules Ingestion Pipeline: Implementation Plan

Multipart implementation plan for
`../specs/zoltar/012-m7.2-rules-ingestion.md`. Each plan part is sized for
a manual code review and a single commit. Pause after each part for review
before starting the next.

**Status.**

- Part 1 landed 2026-08-04. Its review gate materially changed Parts 2, 3,
  and the documentation work. Empirical record in
  `docs/rules-extraction-findings.md` — **read that before touching Part 2.**
- **Scope changed 2026-08-04 (deliberate deviation from the spec).** A
  retrieval eval harness is added as Part 5, and the spec's Part 6 — the
  eval re-baseline and the dedicated playtest — moves out of this milestone
  into **M7.5 — Rules Retrieval Quality**. Rationale in
  [Scope change](#scope-change-what-moved-to-m75) below. The spec is the
  authority on what M7.2 *was*; this plan is the authority on what is being
  built, and the roadmap gets reconciled in Part 6.

Ordering is roughly dependency order, with one deliberate departure: the
chunker lands before the extractor (Part 2 before Part 3) even though the
pipeline runs them the other way round. The chunker is the only module in
this milestone with a real algorithm, the only one covered by an automated
test, and the only one that must stay importable without marker's model
weights. Getting it reviewed on its own, against a synthetic fixture, is
worth more than matching runtime order — and Part 1 already produced the
real `chunks` JSON to develop it against, so the extractor's absence costs
nothing.

**Part 1** (scaffolding + pins) → **Part 2** (chunker + CI) → **Part 3**
(hash/extract/fixup + `--dry-run` CLI) → **Part 4** (embed/store + full
run) → **Part 5** (retrieval eval harness) → **Part 6** (docs +
`task ingest`).

Parts 1–4 are the Python pipeline. Part 5 is TypeScript, and is the ruler
this milestone hands to M7.5. Part 6 is prose.

## Scope change — what moved to M7.5

The spec's Part 6 defines two post-ingestion validation activities: an eval
re-baseline (6.1) and a dedicated playtest (6.2). Both move to M7.5.

**Why.** M7.5 exists to iterate on chunking — potentially as far as a
hand-curated Markdown of the rules text with a sane heading hierarchy — and
that work changes what is in the index. The re-baseline costs roughly 300
Warden turns plus judge calls (2 models × 15 fixtures × N=10). Buying it
against an index we intend to re-chunk means buying it twice. This is the
same reasoning behind the `roll_dice` deferral already decided, except
worse: that was a confound, this is waste.

**What makes deferring safe** is Part 5. The retrieval harness reads index
quality for the price of a few Voyage calls and no Anthropic spend at all,
so "is this index worth baselining?" gets answered long before anyone pays
to baseline it. Without Part 5 the deferral would just be postponement.

**What this milestone therefore no longer claims.** M7.2 ends with a
populated index and a way to measure it — not with evidence that the Warden
is better off. That evidence is M7.5's, and the three `docs/decisions.md`
entries waiting on it stay open one milestone longer. Part 6 restates them
so they point at M7.5 rather than reading as pending against a milestone
that no longer contains the measurement.

**Spec Done When items affected:** 9 (re-baseline) and 10 (playtest) move
to M7.5. Items 1–8 remain this milestone's, and Part 5 adds a measurement
the spec's Done When list does not anticipate.

### Decisions the spec leaves to implementation

**1. Page provenance: `source` is the only citation the Warden ever
sees.** `findByCosineSimilarity` returns `source` and `content` only —
`section_path` is stored but never surfaced (`rules.repository.ts:45-53`,
`rules-lookup.service.ts:36-42`). So `source` has to carry the whole
citation, and the design doc's example format is `"Mothership Player's
Survival Guide p.34"`.

**Resolved empirically in Part 1 — see `docs/rules-extraction-findings.md`
§ S1.8.** Page provenance comes from the PDF's **running footer**, read via
`pypdfium2` in a pass alongside marker, not from any marker output field.
Every obvious alternative was tried and failed; they are tabulated as dead
ends in the findings log and must not be re-attempted without new
information. In summary: the Markdown carries no page delimiters (16 sparse
`<span id="page-N">` anchors over 44 pages), and the chunks JSON's `page`
field is an internal id whose values look like page numbers and are not
(physical 0 → `7`, 1 → `512`, 2 → `75`).

The footer yields `printed_page == physical_index + 1`, which held on every
page that parsed and resolves 36 of 44 pages. It also yields the true
chapter name, which is what makes decision 6 work.

**2. `chunk.py` must not import `tiktoken` at module scope.** The spec
says the CI test "touches no network." `tiktoken` downloads its BPE files
from the network on first encoder construction, so a module-level
`tiktoken.get_encoding(...)` would make the test network-dependent and
flaky in CI. Resolution: the chunking entry point takes an injectable
`count_tokens: Callable[[str], int]` whose default is a lazily
constructed tiktoken encoder, built on first call, not at import.
`test_chunk.py` passes a trivial deterministic counter instead. The
~400-token target is a retrieval heuristic with no hard boundary (spec
Part 3), so testing the splitting logic against an approximate counter
loses nothing. This is also what satisfies the spec's "the chunking
module must not import anything from `extract.py` or `embed.py` at module
scope" — same constraint, one wider.

Consequence: CI installs a small `ingestion/requirements-dev.txt`
(`pytest` only, pinned), never the full `requirements.txt`. Marker's
extraction models must not land on a CI runner.

**3. `argparse` collides with the spec's exit codes.** `argparse` exits
`2` on a usage error; the spec assigns `2` to "marker extraction failed"
and `5` to "invalid arguments." Resolution: subclass `ArgumentParser` and
override `error()` (and `exit()`) to exit `5`. Without this, a typo in a
flag reports as an extraction failure.

**4. `--database-url` should also read `$DATABASE_URL`.** The spec lists
it as required. Proposed minor deviation: keep it required *in effect*,
but let it default from the `DATABASE_URL` environment variable exactly
as `--voyage-api-key` defaults from `VOYAGE_API_KEY`. The spec's own
usage example (4.2) already exports `DATABASE_URL` and then passes it
back in as a flag, which is pure ceremony. Missing from both flag and env
→ exit `5`. Flag this in the Part 3 PR description; revert to
strictly-required if the reviewer prefers the spec's literal reading.

**5. ivfflat index quality after a bulk load — the one real database
gotcha in this milestone.** `rules_chunk_embedding_idx` is an ivfflat
index created in `V7__rules_index.sql:19-21`, at migration time, against
an empty table. ivfflat computes its cluster centroids at build time from
the rows present; built on zero rows there are no meaningful centroids,
and pgvector's own guidance is to create an ivfflat index *after* the
table has data. Every re-ingestion (`DELETE` + re-`INSERT`) also churns
the index against stale centroids.

Resolution: **`store.py` runs `REINDEX INDEX rules_chunk_embedding_idx;`
after the insert commits**, as a final step, logged. Ingestion is an
offline job — the lock is free. This is also the first thing to try if
Part 4's sanity query returns nothing or returns obviously irrelevant
chunks despite a healthy row count: the failure mode of a degenerate
ivfflat index is poor or empty recall, not an error. Note that
`ORDER BY embedding <=> ...` remains *correct* under a bad index only
because Postgres may fall back to a sequential scan; do not rely on
that.

**6. Continuation chunks lose their heading — fix it in the embedding,
not the tool result.** Chunking produces chunks that begin mid-section,
whose text may contain no heading at all: a continuation of the panic rules
can easily never say "panic." Such a chunk is retrieved on vector
similarity alone and arrives at the Warden as orphaned prose.

Resolution: **`chunk.py` prepends a breadcrumb line — `PANIC CHECKS` — to
every chunk's `content`.** Because it lands in `content` it is part of the
embedded text *and* part of what the Warden reads, so it improves retrieval
rather than only presentation. This is the standard contextual-chunk-header
technique, and it is the reason to prefer it over the alternative below.

**Build the breadcrumb from the footer chapter, not from marker's
`section_hierarchy`** (`docs/rules-extraction-findings.md § S1.7`). That
field is structurally complete but semantically wrong — it records "the last
header seen at each visual level," so on the PSG's scrambled multi-column
spreads siblings become parents (`STEP 5. GAIN STRESS > STEP 6. NOTE TRAUMA
RESPONSE`, `6.1 STARTING CREDITS > D100 TRINKETS`). A breadcrumb built from
that would inject actively wrong context into the embedded text, which is
worse than no breadcrumb at all. The footer chapter is correct where it
resolves; marker's immediate `SectionHeader` may be appended as a second
level where it is trustworthy, but the chapter alone is the reliable floor.

The alternative — surfacing `section_path` through the tool result — is
deliberately *not* in scope by default. It would be small (`section_path`
into the SELECT and `RulesChunkMatch` in `rules.repository.ts:34-59`, one
line in `rules-lookup.service.ts`, one in `rulesLookupOutputSchema` at
`session.schema.ts:113`, plus fixture updates in the two existing specs —
roughly 20 lines across 6 files), and it would *not* change the tool
schema Claude sees, since `session.tools.ts:19` derives the JSON schema
from `rulesLookupInputSchema` only and the output shape is undeclared. But
it is presentation-only: by tool-result time the embedding is already
computed, so it cannot fix the retrieval half. Take it up only if Part 3
finds that marker *does* supply page numbers — in that case `source` reads
`"…PSG p.34"` and the hierarchy is genuinely absent from the payload. If
marker does not, decision 1's fallback already puts the section path into
`source`, and adding the field would write the same string twice.

Either change alters what reaches the Warden on turns that get index hits,
so **both must land before the re-baseline**, which is now M7.5's. This is
a weaker constraint than the `roll_dice` one: they affect only turns that
call `rules_lookup` and receive results, which is precisely the population
the re-baseline studies. But adding either afterwards leaves it unmeasured
until the next baseline. Neither is in M7.2's scope.

### Resolved with Alex — the `roll_dice` fields do not ride along

The deferred `roll_dice` schema fields (`rollType`, `gatedByRollId`,
`actingEntityId`) stay deferred. The re-baseline measures the index change
alone, and the project accepts paying for a third full baseline whenever
those fields land. Both the decision and the re-baseline now sit in M7.5;

stay deferred` needs rewriting when Part 6's documentation lands, because
it currently predicts the fields will ride along with an M7.2 re-baseline
that is not happening.

## Part 2 — Block-based chunking, its unit test, and the CI job

The algorithmic heart of the milestone and the only part with automated
coverage. Reviewed against a synthetic fixture, with a manual eyeball
against Part 1's real extraction output.

**This part was redesigned after Part 1.** The original plan — and
`docs/rules-ingestion.md § Step 4`, and the spec's Part 2 step 4 — all
specify chunking on `###` heading boundaries walked out of marker's
Markdown. That is not implementable: the PSG's Markdown has 10 `###`
headings in 44 pages, and marker's heading levels track font size rather
than hierarchy (`docs/rules-extraction-findings.md § S1.5`). Chunking on
`###` would produce ~10 chunks against a 100–400 target, with nonsense
ancestry. The design doc is wrong here, not just the plan; correcting it is
listed under Part 6.

**The replacement: chunk over marker's typed blocks.** `--output_format
chunks` gives 674 blocks — 409 of them Text/Table/ListGroup — each with a
`block_type`, `html`, and a resolvable physical page index
(`docs/rules-extraction-findings.md § S1.6`). Merging those toward a
~400-token target lands plausibly inside the spec's expected 100–400 chunk
range, keeps tables intact as HTML instead of flattening them, and lets
`PageHeader`/`PageFooter`/`Picture` noise be dropped by type rather than by
regex.

**`ingestion/pipeline/chunk.py`.** Target shape — note it now takes a list
of already-parsed blocks, not a Markdown string, which keeps it just as
pure and just as testable:

```python
@dataclass(frozen=True)
class Block:
    block_type: str        # 'Text' | 'Table' | 'ListGroup' | ...
    text: str              # html already reduced to plain text by extract.py
    page: int              # physical page index, 0-based
    heading: str | None    # marker's immediate SectionHeader, if trustworthy

@dataclass(frozen=True)
class Chunk:
    content: str           # breadcrumb line + body
    section_path: list[str]
    page: int | None       # printed page number, already offset-corrected

def chunk_blocks(
    blocks: list[Block],
    *,
    page_chapters: dict[int, str],      # physical index -> footer chapter
    page_offset: int = 1,               # printed = physical + offset
    target_tokens: int = 400,
    overlap_tokens: tuple[int, int] = (50, 100),
    count_tokens: Callable[[str], int] | None = None,
) -> list[Chunk]:
    ...
```

Behavior, in the order the test asserts it:

- Content blocks are merged in order toward `target_tokens`. A chunk
  boundary is forced whenever the footer chapter changes — chapter is the
  one reliable structural signal this book has, so it is the analogue of
  the heading boundary the original design wanted.
- A `Table` block is never split. Tables are the densest and most
  mechanically load-bearing content in a rules PDF, and half a panic table
  is worse than an oversized chunk. A table that alone exceeds
  `target_tokens` becomes its own chunk and is allowed to be over.
- Non-table runs over `target_tokens` split at block boundaries first, and
  only within a block's text at paragraph boundaries, never mid-sentence.
- **Every chunk's `content` opens with a breadcrumb line** built from
  `section_path` — per Pre-flight decision 6, sourced from the footer
  chapter, *not* from marker's `section_hierarchy`.
- Adjacent chunks from the same chapter overlap by 50–100 tokens; chunks
  from different chapters do not. **Measure overlap on the body, not on
  the prefixed content** — the breadcrumb is byte-identical across every
  chunk in a chapter, so an overlap check computed over `content` would
  count the prefix and pass for the wrong reason. This is the easiest bug
  in this part to ship green.
- `page` is the *printed* page number (`physical + page_offset`), so that
  `source` can be built without every caller re-deriving the offset.
- Pages absent from `page_chapters` (the 8 unresolved ones,
  `docs/rules-extraction-findings.md § S1.8`) fall back to
  `Block.heading` if present, else a `section_path` of `[]` — and must not
  crash. Which of drop / fall back / synthetic-chapter is right is an open
  question in the findings log; the code should make it a one-line policy
  change rather than a structural assumption.
- `count_tokens` defaults to a lazily built tiktoken encoder. No
  `import tiktoken` at module scope; no import from `extract.py`,
  `embed.py`, `store.py`, or `fixup.py` at all.

**`ingestion/tests/test_chunk.py`** — against a synthetic list of `Block`s
with known structure plus a deterministic injected `count_tokens`. The
spec's four Testing Summary assertions, translated to the block model:

1. Chunk boundaries respect chapter boundaries (was: `###` headings).
2. An oversized run splits at block/paragraph boundaries without breaking
   mid-sentence.
3. Overlap between adjacent chunks from the same chapter is within the
   50–100 token band, measured on the body.
4. Chunks carry correct `section_path`.

Plus three the redesign makes necessary:

5. A `Table` block is never split, even when it exceeds `target_tokens`.
6. `page` is offset-corrected (`physical + 1`), and a block on a page
   missing from `page_chapters` still produces a chunk rather than raising.
7. A continuation chunk opens with the same breadcrumb as its first half.

Note the spec's Testing Summary describes this test as running "against a
small synthetic Markdown string." That wording is superseded; the intent —
pure Python, no marker, no Voyage, no database, runs in CI — is unchanged
and is what actually matters.

`ingestion/tests/` is a sibling of `pipeline/`, deliberately departing
from `CLAUDE.md`'s adjacent-tests convention — that convention is written
for the TypeScript apps, and a top-level `tests/` package is the pytest
idiom (spec Part 1). Note this in the PR description so the divergence
reads as intentional in review.

**`.github/workflows/ci.yml`** — a third job alongside `backend` and
`frontend`:

```yaml
  ingestion:
    name: Ingestion (pytest)
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: pip
      - name: Install dev dependencies
        run: pip install -r ingestion/requirements-dev.txt
      - name: Unit tests
        run: pytest ingestion/tests/
```

`requirements-dev.txt`, not `requirements.txt` — installing marker in CI
would defeat the point (spec Testing Summary). If `pytest ingestion/tests/`
fails on a missing `tiktoken`, Pre-flight decision 2's lazy-import
constraint has been violated somewhere; fix the import, do not add
`tiktoken` to the CI install.

**Review gate.** `pytest ingestion/tests/` green locally with only
`requirements-dev.txt` installed in a clean venv — this is the check that
actually proves the hermeticity claim, and it is easy to pass accidentally
in a venv that already has the full requirements. Push the branch and
confirm the `ingestion` job runs and passes on GitHub. Manually run
`chunk_blocks` over Part 1's real PSG extraction (the saved `chunks` JSON,

## Part 3 — Hash verification, extraction, fixups, and the `--dry-run` CLI

The input half of the pipeline: PDF → typed blocks + page chapters →
patched blocks → chunks. Ends with a working `python ingest.py ...
--dry-run`, which is Done When 5 and half of Done When 6, before a single
byte goes to Voyage. Deliberately structured so the expensive-and-external
half (Part 4) is reviewed separately from the cheap-and-local half.

**`ingestion/pipeline/hash.py`** — SHA-256 the input PDF, compare against
`ingestion/<system>/hashes/<edition>.txt`. File format is one line,
`<hash>  <filename>`; read only the hash portion (spec 4.1). Mismatch
warns and proceeds — never blocks. Missing hash file warns and proceeds
(a Phase 2 system with no recorded edition is not an error). No
`--require-hash`; the spec explicitly defers it.

**`ingestion/mothership/hashes/mothership-psg-1e.txt`** — generated from
Alex's reference PDF:

```bash
shasum -a 256 mothership_players_survival_guide.pdf > \
  ingestion/mothership/hashes/mothership-psg-1e.txt
```

(macOS ships `shasum -a 256`, not GNU `sha256sum`; the README should give
both.) Strip the absolute path from the filename column before committing
— the hash file should record a bare filename, not Alex's home directory
layout.

**`ingestion/pipeline/extract.py`** — two passes over the PDF, returning
the two things `chunk_blocks` needs.

*Pass 1, marker.* Invoke into a temp directory with the flags Part 1
established:

```
marker_single <pdf> --output_dir <tmp> --output_format chunks \
  --disable_ocr --disable_image_extraction
```

`--disable_ocr` is not optional on a stock install — marker's default path
dies with `SpawnError: llama-server binary not found`
(`docs/rules-extraction-findings.md § S1.2`). Guard it: if the PDF has no
usable text layer, `--disable_ocr` will silently yield near-empty blocks,
so check total extracted text against a floor and fail loudly with a
message naming OCR as the likely cause rather than emitting three chunks.
Reduce each block's `html` to plain text, keeping tables legible; drop
`PageHeader`, `PageFooter`, `Picture`, `PictureGroup`. Derive each block's
physical page from the `/page/N/` prefix of its `id` — **not** from the
`page` field, which is an internal id (`§ S1.6`).

*Pass 2, footers.* Read the running footer with `pypdfium2` to build
`page_chapters: dict[int, str]` and confirm the page offset. Parse the
first two and last two non-empty lines of each page for
`[<digits>, <CHAPTER>]` where `<digits> == physical + 1` — checking both
ends matters, the footer alternates verso/recto and a tail-only check
loses two pages (`§ S1.8`). Log how many pages resolved; on the PSG it is
36/44, and a sharp drop on some future PDF is the signal that this
heuristic has stopped applying to it.

*Do not* subshell out to `sha256sum`-style tools or re-open the PDF a third
time; `pypdfium2` is already a marker dependency and Part 1 pinned it
explicitly for this use.

Clean up the temp directory on both success and failure. Marker failure →
exit `2`.

**`ingestion/requirements.txt`** — add `pypdfium2==5.10.1`. It arrives
transitively via marker today, but pass 2 imports it directly, and a direct
import deserves a direct pin.

**`ingestion/pipeline/fixup.py`** — apply `ingestion/<system>/fixups.json`
against the extracted **blocks**, per the entry format in
`docs/rules-ingestion.md § Step 2` (`description`, `match.section`,
`match.contains`, `replace_with_template`). Mothership's file is `[]` in
M7.2, so this is plumbing exercised only by the empty case — keep it
correspondingly simple, and make an entry that matches nothing a loud
warning rather than a silent no-op, since a fixup that stops applying
after a marker bump is exactly the failure this file exists to survive.

## Part 4 — Embedding, the dimension guard, storage, and the first real seed

The part that spends money and writes rows. Everything before it was
rehearsal.

**`ingestion/pipeline/embed.py`** — `voyageai.Client().embed(texts,
model=..., input_type="document")`. Batch even though a PSG-sized book
fits in one call (spec Part 2 step 5): the endpoint caps at 1,000 texts
per request, and batching now means the code does not need revisiting for
a larger rulebook. Chunk order must be preserved across batch boundaries
— the embedding at index *i* must belong to chunk *i*, and a reordering
bug here produces an index that looks healthy and returns nonsense.
Non-transient Voyage errors → exit `3`.

**Dimension check** — before deleting or inserting anything: read
`game_system.embedding_dim` for the target slug, assert every returned
vector's length equals it. Mismatch → exit `3` with a message naming both
the configured model and both numbers. This is the guard that would have
caught the `voyage-3-lite` 512-dimension mistake (`docs/decisions.md §
Embedding model`); the ordering matters as much as the check — running it
after the `DELETE` would trade a caught bug for an emptied index.

**`ingestion/pipeline/store.py`** — psycopg, one transaction:

1. `SELECT id, embedding_dim FROM game_system WHERE slug = %s` — no row →
   clear error, exit `4`.
2. `DELETE FROM rules_chunk WHERE system_id = %s` (idempotency, Done
   When 4).
3. Insert one row per chunk: `source`, `section_path` (a Python list maps
   to `text[]` natively under psycopg 3), `content`, `embedding`. Never
   NULL on `embedding` — see Pre-flight. Use `executemany`/`copy` rather
   than a per-row round trip.
4. Commit.
5. `REINDEX INDEX rules_chunk_embedding_idx;` after the commit, logged
   (Pre-flight decision 5).

Database errors → exit `4`.

**`ingest.py`** — replace the Part 3 placeholders; wire exit codes `3` and
`4`. Log a one-line summary on success: chunk count, model, dimension,
system, elapsed time.

**Sanity check (Done When 3).** Add
`apps/zoltar-be/scripts/one-off/rules-lookup-probe.ts`, following the

## Part 5 — Retrieval eval harness

Not in the spec. Added because M7.5 cannot iterate on chunking without a
way to score it, and because Part 4's review gate is otherwise one
hand-typed question. This is the deliverable that makes M7.2 hand M7.5 a
ruler rather than a hunch.

TypeScript, not Python: what matters is what the Warden actually receives,
which means going through `RulesLookupService` — the real `input_type:
'query'` embedding, the real pgvector SQL, the real `limit` semantics. A
Python reimplementation of the query path would let a divergence between
ingestion and runtime hide, which is the precise failure
`docs/decisions.md § Embedding model` already got bitten by once.

### 5.1 The finding this part exists to address

**`rules_lookup` has no similarity floor.** `RulesLookupService.lookup()`
returns whatever `findByCosineSimilarity` gives back
(`rules-lookup.service.ts:29-43`), and the SQL has no threshold clause
(`rules.repository.ts:44-53`) — it is `ORDER BY … LIMIT n`, unconditionally.

On an empty index that is harmless: zero rows, and M7 wired the
empty-result fallback correctly. On a *populated* index it means the Warden
receives three chunks for every question, including questions the PSG
cannot answer. A confidently irrelevant chunk is worse than nothing,
because the empty path degrades gracefully and this one does not.

Deriving that floor from measurement rather than guessing it is a primary
output of this part. Note the spec's `> 0.5` (Done When 3) is an unmeasured
guess; do not promote it to a constant in code without evidence.

### 5.2 Fixture format

Fixtures live in **`apps/zoltar-be/eval/retrieval/fixtures/`** — deliberately
*not* under `eval/fixtures/`. `computeCorpusVersion` hashes every `.json`
file in that directory (`eval/corpus-version.ts:29-33`), so a retrieval
fixture landing there would change the Warden corpus version and trigger
`eval:compare`'s cross-corpus warning on every future comparison. The
function is non-recursive and files-only, so a subdirectory would technically
be skipped — do not rely on that; a later change to make it recursive would
be a silent trap.

Fixtures are queries and page numbers, no rules text, so they belong in
version control under the same posture as the fixup files
(`docs/rules-ingestion.md § Licensing Posture`).

```json
{
  "id": "panic-effect",
  "query": "what happens when a character panics",
  "queryStyle": "authored",
  "expectedPages": [21],
  "expectedChapter": "PANIC CHECKS",
  "answerable": true
}
```

**Label by page, not by chunk id.** This is the decision that determines
whether the fixture set survives M7.5 at all. Chunk ids are regenerated on
every ingestion — Part 4's idempotency strategy is `DELETE` then re-`INSERT`
against `gen_random_uuid()` — so an id-labeled fixture set dies at the first
re-chunk, which is exactly when it is needed. Page numbers are stable across
chunking changes, and Part 3's footer work is what makes them reliable in
`source`. Scoring is therefore "did any returned chunk's `source` cite an
expected page?"

**`queryStyle` is load-bearing, not decoration.** The only real
`rules_lookup` queries ever recorded are three, preserved in
`apps/zoltar-be/playtest-reports/` after the dev database was wiped:

```
"perception check looking around environment, noticing details"
"saving throws stats how to roll checks"
"skill checks INT intellect saves diagnosis repair"
```

All three are keyword-stuffed and fuzzy — nothing like a crisp human
question. A fixture set of only well-formed questions would measure a query
distribution the Warden does not produce. Carry both styles, tagged, and
report their rates separately: an index that scores well on `authored` and
badly on `warden-observed` is the actionable finding, and a single blended
number hides it. Seed `warden-observed` with those three; add more from
telemetry as playtests accumulate.

**Include unanswerable fixtures** (`answerable: false`) — starship combat,
character advancement, anything outside the PSG. Without them recall looks
excellent and teaches nothing about false confidence, and there is no way to
derive the floor from 5.1. These are not filler; they are half the point.

### 5.3 Scoring

Deterministic, no judge, no Anthropic call — this is what makes the harness
cheap enough to run on every chunking change, and it is the sharpest
difference from the M7.4 harness.

- **recall@3** and **recall@5** — 3 is `rules_lookup`'s default `limit`, 5
  its schema maximum (`session.schema.ts:110`). Score both; the Warden
  usually gets 3.
- **MRR** over the answerable set — recall says a right chunk was in there,
  MRR says whether it was first or third.
- **Top-1 similarity distribution, split by `answerable`.** The gap between
  those two distributions *is* the floor. If they overlap, no threshold
  separates them and the honest conclusion is that chunking has to improve
  before a floor is worth adding.
- Per-`queryStyle` breakdown of each of the above.

Report every rate with its denominator, matching the applicability
discipline in `docs/decisions.md § Applicability is reported alongside every
rate`.

### 5.4 Shape

- `apps/zoltar-be/eval/retrieval/` — fixture schema (Zod, mirroring
  `eval/fixture.schema.ts`), loader, scorer. The scorer is pure and gets
  unit tests; that is where the real test value is.
- **Delete `apps/zoltar-be/scripts/one-off/rules-lookup-probe.ts`** from
  Part 4. This harness does its job properly; leaving the probe behind
  means two tools answering the same question at different quality.
- `apps/zoltar-be/scripts/retrieval-eval.ts` + `.core.ts`, following the
  established CLI split. Plain `tsx` is fine — no Nest DI container needed
  if `VoyageService`/`RulesRepository` are constructed directly, matching
  how `eval-replay.ts` avoids the `@swc-node/register` requirement
  (`Taskfile.yml:60-63`).
- `Taskfile.yml` — `eval:retrieval`. Name it inside the existing `eval:*`
  family so it is discoverable, and make the description say plainly that
  it makes Voyage calls but no Anthropic calls.
- **Run artifacts to `$ZOLTAR_EVAL_ROOT/retrieval-runs/`**, matching
  `eval/runs/paths.ts`. Reason: a useful failure report wants the returned
  chunk text to show *what* came back instead of the right answer, and chunk
  text is rules text that must not land in this repo. Sending runs to the
  artifacts repo sidesteps it; keeping fixtures in-repo is fine because they
  contain no rules text.
- **Index provenance in the run manifest** — marker version, chunking
  parameters, embed model, chunk count, ingestion timestamp. A retrieval
  score is only comparable against the same index build; this is the
  analogue of `corpusVersion`/`harnessVersion`, and omitting it reproduces
  exactly the cross-run confusion those were introduced to prevent.

### 5.5 Fixture authoring

Alex's job, and the real cost of this part — the code is small. Target
~25–30 fixtures: roughly two per chapter across the 27 chapters in
`docs/rules-extraction-findings.md § S1.8`, the three `warden-observed`
queries above, and 5–8 unanswerable ones. In a 44-page book the page labels
are quick; the questions are the thinking.

Do not generate the questions from the chunks. That is circular — it would
measure whether the index can retrieve what the index contains. Author from
the book, or from telemetry.

**Tests:** scorer unit tests (recall@k boundaries, MRR with the hit at rank
1/3/6, unanswerable handling, empty results), fixture schema tests (valid
plus representative invalid shapes) — matching `CLAUDE.md`'s Zod-schema
testing standard. No integration test against a live index; the run itself
is the integration test.

**Review gate.** `tsc --noEmit` clean, unit tests green. A full
`task eval:retrieval` run against Part 4's populated index produces a report
with per-style recall@3/@5, MRR, and both similarity distributions. Record
the headline numbers in the PR description — they are M7.5's baseline, and
the first honest answer to "is this index any good." If recall@3 on the
`authored` set is poor, that is a finding, not a failure of this part: it is
the measurement working. Commit.

Worth stating here so M7.5's spec starts from it rather than discovering
it late.

**Closed:**

- **Do the `roll_dice` schema fields land with the re-baseline?** No —
  decided with Alex. Index change alone; a third baseline gets paid for
  later. Now inherited by M7.5 along with the re-baseline itself.
- **Should `section_path` be exposed to the Warden?** Solved in Python
  instead, as a breadcrumb prefix inside the embedded `content`, which
  fixes retrieval rather than only presentation. See Pre-flight decision 6.
- **Does marker expose page boundaries?** Yes, but not through any field
  that looks like it does. Resolved empirically in Part 1: page number
  comes from the PDF's running footer via `pypdfium2`, `printed =
  physical + 1`. The Markdown anchors, the chunks JSON `page` field, and
  marker's own `PageFooter` blocks are all dead ends — tabulated as such
  in `docs/rules-extraction-findings.md`.
- **Is the optional `sectionPath` tool-result change worth doing?** It was
  conditional on pages being available, and they are. Deferred to M7.5:
  it changes what reaches the Warden, so it has to land before the
  re-baseline, and the re-baseline is now M7.5's. Part 5's per-fixture
  output is better evidence for the decision than guessing from `source`
  strings anyway.
- **How do we evaluate rules lookup at all?** Part 5. Page-labeled
  fixtures, deterministic scoring, no judge, both query styles, and
  unanswerable questions to derive the similarity floor.
- **Does chunking iteration belong in M7.2?** No — M7.5. M7.2 ships the
  pipeline and the ruler; M7.5 uses the ruler.
