# M7.1 — Playtest Review Tooling: Implementation Plan

Multipart implementation plan for `docs/specs/zoltar/m7.1-playtest-review-tooling.md`.
Each plan part is sized for a manual code review and a single commit. Pause
after each part for review before starting the next.

Terminology note: the M7.1 spec itself is organized into six spec Parts
(Part 1 … Part 6). Plan parts map onto spec parts but do not number 1:1 —
where a plan part cross-references the spec it is written as "spec Part N".

## Pre-flight corrections to the spec

Small documentation/path drift that the spec assumes. Resolve up front, by
the plan part that touches each surface — no dedicated commit:

- **Warden prompt source location.** Spec §1.2 says
  `WARDEN_SYSTEM_PROMPT_MOTHERSHIP` lives "somewhere under
  `apps/zoltar-be/src/session/wardens/` per the M7 spec". In the current
  tree it lives at `apps/zoltar-be/src/session/session.prompt.ts:20` as a
  string-array joined with `.join('\n')` on line 84. The constant is used
  on line 214 of the same file. Plan Part 1 reads from that location and
  removes the const + the `.join('\n')` assembly there. The `session/wardens/`
  directory does not exist; skip the "remove the old dir if empty" step.
- **`join('\n')` byte-identity gotcha.** The const is an array joined with
  `'\n'` and carries no trailing newline. `mothership-m7.txt` must match
  the joined string exactly — no trailing newline, LF line endings. The
  sha256 comparison in Plan Part 1 must be run against the `.join('\n')`
  result, not against the source file containing the array literal.
- **Migration number.** Spec §3 calls the new views migration
  "`V<N>__review_views.sql`". The next free slot on `main` is **V13** —
  V12 is `V12__dice_request.sql` from M7. Plan Part 3 uses
  `V13__review_views.sql`.
- **Doc filename casing.** The spec references `docs/ENVIRONMENTS.md`,
  `docs/DECISIONS.md`, and `docs/schema.md`. The repository has them
  lowercase: `docs/environments.md`, `docs/decisions.md`, `docs/schema.md`.
  All plan parts that touch docs use the lowercase names.
- **Test-file naming.** Integration tests in this repo use `.spec-int.ts`
  (matching existing files like `session.service.spec-int.ts`). Unit tests
  use `.spec.ts`. Plan parts follow the existing convention.

## Part 1 — `WardensModule`, prompt file, SessionService integration (spec Part 1)

Foundational. Lands the module, the flat-file prompt, and the
`SessionService` rewire. Telemetry capture of the prompt `{filename, hash}`
is held back to Part 2 to keep this part focused.

**Create the module skeleton:**

- `apps/zoltar-be/src/wardens/wardens.module.ts` — `@Module` exporting
  `WardenPromptsService`.
- `apps/zoltar-be/src/wardens/warden-prompts.service.ts` — implements
  `OnModuleInit`. Surface per spec §1.3: `getSelected`, `getAll`,
  `getByFilename`. Uses `ConfigService` to read
  `WARDEN_PROMPT_OVERRIDE_MOTHERSHIP`.
- `apps/zoltar-be/src/wardens/prompt-paths.ts` — exports `promptsDir()`,
  `hashPromptText(text)` (8-char sha256 hex prefix), and
  `rereadPromptFile(system, filename)` (per spec §1.3).
  `promptsDir()` must resolve to `src/wardens/prompts/` at both runtime
  and test time — not `dist/`. Use `path.resolve(__dirname, 'prompts')`
  with the understanding that NestJS compiles to `dist/` during build;
  verify the CLI path resolution (Part 4) and `tsx` direct execution
  both see the same directory. If not, introduce an explicit `src/`
  anchor (e.g. walk up to the `apps/zoltar-be/src` root via filesystem
  markers) and document the reasoning in the file header.

**Migrate the prompt text:**

- Extract the array contents of `WARDEN_SYSTEM_PROMPT_MOTHERSHIP` from
  `apps/zoltar-be/src/session/session.prompt.ts:20-84` and write
  `apps/zoltar-be/src/wardens/prompts/mothership-m7.txt` containing the
  `join('\n')`-equivalent bytes: LF line endings, no trailing newline, no
  BOM.
- Record the sha256 of the joined const string *before* deleting it (run
  a one-off `node -e` computing the digest) and the sha256 of the new
  file. Both must match. Record both values in the commit message.
- Delete the const from `session.prompt.ts`. Update line 214 to consume
  the prompt text via a parameter (wired up below) instead of the direct
  import.

**Wire `SessionService`:**

- `apps/zoltar-be/src/session/session.module.ts` — add
  `WardensModule` to `imports`.
- `apps/zoltar-be/src/session/session.service.ts` — inject
  `WardenPromptsService`. Call `getSelected('mothership')` once per
  `sendMessage` invocation. The resulting `{text}` is threaded into
  `buildSessionRequest` via a new parameter so `session.prompt.ts` stops
  owning the prompt source. Keep the selected `{filename, hash}`
  available for Part 2's telemetry population — temporarily unused this
  part, or thread it forward so Part 2 only touches the telemetry call
  site.
- `buildSessionRequest` signature gains `wardenPromptText: string`.
  `systemBlocks[1].text` reads from that parameter instead of the const.
  The `cache_control: ephemeral` marker on the block is unchanged.

**Tests:**

- `apps/zoltar-be/src/wardens/warden-prompts.service.spec.ts` — covers
  discovery, hash stability, one-byte-diff hash divergence, default
  selection by version sort, override honored, missing override throws,
  empty prompts dir throws on `getSelected`. Uses a temp fixture
  directory built in `beforeEach` so tests don't depend on the shipped
  `mothership-m7.txt`.
- `apps/zoltar-be/src/wardens/prompt-paths.spec.ts` — `rereadPromptFile`
  returns the current on-disk text and hash (prove in-place edits
  detectable); returns null for missing filename.
- `apps/zoltar-be/src/session/session.prompt.spec.ts` — existing tests
  referencing `WARDEN_SYSTEM_PROMPT_MOTHERSHIP` are updated to pass a
  fixture string through the new `wardenPromptText` parameter.
- `apps/zoltar-be/src/session/session.service.spec.ts` — inject a
  `WardenPromptsService` stub returning a canned `WardenPromptFile`; any
  existing assertions about the prompt body continue to hold.

**Documentation updates (this part):**

- `docs/environments.md` — add `WARDEN_PROMPT_OVERRIDE_MOTHERSHIP` entry
  alongside the existing Voyage variables. Document the dev-loop side-by-
  side use case and the "not for production self-hosted" caveat.

**Review gate.** `tsc --noEmit` clean on `zoltar-be`. Unit tests green.
A manual curl against a running backend produces an identical turn to
pre-part 1 behaviour (same prompt bytes reaching Claude). Commit.

## Part 3 — SQL review views (spec Part 3)

Pure additive migration plus docs. No code wiring yet — Part 4 consumes
the views.

- `infra/db/migrations/V13__review_views.sql` — contains `DROP VIEW IF
  EXISTS … CASCADE;` then `CREATE OR REPLACE VIEW` for all three views
  (`turn_log`, `state_history`, `correction_log`) in one file, in that
  order. SQL bodies per spec §§3.1–3.3.

**`correction_log` join-direction check (Open Question 1 in the spec):**

Before writing the view body, read `apps/zoltar-be/src/session/session.
events.ts` to confirm how `superseded_by` is persisted — the spec says
M6 sets `superseded_by` on the *original* `gm_response` row pointing at
the correction, but the spec's view SQL is written as if the correction
row carries the pointer. Choose the join predicate that matches the
actual persisted direction:

- If `superseded_by` is on the original (M7 spec's claim): `JOIN
  game_event orig ON orig.adventure_id = c.adventure_id AND
  orig.superseded_by = c.id`.
- If `superseded_by` is on the correction: spec's predicate as written
  (`orig.id = c.superseded_by`).

Record the direction observed in the migration file's leading comment so
a future reader doesn't have to re-derive it.

**Run the migration:**

- `task flyway:migrate` — with an empty dev DB at minimum, to prove the
  migration applies cleanly. A second run of `task flyway:clean &&
  flyway:migrate` proves idempotency.
- Sanity-query each view in `psql` against seeded data (a recent M7 turn
  is sufficient): `SELECT * FROM turn_log LIMIT 5;` etc. Non-empty
  output is sufficient validation here; Part 4's tests exercise the
  full shape.

**Documentation updates (this part):**

- `docs/schema.md` — new "Review Views" section covering all three
  views, each with: one-line purpose, the columns it surfaces, and a
  note that views are not modelled in Drizzle (query via the `sql`
  template).

**Review gate.** Migration applies on a clean DB and idempotently on a
dirty one. All three views return rows against a seeded M7 adventure.
Join direction in `correction_log` is verified against
`session.events.ts`. Commit.

## Part 4 — CLI review script (spec Part 4)

The largest single plan part. Self-contained — no other production code
changes, only additions under `apps/zoltar-be/scripts/`.

**Directory + script scaffold:**

- `apps/zoltar-be/scripts/` — new directory.
- `apps/zoltar-be/scripts/playtest-review.ts` — entry point. Arg parsing
  (positional `<adventure-id>`, `--stdout`, `--output <path>`), DB pool
  opened via the existing `db.provider` pattern reusing `DATABASE_URL`.
  Closes the pool cleanly on exit. No NestJS boot — per spec §4.4, it's
  a thin CLI: `Pool`, Drizzle, `fs`, markdown formatter, and the
  `prompt-paths.ts` helpers from Part 1.
- `.gitignore` — add `apps/zoltar-be/playtest-reports/`.
- `Taskfile.yml` — new `playtest:review` task wrapping
  `npx tsx apps/zoltar-be/scripts/playtest-review.ts` with `--`
  arg-forwarding. Mirror the invocation style of whatever existing
  `task` wrappers use argument forwarding today.

**Queries and data shaping:**

- Three SQL calls total per spec §4.4: `turn_log`, `correction_log`, and
  a one-row header lookup joining `adventure`, `campaign`, and
  `game_system`.
- Shape a per-turn struct that rolls `diceRolls`, `rulesLookups`,
  `applied`, `thresholds`, `notes`, token counts, `toolLoopIterations`,
  and the correction (if any) into a single render-friendly object.
- Distinct `{filename, hash}` pairs collected across all turns drive
  both the header "Warden prompts used" list and the "Prompt texts"
  appendix.

**Markdown rendering (per spec §4.2):**

- Header, per-turn sections, correction events, summary, prompt texts
  appendix — in that order.
- Zero-result `rules_lookup` entries carry a `⚠️` marker per spec §4.2.
  Open Question 2 in the spec prefers emoji unless the reviewer
  objects; proceed with emoji and flip to `[!]`/`WARN:` only if Part 7
  sanity-check calls it out.
- `diceRolls` rendered in sequence order, labelled `[player]` or
  `[system]`, with notation/purpose/results/modifier/total. `[player]`
  rolls include their `requestId`.
- `applied` state changes flattened to bulleted diffs, not raw JSON.
- `gmUpdates.notes` on its own line when non-empty.
- Corrections render twice: inline in the turn where they fired, and in
  the top-level "Correction events" section.
- Default output path
  `apps/zoltar-be/playtest-reports/<adventure-id>-<yyyymmdd-hhmmss>.md`
  — create parent directory on first run.

**Prompt text appendix and hash handling (per spec §4.3):**

For each distinct `{filename, hash}` pair seen in telemetry, call
`rereadPromptFile` from `prompt-paths.ts`:

- Current hash matches → embed text verbatim.
- Current hash differs → embed current text with a `Prompt hash
  mismatch.` warning block naming both hashes.
- File missing → warning block, no text embed.

Per-turn Warden prompt references in the body always show the *recorded*
hash. Only the appendix surfaces the current on-disk state.

**Exit codes:**

- Adventure id doesn't exist → non-zero with a clear message.
- Adventure has zero turns → non-zero with a clear message.

**Tests:**

- `apps/zoltar-be/scripts/playtest-review.spec-int.ts` (integration; needs
  the test DB + views migration). Fixture builder seeds an adventure
  with 3 turns, a correction on turn 2, one zero-result rules lookup on
  turn 1, one system-generated roll on turn 3. Assert the generated
  markdown matches a stored snapshot.
- Additional cases in the same file: mismatched on-disk hash triggers
  the mismatch warning block; deleted prompt file triggers the deletion
  warning block; adventure id with zero turns exits non-zero. The
  on-disk-hash cases point `promptsDir()` at a test-specific fixture
  directory via an env var or a module override, so the shipped
  `mothership-m7.txt` is untouched.

**Review gate.** Integration tests green including snapshot match.
Running `task playtest:review -- <real-adventure-id>` against a dev DB
produces a readable markdown file in
`apps/zoltar-be/playtest-reports/`. The file embeds `mothership-m7.txt`
verbatim in the appendix, hash matches header. Commit.

## Part 5 — Save synthesis script (spec Part 5.1–5.2)

Splitting spec Part 5 into save (this part) and load (Part 6) so each
commit stays scoped to a single transactional surface.

- `apps/zoltar-be/src/synthesis/synthesis-export.schema.ts` — exports
  `SynthesisExport` interface and a Zod schema validating it. Schema is
  defined here (not in the script) so Part 6's loader can import it.
  Shape per spec §5.1 (`version: 1`, `exportedAt`, `source`, `system`,
  `gmContext`, `campaignState`, `adventure`).
- `apps/zoltar-be/scripts/save-synthesis.ts` — entry point. Positional
  `<adventure-id>`, optional `--output <path>`, `--stdout`. Same DB
  pool/Drizzle pattern as the review CLI; no NestJS boot.
- Preconditions per spec §5.2: adventure must exist; adventure must have
  zero `gm_response` events (checked with the single query in §5.2).
  Clean non-zero exit with the review-CLI pointer message if either
  fails.
- Load `campaign`, `gm_context` (by campaign_id), `campaign_state` (by
  campaign_id). Serialize verbatim — no normalization of the blobs.
- Default output:
  `apps/zoltar-be/synthesis-saves/<campaign-slug>-<yyyymmdd-hhmmss>.json`.
  Campaign slug: lowercase, underscores, alphanumerics only, truncated
  to 40 chars.
- `.gitignore` — add `apps/zoltar-be/synthesis-saves/`.
- `Taskfile.yml` — new `playtest:save-synthesis` task wrapping the
  script.

**Tests:**

- `apps/zoltar-be/scripts/save-synthesis.spec-int.ts`:
  - Zero-turn adventure produces a `SynthesisExport` whose
    `gmContext.blob` and `campaignState.data` deep-equal the source rows
    after JSON round-trip.
  - Any `gm_response` event in `game_events` → non-zero exit with a
    clear error message containing the review-CLI pointer.
  - `source.campaignId` / `source.adventureId` equal source UUIDs (not
    newly generated).

**Review gate.** Integration tests green. Manually saving a real
zero-turn adventure produces a JSON file that visibly contains the
opening narration and the character's starting resource pools. Commit.

## Part 6 — Load synthesis script + round-trip test (spec Part 5.3)

Depends on Part 5's Zod schema. Completes the synthesis feature.

- `apps/zoltar-be/scripts/load-synthesis.ts` — entry point. Positional
  `<file.json>`, optional `--name <string>`.
- Zod-parse the file; reject unknown versions and shape mismatches with
  clear non-zero exits.
- Validate `system.slug === 'mothership'`; error otherwise.
- User lookup per spec §5.3: read `PLAYTEST_LOAD_USER_ID`; if unset,
  SELECT the first user and print a warning naming it; if no users
  exist, fail. (Spec Open Question 4 — lean "acceptable with warning";
  revisit only if Part 7 sanity-check flags it.)
- Single transaction: INSERT new `campaign` (fresh UUID, generated or
  overridden name, `system_id` looked up by slug), new `gm_context`
  (saved schema version + blob, linked to new campaign), new
  `campaign_state` (saved schema version + data, linked to new
  campaign), new `adventure` (fresh UUID, `status = 'ready'`,
  `mode = 'freeform'`, linked to new campaign). Commit.
- Print new adventure id and the paste-ready
  `/campaigns/<id>/adventures/<id>/play` URL.
- Idempotency: loading the same file twice produces two distinct
  campaigns/adventures — intentional per spec §5.3.
- `Taskfile.yml` — new `playtest:load-synthesis` task.

**Tests:**

- `apps/zoltar-be/scripts/load-synthesis.spec-int.ts`:
  - Valid export creates fresh rows in the four tables; blobs/data
    preserved; status/mode correct.
  - Unknown version / malformed file → non-zero exit with clear error.
  - `PLAYTEST_LOAD_USER_ID` unset → first-user fallback + warning
    stdout/stderr capture.
  - Empty `user` table → non-zero exit with clear error.
- `apps/zoltar-be/scripts/save-load-roundtrip.spec-int.ts`:
  - Save zero-turn adventure to a temp file, load it, assert loaded
    adventure's `gm_context.blob` equals source's and
    `campaign_state.data` equals source's. UUIDs differ.

**Documentation updates (this part):**

- `docs/environments.md` — add `PLAYTEST_LOAD_USER_ID` with semantics
  and intended use.

**Review gate.** Integration tests including the round-trip green.
Manual end-to-end: save a zero-turn adventure, load it, hit the printed
`/play` URL in the browser, see the opening narration render. Commit.

## Part 7 — Sanity-check pass + final docs (spec Part 6 + Documentation PR Checklist)

This plan part is the "gate" spec §6 describes, **but only after a real
playtest has been run against the production stack using Parts 1–6.**
If the playtest has not happened yet, pause the plan here until it has.

**Procedure (spec §6):**

1. Run a full Mothership adventure through the production stack. Target
   15–25 turns, exercising dice, rules lookups, at least one correction
   path, one threshold crossing.
2. Generate the report: `task playtest:review -- <adventure-id>`.
3. Read the report end-to-end. For each section: is the information
   pulling its weight? Anything absent that should be present? Anything
   bloating output without earning its place?
4. For each field in `AdventureTelemetryPayload`: does it appear
   somewhere in the report? If not, why is it in the payload?
5. (Recommended) Save the adventure's synthesis *before* the session,
   then load + run a second session with a different
   `WARDEN_PROMPT_OVERRIDE_MOTHERSHIP`. Generate both reports. If
   comparison ergonomics are bad, that's a finding to fix in this part.

**Findings handling:**

- Payload shape changes: update `AdventureTelemetryPayload`, the
  telemetry payload builder, the view SQL if a column references the
  dropped/added path, the CLI renderer, and every test that constructs
  a fixture payload. The payload is `jsonb` — no DB migration needed.
  Document the change in `docs/decisions.md`.
- No shape changes: record an entry in `docs/decisions.md` stating the
  shape was reviewed against a real playtest and held up. Prevents the
  question getting re-opened later without cause.

**Documentation PR checklist (close-out for the milestone):**

Batch the remaining documentation updates here so the rest of the plan
parts stayed tightly scoped:

- `docs/decisions.md` — new entries:
  - "Warden prompt versioning via flat files with hash capture"
    (rationale for file-based over DB-backed `warden_prompt` table).
  - "Playtest review reports are the durable artifact, not the
    database".
  - "Warden prompts live in `apps/zoltar-be/src/wardens/`, not in
    `@uv/game-systems`" (I/O boundary, product-specific coupling,
    build-step friction during iteration).
  - "Save-synthesis requires a zero-turn adventure" (intent boundary
    vs. future session-export).
  - Any payload-shape decisions from the sanity check.
- `docs/roadmap.md` — check off M7.1 items as they land; one-line
  pointer at the spec file.
- `docs/schema.md` — final pass to confirm the Review Views section
  (landed in Part 3) and the `wardenPrompt` telemetry field (landed in
  Part 2) are both described consistently with the final implementation.
- `docs/environments.md` — final pass to confirm both env vars
  (`WARDEN_PROMPT_OVERRIDE_MOTHERSHIP` landed in Part 1,
  `PLAYTEST_LOAD_USER_ID` landed in Part 6) are present and consistent.

**Review gate.** Full `tsc --noEmit` clean on `zoltar-be`; full unit +
integration test sweep green; `docs/decisions.md` carries either a
"payload shape changed" entry plus the code/test updates *or* a
"shape held up" entry with no code changes; `docs/roadmap.md` M7.1
checklist complete. Commit. M7.1 closed.

## Open questions from the spec

Tracked per-plan-part so they resolve as implementation proceeds:

1. **`superseded_by` pointer direction** — resolved in Plan Part 3 by
   reading `session.events.ts` before finalizing the `correction_log`
   view. Direction observed gets a one-line comment in the migration.
2. **Emoji vs. ASCII flags in the report** — proceed with `⚠️` per
   spec default. Flip to `[!]`/`WARN:` only if Part 7 sanity-check
   objects.
3. **Sanity-check scope mandate** — if the first playtest surfaces
   payload fields worth dropping/renaming, those changes are in scope
   for M7.1 and land in Part 7's PR. Accept the scope expansion
   upfront.
4. **`PLAYTEST_LOAD_USER_ID` fallback** — proceed with "fall back to
   first user + print warning". Flip to strict-fail-on-unset only if
   Part 7 sanity-check finds the dev DB regularly has >1 user.
