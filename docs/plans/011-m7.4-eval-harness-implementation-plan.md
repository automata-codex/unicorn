# M7.4 — Warden Eval Harness: Implementation Plan

Multipart implementation plan for
`docs/specs/zoltar/011-m7.4-eval-harness-spec.md`. Each plan part is sized
for a manual code review and a single commit. Pause after each part for
review before starting the next.

**Dependency order:** the fixture type (Part 1) is the shared contract
every other part reads or writes, so it goes first. `capture-fixture`
(Part 2) and the seed-and-execute core (Part 3) both depend only on Part 1,
not on each other — Part 3's tests hand-construct a fixture object rather
than shelling out to `capture-fixture`. Structural checks (Part 4) and
judged checks (Part 5) both depend on Part 3's `TurnExecutionResult` shape.
The report renderer (Part 6) depends only on knowing the result shape
Parts 4/5 produce. The CLI (Part 7) wires 1 through 6 together and is
necessarily last code part. Part 8 (building the real fixture library) is
a data-authoring pass using the finished tool, not new code, and depends on
everything.

**Part 1 → Part 2 → Part 3 → Part 4 → Part 5 → Part 6 → Part 7 → Part 8.**

## Pre-flight corrections and decisions the spec left open

Resolved up front by reading the actual code, so each plan part can just
execute rather than re-derive:

- **The env var is `WARDEN_PROMPT_OVERRIDE_<SYSTEM>`, not the bare
  `WARDEN_PROMPT_OVERRIDE` the spec's invocation example implies.**
  `WardenPromptsService` (`src/wardens/warden-prompts.service.ts`) builds
  the override key as `` `WARDEN_PROMPT_OVERRIDE_${system.toUpperCase()}` ``
  and reads it via `ConfigService`, not `process.env` directly. For
  Mothership this is `WARDEN_PROMPT_OVERRIDE_MOTHERSHIP`. Part 7's CLI
  wiring sets this env var (or passes the equivalent through
  `ConfigService`) from the `--prompt-variant` flag — using the spec's
  literal `WARDEN_PROMPT_OVERRIDE` name would silently no-op. Confirm at
  implementation time whether the override value must be the full filename
  (`mothership-m7-candidate-1.txt`) or the stripped id — read
  `WardenPromptsService`'s comparison logic directly rather than guessing.
- **Candidate prompt files live in the real prompts directory, not a
  separate one.** `WardenPromptsService` loads every `<system>-*.txt` from
  `promptsDir()` (`src/wardens/prompts/`) once at `onModuleInit` and
  matches the override against what it found there. A prompt variant named
  in `--prompt-variant mothership-m7-candidate-1.txt` must already exist in
  `src/wardens/prompts/` before a harness run references it — the harness
  does not deploy prompt files itself. `WARDENS_PROMPTS_DIR` (a second,
  independent override for pointing discovery at a whole different
  directory) exists but is documented in the code as a test-only hook; this
  plan does not use it for eval runs, only the per-system override, to keep
  prompt-variant provenance visible in the same directory as shipped
  prompts.
- **`check` and `rubric` fixture fields are display text and a rubric
  selector, not executable code, and not free-form per fixture.** The
  spec's fixture format types both as bare `string`, but also says
  structural assertions are "one per tag" (the table has exactly one row
  per tag) and judge rubrics are explicitly "one per tag, not one per
  fixture." Reconciling those: the actual checker/rubric function is
  selected by the fixture's `tag` field through a registry (Part 4/5), and
  `check`/`rubric` are:
  - `check` (structural fixtures): free-text description, carried through
    unchanged into the report's "Expected: ..." line. Not parsed, not
    executed. Purely documentation of intent, authored by whoever writes
    the fixture.
  - `rubric` (judged fixtures): a rubric-template identifier, resolved
    against a small in-repo registry (`{HIDDEN-INFO-LEAK: ..., OVER-RESOLUTION:
    ...}`) rather than free text. In practice this will typically just be
    the tag name itself (e.g. `"HIDDEN-INFO-LEAK"`) unless a rubric needs
    versioning later (`"HIDDEN-INFO-LEAK-v2"`) — the registry key space is
    intentionally separate from `FailureModeTag` so a rubric can be revised
    without touching every fixture that references it, but starts 1:1.
  This resolves the spec's literal `string` typing without inventing a new
  DSL: `check` never executes, `rubric` looks up a template, `facts`
  supplies the per-instance interpolation values the template asks for.
- **Scratch adventures run against the real (dev) database, not the
  ephemeral `zoltar_test` database, and make real Anthropic calls.** The
  entire point of the harness is exercising real prompt variants against a
  real model — `zoltar_test` is wiped/truncated by the test suite between
  runs and Anthropic calls are stubbed there by convention
  (`session.service.spec-int.ts`). The harness instead connects via the
  same `DATABASE_URL` the running backend uses, and creates a fully
  self-contained scratch `campaign`/`adventure` per fixture run, name-tagged
  (e.g. `campaign.name = "__eval__${fixture.id}__${runId}"`) so scratch rows
  are identifiable in the DB and never collide with real campaigns. Default
  behavior deletes the scratch campaign (cascades to everything under it)
  after each fixture's assertions are captured; a `--keep-scratch` flag
  skips deletion for post-run manual inspection. This needs to be called
  out prominently in the harness's `--help` output and README — it is the
  one part of this milestone that touches non-ephemeral state and costs
  real API tokens per invocation.
- **`playerInput.type: 'diceResult'` maps to `SessionService.submitDiceResult`,
  not `sendMessage`.** The fixture format's two `playerInput` variants
  correspond to the two turn-entry methods on `SessionService`. Part 3
  branches on `playerInput.type` to call the right one. Confirm
  `submitDiceResult`'s exact argument shape (it takes a resolved dice
  result keyed to a pending `dice_request`, per the survey) at
  implementation time — the scratch adventure must have a matching pending
  `dice_request` row seeded for this path to be exercisable at all, which
  in practice means fixtures using `diceResult` player input need their
  `seededState` captured at a turn boundary where a `dice_request` was
  actually pending (i.e., `capture-fixture`'s target sequence number lands
  right after a turn that issued one).
- **Seeding a scratch adventure reuses `session.service.spec-int.ts`'s
  `seedReadyAdventure()` shape, not a new bespoke sequence.** That helper
  already knows the full row chain a playable adventure needs
  (`game_system` → `campaign` → `user` → `campaign_member` →
  `character_sheet` → `campaign_state` → `adventure` → `gm_context`). Part
  3 factors an equivalent into `eval/harness-runner.ts`, parameterized to
  seed `campaign_state.data` / `gm_context.blob` / `message` rows /
  `pending_canon` rows from the fixture's frozen `seededState` instead of
  hardcoded defaults. `message` and `pending_canon` rows from the fixture
  get their `adventureId` rewritten to the new scratch adventure's id on
  insert — everything else about them (content, `role`, `createdAt`,
  `sequenceNumber` for pending canon) is copied verbatim, even though the
  scratch adventure's own `game_events` sequence numbering starts fresh at
  1 and has no historical continuity with those numbers. That's fine:
  nothing in the assertion set relies on cross-referencing a seeded
  `pending_canon.sequenceNumber` against the scratch adventure's own event
  sequence — the seeded rows exist purely to give the turn under test the
  same "what canon already exists" context the original turn had.
- **The judge call needs its own minimal path to Sonnet 5, separate from
  the Warden's model.** `AnthropicService` backs the Warden's own calls;
  confirm at implementation time whether it already supports a per-call
  model override (in which case Part 5 reuses it with
  `model: 'claude-sonnet-5'`) or is hardcoded to the Warden's model, in
  which case Part 5 adds a small direct-SDK judge-call function instead of
  routing through `AnthropicService`. Either way, no new API key/config is
  needed — same Anthropic credentials, different model string.
- **`vitest.integration.config.ts`'s glob needs `eval/**/*.spec-int.ts`
  added.** Today it globs `src/**/*.spec-int.ts` and
  `scripts/**/*.spec-int.ts`; this milestone's first `*.spec-int.ts` file
  living directly under the new `apps/zoltar-be/eval/` directory (Part 3's
  `harness-runner.spec-int.ts`) won't be picked up otherwise. Add this in
  Part 3, where it first matters.
- **No `npm run eval:harness` or Taskfile entries exist yet.** Both are
  added in Part 7 once there's a working CLI to point them at — adding them
  earlier would just be dead wiring.

## Part 1 — Fixture schema and loader

Foundational; every later part reads or writes this shape. No DB, no CLI,
pure types plus a directory-loader function.

**`apps/zoltar-be/eval/fixture.schema.ts`:**

- `FailureModeTag` — Zod enum of the eight in-scope tags:
  `OUT-OF-ORDER-RESOLUTION`, `SYSTEM-ROLLED-PLAYER-ACTION`,
  `UNAUDITABLE-MAPPING`, `MISSING-CANON-CAPTURE`, `NARRATING-PAST-A-BLOCK`,
  `UNSURFACED-CHECK`, `HIDDEN-INFO-LEAK`, `OVER-RESOLUTION`.
  (`STATUS-FIELD-OVERLOAD` / `SNAPSHOT-GAP` are deliberately absent — not
  just unused, since their presence in the enum would let a future fixture
  silently target an unimplemented checker.)
- `evalFixtureSchema` — Zod schema mirroring the spec's `EvalFixture`
  interface exactly: `id`, `tag`, `sourceAdventureId`, `sourceSequenceNumber`,
  `seededState` (`campaignState`/`gmContextBlob`/`pendingCanon`/`messages`/
  `capturedAt`, all passed through as loosely-typed `unknown`/`Record`
  shapes at this layer — deep validation against `MothershipCampaignState`
  etc. happens when the harness actually seeds a DB with them, in Part 3,
  not here), `playerInput` (`type: 'message' | 'diceResult'`, `content`),
  and a discriminated-union `assertion`:
  `{mode: 'structural', check: string} | {mode: 'judged', rubric: string, facts: Record<string,string>}`.
- Export the inferred TS type `EvalFixture` alongside the schema, same
  pattern as `synthesisExportSchema`/`SynthesisExport`.

**`apps/zoltar-be/eval/fixture-loader.ts`:**

- `loadFixtures(dir: string, opts?: {tags?: FailureModeTag[]}): Promise<EvalFixture[]>` —
  reads every `*.json` in `dir` (non-recursive; fixtures are "one file per
  fixture" per spec, flat directory), `JSON.parse`s and validates each
  against `evalFixtureSchema`, collects parse errors per-file rather than
  throwing on the first bad file (a fixture author's typo in one file
  shouldn't block running the other nineteen). Returns only fixtures
  matching `opts.tags` if given, all fixtures otherwise.
- A `FixtureLoadError` (extends `Error`, carries `filename` + underlying
  Zod issues) for malformed files; the CLI (Part 7) is responsible for
  deciding whether to hard-fail or warn-and-skip — the loader itself always
  reports every error found, never silently drops a bad file.

**Tests (`apps/zoltar-be/eval/fixture.schema.spec.ts`,
`apps/zoltar-be/eval/fixture-loader.spec.ts`):**

- Schema: valid structural fixture, valid judged fixture, missing
  required field, wrong `assertion.mode` discriminant, unknown `tag` value
  (confirms `STATUS-FIELD-OVERLOAD`/`SNAPSHOT-GAP` are rejected).
- Loader: directory with a mix of valid/invalid files — valid ones load,
  invalid ones report errors without crashing the whole load; `tags` filter
  narrows correctly; empty directory returns `[]` without erroring (the
  spec's fixture-count-bar requirement that under-covered tags don't break
  anything).

**Review gate.** `tsc --noEmit` clean. Unit tests green. Commit.

## Part 2 — `capture-fixture` CLI

Depends on Part 1's schema only. Thin wrapper around M7.3's
`reconstructStateAsOfTurn`, matching the existing `scripts/` conventions
(`load-synthesis.ts`, `playtest-review.ts`): `node:util` `parseArgs`, a
local `UsageError`, `*.core.ts`/`*.ts` split, raw `pg.Pool` + `drizzle`
reading `DATABASE_URL` directly.

**`apps/zoltar-be/scripts/capture-fixture.core.ts`:**

- `captureFixture(db, args: {adventureId: string; targetSequenceNumber: number; tag: FailureModeTag; id: string}): Promise<EvalFixture>`:
  calls `reconstructStateAsOfTurn(db, adventureId, targetSequenceNumber)`
  (imported from `src/replay/reconstruct-state.ts`), then assembles an
  `EvalFixture`-shaped object with:
  - `seededState` populated from the reconstruction result plus
    `capturedAt: new Date().toISOString()`.
  - `sourceAdventureId`/`sourceSequenceNumber` set from the CLI args.
  - `playerInput` and `assertion` filled with clearly-marked placeholder
    values (e.g. `content: "TODO: fill in from the source turn's player message"`,
    `check: "TODO"`) — the tool's whole job stops at reconstruction; a
    human fills in the rest by hand per the spec's design.
  - Propagates `ReplayError` from `reconstructStateAsOfTurn` unchanged
    (bad `targetSequenceNumber`, missing turn-0 snapshot) rather than
    wrapping it — the CLI wrapper's `main()` catch already knows how to
    report an `Error`'s message to stderr.

**`apps/zoltar-be/scripts/capture-fixture.ts`:**

- `parseArgs` for the two positionals (`adventure-id`, `target-sequence-number`)
  and the three flags (`--tag`, `--id`, `--output`), matching the spec's
  invocation example exactly. `--tag` validated against `FailureModeTag`
  at the CLI boundary (clear `UsageError` listing valid tags on typo,
  rather than a Zod stack trace).
- Writes the assembled fixture as pretty-printed JSON to `--output`;
  refuses to overwrite an existing file without a `--force` flag (accidental
  re-capture silently clobbering a hand-edited fixture is exactly the
  failure mode the spec's "Out of Scope" section calls out as something
  that must always be a deliberate action, never automatic).
- Standard `main().then(...)` exit-code bottom-of-file pattern.

**Tests (`apps/zoltar-be/scripts/capture-fixture.spec-int.ts`):**

Same style as `reconstruct-state.spec-int.ts` — seed a multi-turn adventure
via direct repository calls (or import the same test helper if
`reconstruct-state.spec-int.ts` exposes one worth reusing; check before
duplicating), then:

- `captureFixture` against a real turn boundary produces an `EvalFixture`
  whose `seededState` matches `reconstructStateAsOfTurn`'s own direct
  output for the same args.
- Invalid `targetSequenceNumber` propagates `ReplayError` through to a
  non-zero CLI exit code.
- `--output` refuses to overwrite an existing file unless `--force` is
  passed (a plain unit-ish test against the CLI wrapper's file-existence
  check, doesn't need the DB).

**Review gate.** `tsc --noEmit` clean. Integration tests green. Manually
run `npx tsx scripts/capture-fixture.ts <a real dev-DB adventure id> <seq> --tag ... --id ... --output /tmp/x.json` and inspect the output file by eye. Commit.

## Part 3 — Scratch-adventure seeding and turn execution core

Depends on Part 1's `EvalFixture` type only (not on Part 2's CLI — this
part's tests hand-construct fixture objects). This is the harness's
execution engine: given a fixture, produce a fully-seeded scratch
adventure, run one real turn through the real `SessionService` under a
given prompt variant, and return everything the checkers need.

**`apps/zoltar-be/eval/harness-runner.ts`:**

- `TurnExecutionResult` type: the post-turn `game_events` rows (ordered),
  the one `adventure_telemetry` row, the post-turn `pending_canon` rows,
  the post-turn `campaign_state.data`, and whatever `SessionService`'s
  return value itself carried (`applied`, `thresholds`, `diceRequests`) —
  this is the shape Parts 4/5's checkers consume, so get it fully fleshed
  out here rather than growing it ad hoc later.
- `seedScratchAdventure(db, fixture: EvalFixture, runId: string): Promise<{adventureId, campaignId, playerUserId}>` —
  the row chain from the pre-flight note (`game_system` → `campaign` →
  `user` → `campaign_member` → `character_sheet` → `campaign_state` →
  `adventure` → `gm_context` → `message` rows → `pending_canon` rows),
  seeded from `fixture.seededState` rather than hardcoded test defaults.
  `campaign.name` tagged `__eval__${fixture.id}__${runId}`.
- `runFixtureTurn(db, sessionService: SessionService, fixture: EvalFixture, seeded: {...}): Promise<TurnExecutionResult>` —
  branches on `fixture.playerInput.type`: `'message'` calls
  `sessionService.sendMessage(...)`, `'diceResult'` calls
  `sessionService.submitDiceResult(...)` (exact arg mapping per the
  pre-flight note); afterward queries `game_events`/`adventure_telemetry`/
  `pending_canon`/`campaign_state` fresh from the DB for the scratch
  adventure (not just whatever `SessionService`'s own return value
  happened to include) so checkers always see the real persisted state.
- `teardownScratchAdventure(db, campaignId): Promise<void>` — deletes the
  scratch `campaign` row; cascading FKs take care of everything under it.
  Not called automatically by `runFixtureTurn` — the CLI (Part 7) owns
  calling this (or not, under `--keep-scratch`) so this module stays a
  pure building block.
- **Real `SessionService` construction, not the test-suite's stub-heavy
  one.** The harness needs a real `AnthropicService` (so a real model call
  happens) and a real `WardenPromptsService` (so the prompt-variant
  override actually takes effect) — but can reuse stubs for `DiceService`/
  `RulesLookupService` only if the fixture's assertion doesn't depend on
  real dice math; check the six structural tags against this before
  assuming stubs are safe (`OUT-OF-ORDER-RESOLUTION` and
  `SYSTEM-ROLLED-PLAYER-ACTION` explicitly care about roll sequencing and
  `roll_source`, which flow through `DiceService` — use the real one). Net
  effect: this part likely just bootstraps the full `SessionModule` via
  Nest's `Test.createTestingModule({imports: [SessionModule, ...]})`
  (first use of `TestingModule` in this repo — confirm `SessionModule`'s
  full import list resolves cleanly standalone, i.e. that nothing it
  transitively needs is missing outside the full app bootstrap) rather than
  hand-wiring stubs, since real-everything is exactly what an eval harness
  needs.
- Add `eval/**/*.spec-int.ts` to `vitest.integration.config.ts`'s glob (see
  pre-flight note).

**Tests (`apps/zoltar-be/eval/harness-runner.spec-int.ts`):**

- Hand-construct an `EvalFixture` object (valid per Part 1's schema, not
  loaded from a file) with a small scripted `campaignState`/`messages`.
  `seedScratchAdventure` produces a queryable adventure whose seeded rows
  match the fixture's `seededState` exactly. `runFixtureTurn` against it
  (real `SessionService`, real Anthropic call — this test is slower and
  costs real tokens; mark it clearly, e.g. a `describe.skipIf(!process.env.RUN_LIVE_EVAL_TESTS)`
  guard so it doesn't run in ordinary CI-less local `npm test` loops)
  produces a `TurnExecutionResult` with a non-empty `game_events` sequence.
  `teardownScratchAdventure` actually removes the campaign row and
  everything cascaded under it.
- A `submitDiceResult`-path fixture (seeded with a pending `dice_request`
  row) exercises the other branch of `runFixtureTurn`.

**Review gate.** `tsc --noEmit` clean. Integration tests green (including
at least one live run against real Anthropic, run manually if the
`RUN_LIVE_EVAL_TESTS` guard keeps it out of the default test run). Manually
inspect a scratch adventure's rows via `psql` after a run, before teardown,
to confirm the seeding looks right by eye. Commit.

## Part 4 — Structural assertion checkers

Depends on Part 3's `TurnExecutionResult` shape. Pure functions, no DB, no
network — each takes a `TurnExecutionResult` (plus the fixture's `facts`-free
context, since structural checks don't need judge-style per-instance facts)
and returns a pass/fail verdict with a human-readable "expected vs. actual"
detail for the report.

**`apps/zoltar-be/eval/checks/structural/*.ts`** — one file per tag, six
files (`out-of-order-resolution.ts`, `system-rolled-player-action.ts`,
`unauditable-mapping.ts`, `missing-canon-capture.ts`,
`narrating-past-a-block.ts`, `unsurfaced-check.ts`), each exporting a
function of shape `(result: TurnExecutionResult) => StructuralVerdict`
where `StructuralVerdict = {passed: boolean; actual: string}` (the
`Expected:` half of the report comes from the fixture's own `check` text,
per the pre-flight decision — the checker only needs to produce
`Actual:`).

Concrete per-tag logic, reading `TurnExecutionResult.gameEvents`/
`adventureTelemetry`/`campaignState` (all confirmed shapes from the
survey):

- **`OUT-OF-ORDER-RESOLUTION`**: walk `gameEvents` filtered to
  `eventType === 'dice_roll'`, grouped by the entity the roll's `payload.purpose`
  attributes it to; for any entity with both a to-hit-flavored and a
  damage-flavored roll, the damage roll's `sequenceNumber` must be greater.
  Also: no `dice_roll` event may have a lower `sequenceNumber` than the
  `player_action` event it resolves. Exact string-matching on `purpose` to
  classify "to-hit" vs. "damage" is heuristic — document the substring
  match used and flag in the PR description that this is a best-effort
  classifier, not a guaranteed-general parser, same caveat class as
  anything pattern-matching free text.
- **`SYSTEM-ROLLED-PLAYER-ACTION`**: for the `dice_roll` event(s)
  corresponding to the player's own declared action (the first dice roll
  after the turn's `player_action` event, before any NPC/system rolls),
  assert `rollSource === 'player_entered'` OR a `dice_request` row exists
  with matching `issuedAtSequence` and `status: 'pending'`.
- **`UNAUDITABLE-MAPPING`**: for every `dice_roll` event whose
  `payload.purpose` matches a narrative-selection heuristic (contains
  language like "determine which," "select," "decide" rather than pure
  mechanics like "to-hit," "damage," "save") — again a heuristic string
  classifier, same caveat — assert `payload.purpose` states the
  result-to-meaning mapping (checked by confirming the purpose string
  contains a numeric range or threshold token, e.g. matches `/\d.*(?:=|:|means|indicates)/`)
  and that this `dice_roll` event's `createdAt`/`sequenceNumber` precedes
  any dependent `gm_response`/`state_update` referencing its result.
- **`MISSING-CANON-CAPTURE`**: needs the fixture's *expected* narration to
  know whether a new detail was introduced — this is the one structural
  check that also reads a fixture-supplied fact, so its function signature
  is `(result, expectedNewDetail: string) => StructuralVerdict` rather than
  `TurnExecutionResult` alone; store that one fact in the fixture's `check`
  string itself (parsed loosely, e.g. everything after a `expects:` marker)
  rather than inventing a `facts` field for structural fixtures (which the
  schema doesn't have — judged fixtures have `facts`, structural ones
  don't, per the spec's literal type). Verdict: pass if
  `TurnExecutionResult.campaignState.worldFacts` gained a new key this turn,
  OR a new `pending_canon` row was inserted this turn (`sequenceNumber`
  equal to this turn's `gm_response` sequence).
- **`NARRATING-PAST-A-BLOCK`**: if the turn produced a pending
  `dice_request` (unresolved) or the turn's own tool loop hit a blocked
  state (check `adventureTelemetry.payload.toolLoopIterations`/`notes` for
  a block marker — confirm the exact field name at implementation time),
  assert the `gm_response.payload.playerText` does not contain narration
  timestamped/sequenced after the block — in practice this likely reduces
  to "the response text length/content stops at a reasonable point and
  doesn't include resolution language for the blocked action," which is
  inherently fuzzier than the other five; flag this one in the PR as the
  weakest structural checker and note it may need a judged fallback later
  if it proves too noisy in practice.
- **`UNSURFACED-CHECK`**: for `dice_roll` events whose `purpose` indicates
  player-visible stakes (heuristic, as above), assert a corresponding
  `dice_request` row exists (the roll was surfaced to the player) rather
  than the roll resolving system-side with no `dice_request`.

**`apps/zoltar-be/eval/checks/structural/registry.ts`:**

- `structuralCheckers: Record<Extract<FailureModeTag, ...six tags...>, (result: TurnExecutionResult, fixture: EvalFixture) => StructuralVerdict>` —
  the lookup Part 7's CLI uses to dispatch a structural fixture to its
  checker by `fixture.tag`.

**Tests (`apps/zoltar-be/eval/checks/structural/*.spec.ts`, one per file):**

This is where the spec's "Testing the Harness Itself" section is satisfied
— no DB, no fixture files, just hand-built `TurnExecutionResult` objects:

- One hand-built `TurnExecutionResult` representing clean behavior → passes.
- One hand-built `TurnExecutionResult` with the specific violation this
  checker exists to catch (e.g., for `OUT-OF-ORDER-RESOLUTION`, a
  `gameEvents` array with a damage-purpose roll at a lower
  `sequenceNumber` than its to-hit roll) → fails, with an `actual` string
  that clearly names the violation.
- At least one boundary case per checker (e.g., a turn with zero dice
  rolls at all shouldn't false-positive-fail `OUT-OF-ORDER-RESOLUTION`).

**Review gate.** `tsc --noEmit` clean. Unit tests green, explicitly
including a pass case and a deliberately-broken fail case per checker (per
spec). Commit.

## Part 5 — Judge-graded assertion checkers

Depends on Part 3's `TurnExecutionResult` shape. Two rubrics, authored
once, each driving a single Claude Sonnet 5 call per fixture.

**`apps/zoltar-be/eval/checks/judged/rubrics.ts`:**

- `judgeRubrics: Record<'HIDDEN-INFO-LEAK' | 'OVER-RESOLUTION', {template: string; requiredFacts: string[]}>` —
  `template` is the rubric prompt text with `{{factName}}` placeholders;
  `requiredFacts` names which keys the fixture's `facts` map must supply
  (`perceptionBoundary` for `HIDDEN-INFO-LEAK`, `resolutionLevel` — on-screen
  vs. off-screen/summarized — for `OVER-RESOLUTION`). Validate at
  registration/load time (or in Part 1's schema loader — decide during
  implementation which is more natural) that every judged fixture supplies
  its tag's `requiredFacts`, so a missing fact fails fast at fixture-load
  time rather than mid-judge-call.
- Rubric prompt content, per spec: for `HIDDEN-INFO-LEAK`, ask whether the
  turn's `gm_response.payload.playerText` reveals anything — including
  specific roll values, thresholds, or mechanical outcomes — beyond the
  fixture's stated `perceptionBoundary`. For `OVER-RESOLUTION`, ask whether
  roll count/granularity in this turn's `gameEvents` matches the fixture's
  stated `resolutionLevel` or over-simulates off-screen content.

**`apps/zoltar-be/eval/checks/judged/judge.ts`:**

- `runJudgeCall(fixture, result: TurnExecutionResult): Promise<JudgedVerdict>`
  where `JudgedVerdict = {passed: boolean; rationale: string}`. Builds the
  rubric prompt (template + interpolated `facts` + the relevant slice of
  `result`, e.g. `playerText` and the turn's `gameEvents`), calls Sonnet 5
  forcing a structured tool-call response (`{passed: boolean, rationale: string}`)

## Part 7 — Harness CLI (`eval:harness`)

Depends on Parts 1, 3, 4, 5, 6 — the integration point. Same `scripts/`
conventions as Part 2 and the rest of the repo's CLI tools.

**`apps/zoltar-be/scripts/eval-harness.core.ts`:**

- `runHarness(args: {fixturesDir: string; tags?: FailureModeTag[]; promptVariant?: string; keepScratch?: boolean}): Promise<{report: string; results: FixtureResult[]}>`:
  1. `loadFixtures(fixturesDir, {tags})` (Part 1). Any `FixtureLoadError`s
     get logged to stderr as warnings; loading continues with the fixtures
     that did parse (a bad fixture file shouldn't block the rest of the
     run — but the CLI's exit code still reflects it, see below).
  2. If `promptVariant` given, set `WARDEN_PROMPT_OVERRIDE_MOTHERSHIP` (per
     the pre-flight note) before constructing the `SessionService`/
     `WardenPromptsService` instance — override must be set before
     `WardenPromptsService`'s `onModuleInit` resolves selection, so this
     needs to happen before the Nest module bootstrap, not after.
  3. For each fixture (sequentially — these hit a real DB and a real
     model, no need for the concurrency complexity of parallelizing, and
     serial execution keeps output ordering predictable for the report):
     seed via `seedScratchAdventure`, run via `runFixtureTurn`, dispatch to
     `structuralCheckers[fixture.tag]` or `runJudgeCall` depending on
     `fixture.assertion.mode`, teardown via `teardownScratchAdventure`
     unless `keepScratch`.
  4. Collect `FixtureResult[]`, render via `renderReport`.
- Exit-code policy: non-zero if any fixture failed its assertion, *and*
  non-zero if any fixture file failed to load — a silently-skipped broken
  fixture must not read as a clean run.

**`apps/zoltar-be/scripts/eval-harness.ts`:**

- `parseArgs` for `--fixtures`, `--tag` (comma-separated, matching the
  spec's invocation example), `--prompt-variant`, `--output`,
  `--keep-scratch`. `--output` writes the rendered report to a file if
  given a path, or a directory default (mirroring `playtest-review.ts`'s
  `playtest-reports/` convention — e.g. `eval-reports/<timestamp>-<promptVariant>.md`)
  if given the bare word `report` per the spec's literal example, or
  prints to stdout if omitted entirely. Confirm the exact `--output report`
  semantics the spec's example implies (a literal directory-selector
  keyword vs. a typo for a path) before implementing — if genuinely
  ambiguous, prefer stdout-by-default plus an explicit path, and note the
  deviation from the spec's example in the PR description.
- Standard `main().then(...)` exit pattern.

**Wiring:**

- `apps/zoltar-be/package.json`: add `"eval:harness": "tsx scripts/eval-harness.ts"`.
- `Taskfile.yml`: add `eval:harness` and (if not already added in Part 2)
  `eval:capture-fixture` tasks, matching the `playtest:*` task style.
- README or a short comment block in `eval-harness.ts` itself: prominent
  warning that this command hits a real database and makes real,
  token-costing Anthropic calls — not a CI-safe or free-to-run-repeatedly
  command, consistent with the spec's "manually-invoked local tool, no CI

**Tests (`apps/zoltar-be/scripts/eval-harness.spec-int.ts`):**
