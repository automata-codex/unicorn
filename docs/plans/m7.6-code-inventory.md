### 1.3 Pool definition metadata the validator reads

`packages/game-systems/src/mothership/pool-definitions.ts`, complete file:

```typescript
import { z } from 'zod';

export const PoolDefinitionSchema = z.object({
  min: z.number().int().nullable(),
  max: z.number().int().nullable(),
  thresholds: z
    .array(
      z.object({
        value: z.number().int(),
        effect: z.string(),
      }),
    )
    .default([]),
});

export type PoolDefinition = z.infer<typeof PoolDefinitionSchema>;

const HP_DEFINITION: PoolDefinition = {
  min: null,
  max: null,
  thresholds: [{ value: 0, effect: 'death_save_required' }],
};

const STRESS_DEFINITION: PoolDefinition = {
  min: 0,
  max: null,
  thresholds: [],
};

const DEFAULT_DEFINITION: PoolDefinition = {
  min: null,
  max: null,
  thresholds: [],
};

export function getMothershipPoolDefinition(poolName: string): PoolDefinition {
  if (poolName.endsWith('_hp')) return HP_DEFINITION;
  if (poolName.endsWith('_stress')) return STRESS_DEFINITION;
  return DEFAULT_DEFINITION;
}
```

**Every Mothership pool that has a definition, exhaustively — there are three, and two of
them are selected by string suffix:**

| Selector | `min` | `max` | `thresholds` | Applies to |
|---|---|---|---|---|
| `*_hp` | `null` | `null` | `[{ value: 0, effect: 'death_save_required' }]` | any pool key ending `_hp`, player or NPC |
| `*_stress` | `0` | `null` | `[]` | any pool key ending `_stress` |
| everything else | `null` | `null` | `[]` | `alvarez_armor`, `station_power_reserve`, `*_timer`, … |

Three observations about what this metadata does *not* carry, stated descriptively:

1. **`max` is `null` on all three definitions**, so the validator's ceiling branch
   (`apps/zoltar-be/src/session/session.validator.ts:201-208`) never fires for any Mothership
   pool. The per-pool `max` stored on the `{ current, max }` record — e.g. `alvarez_hp.max = 20` —
   is **not** used as a validation ceiling. It is rendered into the snapshot
   (`session.snapshot.ts:87`) and read by the frontend status strip
   (`play-helpers.ts:57-63`), but nothing clamps against it. HP can be healed above `max`.
2. **There is no per-entity or per-character definition lookup** — selection is purely by
   key suffix, so a definition is shared by the player's `alvarez_hp` and an NPC's
   `veridian_contractor_alpha_hp`.
3. `armor` pools fall through to `DEFAULT_DEFINITION`, so `alvarez_armor` has `min: null` and
   may go negative.

Threshold semantics carry a comment worth surfacing, at
`apps/zoltar-be/src/session/session.validator.ts:215-220`:

```typescript
  // Thresholds fire only on downward crossings (negative delta). The spec's
  // formal rule in §"Part 2 → resourcePools → 3" lists a symmetric positive-
  // delta case as well, but the spec test list is explicit that HP healed
  // from -1 to +2 does not fire (already past it). The asymmetric reading
  // satisfies the concrete test; no M6 pool carries an upward-violation
  // threshold. Revisit if such a threshold is introduced.
```

`deriveMothershipCharacterResourcePools` itself,
`packages/game-systems/src/mothership/character-pools.ts:1-25`, complete:

```typescript
import type { MothershipCharacterSheet } from './character-sheet.schema';

export type ResourcePool = { current: number; max: number | null };

/**
 * Derives the resource pools the Mothership campaign state must carry for a
 * player character: HP and stress. Names follow the canonical
 * `{entity_id}_{pool_name}` convention. Called at character creation time so
 * the pools exist in `campaign_state.data.resourcePools` before synthesis
 * runs — synthesis is not expected to re-derive them.
 */
export function deriveMothershipCharacterResourcePools(
  sheet: MothershipCharacterSheet,
): Record<string, ResourcePool> {
  return {
    [`${sheet.entityId}_hp`]: {
      current: sheet.maxHp,
      max: sheet.maxHp,
    },
    [`${sheet.entityId}_stress`]: {
      current: 0,
      max: sheet.maxStress,
    },
  };
}
```

**It reads exactly three fields: `entityId`, `maxHp`, `maxStress`.** Nothing else on the
sheet reaches `resourcePools`. Note in particular that `saves.armor` / `saves.armorMax` are
**not** derived into an `armor` pool — the `alvarez_armor` pool that exists in the captured
corpus was minted by the model, not by this function (corroborated by
`docs/decisions.md`'s amendment: "plus an `alvarez_armor` that no derivation produces").

```typescript
  const lines = [
    `${sheet.name} (${sheet.class})`,
    // The canonical entity id, not a display name. Without it the model has
    // only `name` to work from and invents an id to build pool names out of —
    // "Lt. Alvarez" derives equally well to `lt_alvarez` or `alvarez`, and the
    // captured M7.5 adventure ended up carrying both for one character. See
    // `docs/decisions.md § Player resource pools are derived at character
    // creation, not at synthesis`.
    `Entity ID: ${sheet.entityId}`,
    `Stats: STR ${sheet.stats.strength}, SPD ${sheet.stats.speed}, INT ${sheet.stats.intellect}, CMB ${sheet.stats.combat}, INST ${sheet.stats.instinct}, SAN ${sheet.stats.sanity}`,
    `Saves: Fear ${sheet.saves.fear}, Body ${sheet.saves.body}, Armor ${sheet.saves.armor}/${sheet.saves.armorMax}`,
    `HP: ${sheet.maxHp}   Stress Threshold: ${sheet.maxStress}`,
    `Skills: ${sheet.skills.join(', ') || '(none)'}`,
    `Equipment: ${sheet.equipment.join(', ') || '(none)'}`,
  ];
  return lines.join('\n');
}
```

Note the label `Stress Threshold:` for `maxStress` — the only place in the codebase where
that field is given a name other than "max stress".

- A fixture id present in the source run but **missing from disk** has every source row

### 3.5 Would a sheet shape change need a migration?

**The column absorbs it.** `character_sheet.data` is `jsonb NOT NULL DEFAULT '{}'` with no
check constraint, no generated columns, no expression indexes, and no FK derived from its
contents (§1.4). Postgres will store any shape.

Whether a *data* migration is needed is a separate question, and the answer is determined by
one thing: `MothershipCharacterSheetSchema` is enforced on **write only**
(`character.controller.ts:39`, `:59`). There is no read-side `.parse()` of
`character_sheet.data` anywhere — `findByCampaignId` returns the raw row
(`character.repository.ts:31-38`), `getPlayerEntityIds` reads one field defensively
(`session.repository.ts:155`), and the synthesis controller casts rather than parses
(`synthesis.controller.ts:161`). So an old-shape row would not throw on read; it would
produce `undefined` at whichever field the consumer touched — most visibly a
`TypeError: Cannot read properties of undefined` in `formatMothershipCharacterProse`
(`synthesis.prompts.ts:40`, which dereferences `sheet.stats.strength` unguardedly) or a
blank render in `CharacterView.svelte`.

There **is** a working precedent for a mechanical transform:
`V10__character_sheet_drop_current_fields.sql` (quoted in §1.4) did a pure SQL `jsonb`
rewrite — subtract two keys, add one derived from a third, with a `COALESCE(…, 3)` default
for the case where the source was missing. That covers the "mechanical" case.

**Whether a specific future change is mechanical or needs per-row judgement cannot be
answered here** — it depends on the target shape, which this document deliberately does not
have. What can be said about the *inputs* to that judgement:

- Any field the current schema requires and a new shape splits — `saves.armor: number`
  becoming an item with `{ base, current, destroyed }` is the case `docs/decisions.md:551`
  and `docs/m7.6-psg-character-sheet-inventory.md §4` both describe — has no recoverable
  provenance in the existing row. A single integer cannot be mechanically split into base vs
  current without knowing whether the character had taken armor damage.
- `equipment: string[]` → structured items has the same property: free-text strings written
  by a human through `CharacterEdit.svelte`.
- Purely additive fields need no migration at all, per `docs/schema.md:19`.
- `campaign_state.data` has a harder constraint than the sheet: `schemaVersion: z.literal(1)`
  (`campaign-state.schema.ts:11`) and it *is* parsed, at
  `synthesis.write.ts:200`. Any campaign-state shape change that bumps that literal breaks
  every existing row at the next synthesis commit unless migrated.

**Unknown:** with the dev DB at 0 rows, there is currently nothing to migrate locally. If
production rows exist, both the count and the per-row inspection are needed before "mechanical
vs judgement" can be answered concretely.

### Q1 — Adventure boundary reseed

**Answered definitively.** Trace, in order.

**(a) A second adventure can be created today.** `AdventureService.create`
(`apps/zoltar-be/src/adventure/adventure.service.ts:18-21`), complete:

```typescript

    await this.campaignService.assertMember(campaignId, userId);
    return this.repo.insert({ campaignId, callerId: userId });

```

The only precondition is campaign membership. `AdventureRepository.insert`
(`adventure.repository.ts:15-25`) inserts unconditionally with `status: 'synthesizing'`. The
controller (`adventure.controller.ts:26-41`) adds nothing. There is **no** uniqueness
constraint on `adventure.campaign_id`, and no `hasActiveAdventure` check on this path —
`CampaignRepository.hasActiveAdventure` exists (`campaign.repository.ts:182-198`) but is

`docs/roadmap.md:359` confirms this is known and deferred: the M9 bullet is
"Enforce one adventure per campaign — backend rejection on adventure creation when the
campaign already has *any* adventure", and states that
"`docs/decisions.md § One active adventure per campaign` explicitly permits it today".

**(b) Nothing on the second-adventure path re-derives player pools.**
`deriveMothershipCharacterResourcePools` has exactly two call sites in non-test code —
`character.service.ts:45` (create) and `character.service.ts:73` (update). Verified by grep;
the only other hits are the package definition, its own spec, and the barrel export. Neither
call site is on the adventure-creation or synthesis path.

**(c) The synthesis write path preserves the reduced values.** Second-adventure synthesis
runs `commitGmContext` (`synthesis.service.ts:194-231`), which reads the *existing*
campaign state at `:203` and passes it into `buildCampaignStateData`. That function reads
existing pools at `synthesis.write.ts:162-164` and hands them to `buildResourcePools` as
`existingPools`, which begins (`synthesis.write.ts:109`):

```typescript
  const merged: Record<string, ResourcePool> = { ...existingPools };
```

and then, for each proposed key (`synthesis.write.ts:115`):

```typescript
    if (key in merged) continue; // preserve existing player pools
```

The write itself is an upsert keyed on campaign, not adventure
(`synthesis.repository.ts:58-69`):

```typescript
      await tx
        .insert(schema.campaignStates)
        .values({
          campaignId: args.campaignId,
          system: 'mothership',
          schemaVersion: 1,
          data: args.campaignStateData,
        })
        .onConflictDoUpdate({
          target: schema.campaignStates.campaignId,
          set: { data: args.campaignStateData, updatedAt: sql`now()` },
        });
```

**Answer to the specific question:** a character whose HP was reduced during adventure 1
**begins adventure 2 at the reduced value.** Same for stress. The `alvarez_hp: 7/20` in
`turn28-hidden-info-leak.json` would carry into a second adventure as `7/20`.

`mergePlayerResourcePools` reinforces the same direction if it ever ran again
(`campaign.repository.ts:93-96`):

```typescript
      const mergedPools: Record<string, ResourcePool> = { ...newPools };
      for (const [key, value] of Object.entries(existingPools)) {
        mergedPools[key] = value;
      }
```

New pools are laid down first and **existing keys overwrite them** — so even an explicit
re-derivation would not reset HP. Its doc comment (`campaign.repository.ts:64-73`) states the
intent:

```
   * Merges new resource pools into `campaign_state.data.resourcePools` for a
   * campaign, preserving any pools already present. Used at character
   * creation time to seed player HP / stress. Existing keys always win so
   * that an in-progress adventure can never have its live state clobbered by
   * re-running character creation (today that path is blocked upstream, but
   * the merge is cheap insurance).
```

**One consequence of "existing keys always win" worth recording, since it is the inverse of
the question asked:** because `mergePlayerResourcePools` cannot overwrite, a character sheet
edited to raise `maxHp` (via `CharacterService.update`, consumer #5) will **not** update the
existing `alvarez_hp` pool's `max` either. The pool keeps its old `{ current, max }` entirely.
The re-derivation at `character.service.ts:73` is therefore a no-op whenever the pools
already exist — which, since `create` seeds them, is always. It has effect only in the case
where a sheet's `entityId` was changed, which mints a *new* pair of pools under the new
prefix and leaves the old pair orphaned.

**Also noted:** nothing anywhere resets `entities`, `flags`, `scenarioState`, or `worldFacts`
at an adventure boundary either. `buildCampaignStateData` spreads existing entities
(`synthesis.write.ts:188-191`), carries `existingScenarioState` and `existingWorldFacts`
forward verbatim (`:171-174`, `:193-197`), and **replaces** `flags` wholesale with the new
payload's (`:192`). Flags are the one section a second synthesis clears.

**Is there a "rest" code path?** No. Grep for a rest mechanic across `apps/zoltar-be/src` and
`packages/game-systems/src` finds nothing. The only mention is descriptive text in the Warden
prompt, `apps/zoltar-be/src/wardens/prompts/mothership-m7.txt:145-147`:

```
- A character gains 1 Stress every time they fail a Stat Check or Save.
  Resting lets them roll a Rest Save to shed Stress; Shore Leave converts
  Stress into permanently improved Saves.
```

So a rest is entirely a Warden-narrated event that arrives as an ordinary negative
`resourcePools` delta and is floored at 0 by the generic rule above. There is no
rest-specific code, no Minimum Stress concept, and no per-character floor.

**Does the code agree with the doc?** `docs/decisions.md:520` says
`deriveMothershipCharacterResourcePools` "seeds the pools at full HP and zero stress from the
ceilings." **The code agrees with that sentence exactly.** The same document then flags the
*rules* disagreement itself, at `docs/decisions.md:551-554`:

```
**One correction of fact in the entry above:** it describes the derivation as seeding
pools "at full HP and zero stress." Current Stress starts at **2**, not 0, and floors at
Minimum Stress thereafter, never at zero. Whether the code matches the entry or the rules
is a verification item for M7.6.
```

**That verification item is now closed: the code matches the entry (0), not the rules (2).**
The floor likewise matches the entry (0), not the rules (Minimum Stress). Both halves of the
addendum's open question resolve the same way.

One further mismatch in the same area, stated descriptively: `maxStress` is used as the
pool's `max` (`character-pools.ts:22`), rendered as `Stress Threshold:` in the synthesis
prompt (`synthesis.prompts.ts:42`), and shown as the stress bar's denominator in the frontend
(`play-helpers.ts:62`, `CharacterStatusStrip.svelte`) — but because `STRESS_DEFINITION.max` is
`null`, **it is not enforced as a ceiling by the validator**. Stress can exceed `maxStress`
without rejection. The frontend default for `maxStress` is `3`
(`CharacterCreate.svelte:38`, `CharacterEdit.svelte:44`), which is what produced the `0/3`
seen throughout the corpus.

### Q3 — Cross-adventure snapshot scope

**Answered definitively, in three parts.**

**(a) The snapshot is not adventure-scoped anywhere.** `buildStateSnapshot`
(`apps/zoltar-be/src/session/session.snapshot.ts:43-77`) takes exactly two inputs —
`gmContextBlob` and `campaignStateData` — and no adventure id. It renders five sections
unconditionally from the campaign-state blob:

```typescript
  const pools = renderResourcePools(campaignStateData.resourcePools);
  if (pools !== null) sections.push(pools);

  const entities = renderEntities(
    campaignStateData.entities,
    new Set(gmContextBlob.playerEntityIds ?? []),
  );
  if (entities !== null) sections.push(entities);

  const flags = renderFlags(
    campaignStateData.flags,
    gmContextBlob.structured?.flags,
  );
  if (flags !== null) sections.push(flags);

  const scenarioState = renderScenarioState(campaignStateData.scenarioState);
  if (scenarioState !== null) sections.push(scenarioState);

  const worldFacts = renderWorldFacts(campaignStateData.worldFacts);
  if (worldFacts !== null) sections.push(worldFacts);
```

Each render function is a sort-and-format over the full map, with **one filter in the whole
file**: `renderEntities` drops non-player entities whose `visible` is false
(`session.snapshot.ts:123`). No render function takes an adventure parameter or consults one.
`renderResourcePools` (`:79-91`), `renderFlags` (`:132-155`), `renderScenarioState`
(`:157-171`) and `renderWorldFacts` (`:173-181`) all emit every key.

`renderEntities` verbatim, `session.snapshot.ts:110-130`:

```typescript
function renderEntities(
  entities: CampaignStateData['entities'],
  playerEntityIds: ReadonlySet<string>,
): string | null {
  const playerLines = [...playerEntityIds].sort().map((id) => {
    const entity = entities[id];
    if (!entity) return `${id}: visible, status=unknown, player_character`;
    const visibility = entity.visible ? 'visible' : 'hidden';
    return `${id}: ${visibility}, status=${entity.status}, player_character`;
  });

  const otherLines = Object.keys(entities)
    .sort()
    .filter((id) => !playerEntityIds.has(id) && entities[id].visible)
    .map((id) => `${id}: visible, status=${entities[id].status}`);

  const lines = [...playerLines, ...otherLines];
  if (lines.length === 0) return null;

  return `<entities>\n${lines.join('\n')}\n</entities>`;
}
```

The snapshot is the *first user message* of every turn's request
(`apps/zoltar-be/src/session/session.prompt.ts:163-170`), and a second copy is written to
telemetry (`session.service.ts:386-389`).

**So: if a campaign had entities and pools from two adventures, both would appear in the
snapshot sent to the Warden.** Adventure-1 NPCs would keep appearing, at whatever `visible`
and `status` they were left at, for the whole of adventure 2. Adventure-1 timers and
scenario state would keep rendering. `worldFacts` — including the required spatial-layout
entry the synthesis prompt mandates (`synthesis.prompts.ts:79`) — would accumulate both
adventures' locations.

There is exactly one adventure-derived input to the snapshot, and it is not a scope filter:
`gmContextBlob.structured.flags` is read by `renderFlags` to decide *which flags re-emit
their trigger* (`session.snapshot.ts:144`). Original flags emit `key: value`; flags introduced
during play emit `key: value (trigger: …)`. Since `buildCampaignStateData` replaces `flags`
wholesale at each synthesis (`synthesis.write.ts:192`) and `gm_context` is per-adventure
(`schema.ts:202-212`), the flags section is the one part that is de facto adventure-scoped —
by replacement, not by filtering.

**(b) Entity ids are namespaced per campaign, not per adventure.** The storage is a single
row: `campaign_state` is `UNIQUE (campaign_id)`
(`infra/db/migrations/V2__core_tables.sql:57`), and both writers key on campaign —
`mergePlayerResourcePools` (`campaign.repository.ts:83`, `:101`) and the synthesis upsert
(`synthesis.repository.ts:67`). `entities` and `resourcePools` are flat
`Record<string, …>` maps inside that one blob (`campaign-state.schema.ts:15`, `:19`) with **no
adventure discriminator field**. `grid_entity` is likewise campaign-keyed
(`schema.ts:291-301`).

The only uniqueness enforcement is *within a single synthesis payload*:
`validateSubmitGmContextForWrite` rejects duplicate ids inside one `structured.entities`
array (`synthesis.write.ts:45-53`):

```typescript
  const seen = new Set<string>();
  for (const entity of input.structured.entities) {
    if (seen.has(entity.id)) {
      throw new SynthesisWriteValidationError(
        `duplicate entity id in structured.entities: ${entity.id}`,
      );
    }
    seen.add(entity.id);
  }
```

Nothing checks a proposed id against ids already in campaign state. Adventure 2 is free to
mint `survivor_1` when adventure 1 already has one.

**(c) Key-collision behaviour in `resourcePools`, traced through all three merge points.**
The three behave differently and it is worth having them side by side:

| Merge point | `path:line` | Collision winner |
|---|---|---|
| `mergePlayerResourcePools` (character create/update) | `campaign.repository.ts:93-96` | **existing** — `{...newPools}` first, then existing keys overwrite |
| `buildResourcePools` (synthesis write) | `synthesis.write.ts:109`, `:115` | **existing** — `{...existingPools}` first, then `if (key in merged) continue` |
| `applyValidatedTurn` (per-turn fold) | `session.applier.ts:25-28` | **new** — `{...prior, ...applied}`, plain shallow spread, last writer wins |

`applyValidatedTurn`'s merge verbatim, `session.applier.ts:23-36`:

```typescript
  const newCampaignState: MothershipCampaignState = {
    schemaVersion: priorCampaignState.schemaVersion,
    resourcePools: {
      ...priorCampaignState.resourcePools,
      ...applied.resourcePools,
    },
    entities: { ...priorCampaignState.entities, ...applied.entities },
    flags: { ...priorCampaignState.flags, ...applied.flags },
    scenarioState: {
      ...priorCampaignState.scenarioState,
      ...applied.scenarioState,
    },
    worldFacts: { ...priorCampaignState.worldFacts, ...applied.worldFacts },
  };
```

Every section is a shallow spread with the turn's applied values winning. So a colliding
`survivor_1_hp` from adventure 2 would silently take over adventure 1's pool of the same
name at the first turn that touched it — no rejection, no log, no diagnostic. The same
applies to `entities`: `applyEntity` merges field-by-field against the *existing* record
(`session.validator.ts:261-269`), preserving `npcState` from whichever entity held the id
first, which would blend two different NPCs sharing a key.

The one collision guard that does exist, `impersonatesPlayerPool`
(`session.validator.ts:113-136`), is scoped to *player* pool suffixes only and fires solely on
the bootstrap branch (`session.validator.ts:153-173`) — i.e., when the pool does **not**
already exist. It cannot see a cross-adventure NPC collision, since by definition that key
already exists and takes the `existing` branch at `:187`.

`applyValidatedTurn` is also the fold used by replay (`reconstruct-state.ts:4`, and its own
doc comment at `session.applier.ts:9-10`: "This is also the fold step replay (M7.3) threads
forward through the event log turn by turn"), so replay reproduces the same collision
behaviour.

## Part 5 — Observations

Descriptive only.

**5.1 — The sheet reaches Claude exactly once, ever.** The full sheet is rendered into the
*synthesis* prompt (`synthesis.prompts.ts:72`) and never appears in a per-turn Warden prompt.
Everything the Warden knows about the character during play arrives via `<resource_pools>`
and one `<entities>` line. `docs/roadmap.md:304` describes this as an open M7.6 bullet, and
`docs/decisions.md:768-780` is the deferral entry.

**5.2 — Three fields are written and never read by any consumer.** `level`, `pronouns`, and
`notes` are validated on write (`character-sheet.schema.ts:15`, `:13`, `:34`) and rendered in
`CharacterView.svelte` (`:88-91`, `:177-181` — `pronouns` and `notes`), but `level` is read
nowhere at all: it is absent from `formatMothershipCharacterProse`, absent from the frontend
`CharacterSheet` type (`apps/zoltar-fe/src/lib/types.ts:25-40`), and absent from both
create/edit forms. It is a schema field with `.default(1)` and no producer or consumer.

**5.3 — The `assertNoActiveAdventure` guard does not cover completed adventures.**
`CharacterService.update` and `.delete` block only while an adventure is `synthesizing`,
`ready`, or `in_progress` (`character.repository.ts:73-77`). Once an adventure is `completed`,
`aborted`, or `failed`, the sheet is editable and `deriveMothershipCharacterResourcePools`
re-runs — where, per Q1, it cannot change any existing pool but *can* mint a new orphaned pair
if `entityId` changed. `CharacterService.delete` (`:79-87`) removes the sheet row and does
**not** remove the derived pools from `campaign_state.data.resourcePools`; they persist and
keep rendering in the snapshot, now with `getPlayerEntityIds` returning `[]`, which per the
comment at `session.service.ts:908-912` disables `actingEntityId` validation entirely:

```
    // **Skipped entirely when the set is empty**, which is not a formality:
    // `getPlayerEntityIds` reads `character_sheet.data.entityId` and there are
    // campaigns with no character sheet at all. Rejecting against a set that
    // is missing the player would reject every one of the player's rolls, so
    // no set means no opinion.
```

**5.4 — The eval harness writes a `character_sheet` row that the sheet schema would reject.**
`harness-runner.ts:326-328` inserts `data: { entityId: canonicalPlayerEntityId }`. This is
load-bearing (without it `getPlayerEntityIds` returns `[]` and the run measures a code path
production doesn't take — reasoning at `harness-runner.ts:195-207`), and it works because
nothing parses the sheet on read. **A read-side validation of `character_sheet.data`
introduced anywhere would break every eval run**, since the seeded row has 1 of the 9 required
fields.

**5.5 — Comments explaining non-obvious reasoning, worth surfacing.**

- `packages/game-systems/src/index.ts:5-11` explains why the dice surface uses explicit named
  re-exports rather than `export *` — Vite's CJS→ESM interop can't statically analyze
  `__exportStar`, producing runtime "does not provide an export named X" in the browser. The
  Mothership schemas at `:20-26` **do** use `export *`, so they are consumed as types only by
  the frontend. `apps/zoltar-fe` in fact does not import from `@uv/game-systems` for the sheet
  at all — it hand-writes the type (§2.4 #23).
- `synthesis.write.ts:82-103` (`buildResourcePools`) is the fullest written account of the
  duplicate-prefix defect and why key-preservation alone doesn't fix it:
  "Preservation only settles a *collision*; the failure mode is the opposite one, where the
  model spells the player's id differently, collides with nothing, and both spellings
  persist."
- `session.snapshot.ts:93-108` (`renderEntities`) explains why player ids are emitted as a
  *source* rather than a filter override, and cites the failure it fixed.
- `session.validator.ts:215-220` documents a deliberate divergence from the M6 spec on
  threshold symmetry (quoted in §1.3), with a "Revisit if" condition.
- `synthesis.repository.ts:71-77` explains why `adventureSynthesisSnapshots` uses
  `onConflictDoNothing` and why its schema versions are hardcoded to `1`.
- `eval/fixture.schema.ts:214-222` explains why `LEGACY_FIXTURE_SCHEMA_VERSION` is frozen at
  `1` rather than tracking `FIXTURE_SCHEMA_VERSION`.
- `campaign.repository.ts:69-70` — "today that path is blocked upstream, but the merge is
  cheap insurance" — is the note that makes the Q1 behaviour deliberate rather than accidental.

**5.6 — Doc references in comments that point at things that no longer resolve cleanly.**

- `session.validator.ts:218` cites `The spec's formal rule in §"Part 2 → resourcePools → 3"`
  without naming a file. The M6 spec is `docs/specs/zoltar/006-m6-state-management.md`;
  `docs/specs/` is described as ephemeral by policy at `docs/roadmap.md:360`
  ("pruning or archiving accumulated `docs/specs/zoltar/` entries, which are ephemeral by
  policy"). The reference resolves today but is pointed at a directory slated for a sweep.
- `session.snapshot.ts:6` refers to "`playerEntityIds`, which Phase 5 supplies from a
  character-sheet lookup" — "Phase 5" is an M5-implementation-plan phase number, not a
  project phase, and does not resolve against `docs/roadmap.md`'s Phase 1/2 vocabulary.
- `session.validator.ts:220` says "no M6 pool carries an upward-violation threshold" — still
  true (§1.3), but stated against the M6 pool set rather than the current one.
- `run-check.ts:62` cites "spec Part 6" and `capture-fixture.core.ts:60` cites
  `spec §"Seeded state is captured once"`, both without a file path.
- `synthesis.write.ts:59` documents `playerEntityId` as coming "from
  `character_sheet.data.entityId`", which is accurate, but the value arrives via an unchecked
  cast at `synthesis.controller.ts:161` rather than a parse.

**5.7 — `docs/decisions.md:597` describes a derivation signature the code no longer has.**
The entry says the derivation "maps `{ currentHp, maxHp, stress }` from the sheet". Those
field names were removed by `V10__character_sheet_drop_current_fields.sql`; the function reads
`{ entityId, maxHp, maxStress }` (`character-pools.ts:12-25`). **Doc/code disagreement.**

**5.8 — The `alvarez_armor` pool has no producer in code.** It exists in all 15 fixtures at
`{ current: 30, max: 30 }`. `deriveMothershipCharacterResourcePools` produces only `_hp` and
`_stress`; `saves.armor`/`saves.armorMax` on the sheet reach only the synthesis prose
(`synthesis.prompts.ts:41`). So the pool was minted by the model, either through
`initialState` at synthesis or a bootstrap delta during play. Under `getMothershipPoolDefinition`
it resolves to `DEFAULT_DEFINITION` — `min: null`, no thresholds — so it can go negative.
`docs/decisions.md`'s amendment names it explicitly: "plus an `alvarez_armor` that no
derivation produces."

**5.9 — `campaign_state.data` is cast, not parsed, on the read path.**
`session.service.ts:236` does `const campaignStateData = rawState as CampaignStateData;`
after a null check at `:227-231`. The only `.parse()` of `MothershipCampaignStateSchema` in
non-test code is `synthesis.write.ts:200`, on data the same function just built — its doc
comment (`:152-155`) says a failure there "indicates a programmer error in this function, not
a bad tool input". So a malformed or old-schema `campaign_state.data` row would flow through
the entire turn path untyped and unchecked.

**5.10 — Two `ResourcePool` type definitions exist outside the package.**
`campaign.repository.ts:9` and `synthesis.write.ts:16` each declare
`type ResourcePool = { current: number; max: number | null };` locally rather than importing
`ResourcePool` from `@uv/game-systems` (exported at `character-pools.ts:3`). The frontend
declares a third at `play-helpers.ts:9-12`, and the playtest app a fourth at
`apps/zoltar-playtest/src/lib/types.ts:25-28`. All four are currently structurally identical.

**5.11 — Threshold effects are strings with no consumer that interprets them.**
`HP_DEFINITION`'s single threshold carries `effect: 'death_save_required'`
(`pool-definitions.ts:21`). It flows into `ValidationResult.thresholds`
(`session.validator.ts:221-229`) and out to the frontend, where `formatThresholdLine`
(`play-helpers.ts:107-115`) does `t.effect.replace(/_/g, ' ')` and renders it as prose. No
code branches on the value.

**5.12 — Sheet updates are whole-blob replacements.** `CharacterRepository.update`
(`character.repository.ts:51-54`) does `.set({ data, updatedAt })` with the full validated
body. There is no partial-update endpoint and no jsonb merge, so any field the frontend form
does not round-trip is lost on save. `CharacterEdit.svelte` reads back and re-submits
`entityId`, `name`, `class`, `pronouns`, `stats`, `saves`, `maxHp`, `maxStress`, `skills`,
`equipment`, `notes` — but **not `level`**, which is restored to `1` by the schema default
(`character-sheet.schema.ts:15`) on every edit.
