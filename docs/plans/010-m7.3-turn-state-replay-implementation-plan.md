# M7.3 — Turn-State Replay Infrastructure: Implementation Plan

Multipart implementation plan for
`docs/specs/zoltar/010-m7.3-turn-state-replay-spec.md`. Each plan part is
sized for a manual code review and a single commit. Pause after each part
for review before starting the next.

Dependency order (not spec item order): consolidating the applier (spec
item 4) has to land before the replay function (item 6) can call it, and
the snapshot table (item 1) has to exist before `load-synthesis` (item 2)
or the legacy import (item 3) can read from it. `pending_canon.sequence_number`
(item 5) is independent of items 1–4 but is also a prerequisite for item 6.
That gives: **Part 1 (item 4) → Part 2 (item 1) → Part 3 (item 2) → Part 4
(item 3) → Part 5 (item 5) → Part 6 (item 6)**.

## Pre-flight corrections and decisions the spec left open

Resolved up front by reading the actual code, so each plan part can just
execute rather than re-derive:

- **Migration numbers.** Latest on `main` is `V15__adventure_status_aborted.sql`.
  Part 2 uses `V16__adventure_synthesis_snapshots.sql`; Part 5 uses
  `V17__pending_canon_sequence_number.sql`. Re-check `infra/db/migrations/`
  immediately before each part in case something else has landed on `main`
  in the meantime.
- **`adventure_synthesis_snapshots.schemaVersion` — the spec sketches one
  column, the data has two.** `SynthesisExport` (and the DB rows it's
  read from) carries *two* independent schema versions —
  `gm_context.schema_version` and `campaign_state.schema_version`
  (`synthesis-export.schema.ts:30-37`). The spec's storage sketch in item 1
  ("`schemaVersion`") is shorthand, not a literal single-column instruction.
  Part 2 uses two columns: `gm_context_schema_version` and
  `campaign_state_schema_version`.
- **The snapshot table is not itself `SynthesisExport`-shaped.** Spec item 1
  says the table "reuses the existing `SynthesisExport` Zod schema shape for
  the payload." Read literally that would mean storing `source.campaignId`/
  `campaignName` etc. redundantly inside the row. Since the table is already
  keyed by `adventureId` and lives in the same DB as `adventure`/`campaign`,
  those fields are joinable, not worth duplicating. Part 2 stores only
  `gmContextBlob`/`campaignStateData` + their schema versions; Part 3
  (`load-synthesis`) reassembles the full `SynthesisExport` shape by joining
  against `adventure`/`campaign` at read time, immediately before calling
  `parseSynthesisExport`. This is what "reuses the schema shape" cashes out
  to in practice — one shared Zod schema, assembled at the read boundary
  rather than stored pre-assembled.
- **`pending_canon` sequence key: plain `sequence_number` column, not a
  `game_event_id` FK** (spec's "Open Question for CC," item 5). Two reasons,
  both grounded in existing code:
  1. `adventure_telemetry` already solves the exact same problem the exact
     same way — `sequence_number integer NOT NULL` populated from
     `events.gmResponseSeq`, no FK to `game_event`
     (`schema.ts:436-455`, written at `session.repository.ts:622-627`).
     `pending_canon` should match that precedent, not invent a second
     pattern.
  2. A FK can't cleanly model it anyway: a single turn can propose *multiple*
     canon entries (`insertPendingCanon` takes `entries: Array<...>`,
     `canon.repository.ts:20-34`), all sharing one turn's sequence position.
     A `game_event_id` FK would need all of them pointing at the same
     `state_update` (or `gm_response`) row, which is legal SQL but adds a
     join for no benefit the plain integer doesn't already give — the
     replay query in Part 6 just needs `WHERE sequence_number < N`.
- **Old `pending_canon` rows can't be backfilled.** There's no `game_events`
  linkage recorded for canon entries inserted before this migration, so
  Part 5 adds the column nullable, backfills nothing, and only new rows
  (going forward) populate it. Pre-existing adventures are already a
  degraded case for replay purposes — same as the legacy-snapshot situation
  Part 4 handles by one-off import, not by making history perfect.
  **Future todo, not part of this milestone:** once the one legacy playtest
  adventure imported in Part 4 is no longer present in the database (deleted,
  archived, or simply aged out), nothing will depend on `sequence_number`
  being nullable — every remaining row will have been written by the
  post-Part-5 code path. At that point, flip the column to `NOT NULL` in a
  follow-up migration. Track this in `docs/decisions.md` or the roadmap when
  Part 5 lands so it isn't forgotten; don't attempt it in this plan.
- **`commitGmContext` retry-with-different-content is not a real flow**
  (confirmed by Alex, not just inferred from the code) — synthesis is
  committed exactly once per adventure in practice. This simplifies Part 2:
  the `onConflictDoNothing` snapshot-capture behavior has no known staleness
  risk to flag for review; it's simply correct. `writeGmContextAtomic`'s
  `onConflictDoUpdate` on `gm_context`/`campaign_state` exists for
  idempotent same-content retries (e.g. a network retry resubmitting the
  identical write), which `onConflictDoNothing` on the snapshot handles
  correctly too — no divergence.

## Part 1 — Consolidate `applyToCampaignState` and `mergeNpcAgendas` (spec item 4)

Foundational; Part 6 needs one pure function to fold state forward through,
and today the same job is split across a pure function
(`applyToCampaignState`) and an I/O-doing repository method
(`mergeNpcAgendas`).

**The target shape**, matching the spec's literal signature:

```ts
// apps/zoltar-be/src/session/session.applier.ts
export function applyValidatedTurn(input: {
  priorCampaignState: MothershipCampaignState;
  priorGmContextBlob: Record<string, unknown>;
  applied: ValidationResult['applied'];
  npcStates: Record<string, string>;
}): {
  newCampaignState: MothershipCampaignState;
  newGmContextBlob: Record<string, unknown>;
};
```

- `newCampaignState` computation is `applyToCampaignState`'s existing body,
  unchanged (`session.applier.ts:4-17`).
- `newGmContextBlob` computation is `mergeNpcAgendas`'s existing *pure* merge
  logic (`session.repository.ts:206-219`) lifted verbatim: shallow-merge
  `narrative.npcAgendas`, Claude's `npcStates` wins on key collision,
  everything else in the blob passes through unchanged. No-op path (empty
  `npcStates`) still produces the same blob object by value — see the
  behavior-change note below.
- Delete `applyToCampaignState` as a separate export; `mergeNpcAgendas`'s
  DB read/write wrapper is deleted from `session.repository.ts` entirely
  (see below).

**Move the I/O boundary, not just the merge logic.** This is the part of
the consolidation that isn't mechanical — it requires relocating *where*
`gm_context.blob` gets read, from inside `applyTurnAtomic`'s transaction to
`session.service.ts`, mirroring how `campaignStateData` already works
today:

- `session.service.ts:200-213` already loads the current `gm_context.blob`
  as `rawBlob` before the transaction (`this.repo.getGmContextBlob(...)`,
  Promise.all'd alongside `campaignStateData`). **Use `rawBlob` — not the
  local `gmContextBlob` at line 226-229 — as `priorGmContextBlob`.**
  `gmContextBlob` has `playerEntityIds` spliced onto it at those lines for
  prompt-building only (`session.snapshot.ts:14-19,39`: "Phase 5 supplies
  from a character-sheet lookup," never persisted). Passing the augmented
  object into `applyValidatedTurn` would write `playerEntityIds` into the
  `gm_context.blob` DB column, corrupting stored data. This is the single
  highest-risk mistake this part can make — call it out in the PR
  description and check for it explicitly in review.
- At `session.service.ts:326-330` (currently the `applyToCampaignState`
  call), call `applyValidatedTurn` instead, passing `rawBlob as
  Record<string, unknown>`, `campaignStateData`, `validation.applied`, and
  `finalParsed.gmUpdates?.npcStates ?? {}` (this last one needs to move up
  from where it's currently first read, at line 387 — `finalParsed` is
  already computed by line 357, so this is a reordering, not a new value).
  Destructure `{ newCampaignState, newGmContextBlob }`.
- `this.repo.applyTurnAtomic(...)` call (`session.service.ts:375-389`):
  replace `campaignStateData: finalState` with `campaignStateData:
  newCampaignState`, and replace `npcStates: finalParsed.gmUpdates?.npcStates
  ?? {}` with a new `gmContextBlob: newGmContextBlob` field.
- `session.repository.ts` `applyTurnAtomic` (`:529-649`): delete the
  `mergeNpcAgendas` call at `:580-584`. Add a plain write instead, in the
  same transaction, same position:
  ```ts
  await tx
    .update(schema.gmContexts)
    .set({ blob: args.gmContextBlob, updatedAt: sql`now()` })
    .where(eq(schema.gmContexts.adventureId, args.adventureId));
  ```
  Delete the `mergeNpcAgendas` method (`:182-225`) entirely — no remaining
  callers after this change (confirmed single call site).
- `ApplyTurnAtomicArgs` type: replace `npcStates: Record<string, string>`
  with `gmContextBlob: Record<string, unknown>`.

**Deliberate behavior change — flag in the PR description.**
`mergeNpcAgendas`'s old docstring (`session.repository.ts:186-187`) notes it
skips the write entirely when `npcStates` is empty, "to avoid a pointless
read/write that would invalidate the blob's cache byte range." That
optimization is dropped: the new write is unconditional, every turn,
matching how `writeCampaignState` (`session.repository.ts:170-180`)
*already* unconditionally writes `campaign_state` every turn regardless of
whether anything in `data` actually changed. This is a consistency
improvement (one write policy for both sibling objects, not two), traded
against `gm_context.updated_at` now bumping on turns with no NPC agenda
changes. Low risk — nothing currently reads `gm_context.updated_at` for
anything other than debugging/observability. The existing test asserting
the old no-op behavior (see below) is deleted, not preserved.

**Tests:**

- `apps/zoltar-be/src/session/session.applier.spec.ts` (new unit test file
  — pure function, no DB): covers `newCampaignState` merge (existing
  `applyToCampaignState` cases, if any exist today — check for and port
  them) and `newGmContextBlob` merge: new-key-into-existing agendas,
  Claude-wins-on-collision, empty `npcStates` produces a value-equal blob,
  non-`narrative` fields (`entities`, `structured`, etc.) pass through
  untouched.
- `apps/zoltar-be/src/session/session.repository.spec-int.ts`: delete the
  `mergeNpcAgendas` describe block (`:71-145` per current line numbers,
  re-check exact range at implementation time) — the method no longer
  exists. If `applyTurnAtomic` doesn't already have an integration test
  asserting the written `gm_context.blob` reflects merged `npcStates`, add
  one; if it does, extend it to also assert the merge (collision +
  passthrough), replacing the coverage the deleted describe block provided.
- `apps/zoltar-be/src/session/session.service.spec.ts` / `.spec-int.ts`:
  existing tests referencing `applyToCampaignState` or asserting on
  `npcStates` being passed to `applyTurnAtomic` need updating to the new
  shape. Search for `applyToCampaignState` and `npcStates:` across the
  `session/` directory to find every call site needing a signature update
  — the ones listed above are the ones confirmed during planning, but
  `grep -rn "applyToCampaignState\|mergeNpcAgendas"` across `src/` and
  `*.spec*.ts` before starting is the actual completeness check.

**Review gate.** `tsc --noEmit` clean. Unit + integration tests green. A
manual turn against a running backend produces an unchanged narrative and
correctly merges `npcStates` into `gm_context.blob` (verify with a `psql`
query pre/post-turn). Confirm by reading the diff that `priorGmContextBlob`
is sourced from `rawBlob`, not the `playerEntityIds`-augmented local.
Commit.

## Part 2 — Automatic turn-0 capture (spec item 1)

Depends on nothing from Part 1. New table + a hook into the existing
synthesis-commit transaction + removal of `save-synthesis`.

**Migration `infra/db/migrations/V16__adventure_synthesis_snapshots.sql`:**

```sql
CREATE TABLE adventure_synthesis_snapshots (
  adventure_id                   uuid        PRIMARY KEY REFERENCES adventure(id) ON DELETE CASCADE,
  gm_context_schema_version      integer     NOT NULL,
  gm_context_blob                jsonb       NOT NULL,
  campaign_state_schema_version  integer     NOT NULL,
  campaign_state_data            jsonb       NOT NULL,
  captured_at                    timestamptz NOT NULL DEFAULT now()
);
```

Written once per adventure, never updated (see below for the
`ON CONFLICT` handling that enforces this).

**Drizzle schema** (`apps/zoltar-be/src/db/schema.ts`): add
`adventureSynthesisSnapshots` mirroring the `pendingCanon` /
`adventureTelemetry` style already in the file (uuid PK referencing
`adventures` with cascade, `integer`, `jsonb`, `timestamp` withTimezone
defaultNow — no separate `id` column since `adventure_id` is the PK).

**Hook point:** `SynthesisRepository.writeGmContextAtomic`
(`apps/zoltar-be/src/synthesis/synthesis.repository.ts:45-92`), inside the
existing transaction, immediately after the `campaign_state` upsert
(after line 69, before the `grid_entity` insert). The values needed
(`args.gmContextBlob`, `args.campaignStateData`) are already in scope in
this method — no extra query needed, and note this is *not* the same as
reusing `buildSynthesisExport`'s query logic (that reads back already-
committed rows; this hook has the values in hand before they're even
written). What *is* shared is the shape: both this insert and
`buildSynthesisExport` ultimately produce the same
`{schemaVersion, blob}` / `{schemaVersion, data}` pairs, just from
different origins (fresh write here, DB read there).

```ts
await tx
  .insert(schema.adventureSynthesisSnapshots)
  .values({
    adventureId: args.adventureId,
    gmContextSchemaVersion: 1, // schema_version isn't in WriteGmContextArgs today — see note below
    gmContextBlob: args.gmContextBlob,
    campaignStateSchemaVersion: 1,
    campaignStateData: args.campaignStateData,
  })
  .onConflictDoNothing({ target: schema.adventureSynthesisSnapshots.adventureId });
```

- **Schema version values:** `WriteGmContextArgs` (`synthesis.repository.ts:19-30`)
  doesn't currently carry `gmContext`/`campaignState` schema versions — the
  inserts at lines 47-69 don't set them either, so Drizzle/Postgres defaults
  apply (check `schema.ts` for the `gmContexts`/`campaignStates` column
  defaults; `save-synthesis.core.ts:132` notes "default is 1 for pre-V14
  rows," implying the column has a default). If there's a column default,
  read the same default rather than hardcoding `1` in two places — or if
  simplest, hardcode `1` here matching what the write path implicitly
  produces today, with a comment noting it should track the `gm_context`/
  `campaign_state` table defaults if those ever change. Confirm the actual
  default value in `schema.ts` before writing this migration/insert — don't
  assume.
- **`onConflictDoNothing` — retry semantics, resolved.** `gm_context`/
  `campaign_state` use `onConflictDoUpdate` (lines 53-56, 66-69) while the
  snapshot uses `onConflictDoNothing`, which would only diverge if
  `commitGmContext` (`synthesis.service.ts:194-230`) were retried for the
  same `adventureId` with *different* synthesis content. Confirmed (Alex):
  that's not a real flow — synthesis commits once per adventure. No
  staleness risk; `onConflictDoNothing` is simply correct here, matching
  the spec's "written once ... never updated" instruction with no caveat
  needed.

**Remove `save-synthesis`:**

- Delete `apps/zoltar-be/scripts/save-synthesis.ts`,
  `apps/zoltar-be/scripts/save-synthesis.core.ts`,
  `apps/zoltar-be/scripts/save-synthesis.spec-int.ts`.
- `apps/zoltar-be/scripts/save-load-roundtrip.spec-int.ts` currently
  exercises save+load together — delete it here too (Part 3 rewrites
  `load-synthesis`'s own round-trip coverage against the new source, since
  "save" no longer exists as a discrete step to round-trip against).
- `load-synthesis.core.ts:9` imports `timestampLabel` from
  `save-synthesis.core.ts` — before deleting that file, move
  `timestampLabel` (and `slugifyCampaignName` if `load-synthesis` or Part 4
  needs it) into a small shared location, e.g. inline into
  `load-synthesis.core.ts` if it's the only remaining consumer, or a new
  `apps/zoltar-be/scripts/synthesis-shared.ts` if Part 4's one-off script
  also needs it. Check actual usage before deciding; don't create a shared
  file for a function with one caller.
- `Taskfile.yml:42-46` — remove the `playtest:save-synthesis` task.
- `.gitignore` entry for `apps/zoltar-be/synthesis-saves/` — remove (no
  longer produced).

**`truncateAll` test helper:** `apps/zoltar-be/test/db-test-helper.ts:72-93`
— add `'adventure_synthesis_snapshots'` to `TRUNCATE_TABLES`, in the
children-first section alongside `'pending_canon'` (before `'adventure'`).
Integration tests for Part 2 and later parts will silently see leftover
rows across tests without this.

**Tests:**

- `apps/zoltar-be/src/synthesis/synthesis.repository.spec-int.ts` (extend
  existing `writeGmContextAtomic` coverage, or add if none exists at this
  granularity): a successful `writeGmContextAtomic` call produces a row in
  `adventure_synthesis_snapshots` whose `gmContextBlob`/`campaignStateData`
  match what was written to `gm_context`/`campaign_state` in the same call.
  A second `writeGmContextAtomic` call for the same `adventureId` (simulating
  retry) does not change the existing snapshot row.

**Documentation:**

- `docs/schema.md` — add `adventure_synthesis_snapshots` to the schema
  reference, noting "written once at synthesis time, immutable."

**Review gate.** Migration applies cleanly on a clean DB (`task
flyway:migrate`) and the review-gate check from the M7.1 plan's Part 3
style: run it against a dirty DB too, confirm idempotent. `tsc --noEmit`
clean. Unit + integration tests green. Manually run `commitGmContext`'s
flow (create a new adventure through synthesis) against a dev DB, confirm a
row lands in `adventure_synthesis_snapshots` via `psql`. Commit.

  reads `apps/zoltar-be/scripts/load-synthesis.ts`'s positional arg as a

  Promise<SynthesisExport>`) replacing the `readFileSync` + `JSON.parse` +

- `Taskfile.yml:48-52` — update the `playtest:load-synthesis` task

## Part 4 — One-off legacy snapshot import script (spec item 3)

Small; depends on Part 2's table/schema. This is explicitly a one-time
migration script, not ongoing tooling — do not wire it into `Taskfile.yml`
as a `playtest:*` task alongside the real pipeline commands, to avoid
implying it's meant to be run repeatedly.

- New script, e.g.
  `apps/zoltar-be/scripts/one-off/import-legacy-synthesis-snapshot.ts`
  (a dedicated `one-off/` subdirectory signals "not part of the regular
  toolkit" — alternatively a name-prefixed file directly in `scripts/` if
  the team doesn't want a new subdirectory; either is fine, pick during
  implementation and note the choice in the PR).
- Args: `<path-to-legacy-synthesis.json> <adventure-id>` — the adventure id
  is required explicitly rather than trusting `source.adventureId` inside
  the file, since the file is old and the id should be verified against
  what's actually in the DB (guards against pointing this at the wrong
  target).
- Logic: `JSON.parse` the file, validate with the existing
  `synthesisExportSchema` (`synthesisExportSchema.safeParse`, same as
  `parseSynthesisExport` — reuse that function directly rather than
  re-implementing validation), confirm `parsed.source.adventureId ===`
  the CLI-provided adventure id (mismatch → hard error, don't silently
  proceed), confirm the `adventure` row exists in the target DB, confirm
  no row already exists in `adventure_synthesis_snapshots` for that
  adventure id (hard error if one does — this script inserts, it doesn't
  overwrite), then a single `INSERT INTO adventure_synthesis_snapshots`
  using the parsed `gmContext`/`campaignState` schemaVersion+blob/data.
- No Taskfile entry. Document the one-time invocation
  (`npx tsx --env-file=.env scripts/one-off/import-legacy-synthesis-snapshot.ts
  <path> <adventure-id>`) in the PR description, and run it once for real
  against whatever DB hosts the `playtest-2025-07-15.md` adventure as part
  of landing this part — that's the actual point of the script, not just
  having it exist.

**Tests:**

- A single integration test is enough given the throwaway nature: valid
  file + matching existing adventure → row inserted correctly. Mismatched
  adventure id → hard error, no row inserted. Adventure id already has a
  snapshot → hard error, existing row untouched.

**Review gate.** Integration test green. The script has actually been run
once against the real target adventure (not just tested against a fixture)
and a `psql` query confirms the row. Commit.

## Part 5 — `pending_canon.sequence_number` (spec item 5)

Independent of Parts 1–4; only needs to land before Part 6.

**Migration `infra/db/migrations/V17__pending_canon_sequence_number.sql`:**

```sql
ALTER TABLE pending_canon ADD COLUMN sequence_number integer;
CREATE INDEX pending_canon_adventure_seq_idx ON pending_canon (adventure_id, sequence_number);
```

Nullable — see the pre-flight note on why old rows aren't backfilled. Not
unique (per the pre-flight reasoning: multiple canon entries from one turn
legitimately share a sequence number).

- `apps/zoltar-be/src/db/schema.ts` — add `sequenceNumber:
  integer('sequence_number')` to the `pendingCanon` table def
  (`:343-362`), plus the matching index.
- `CanonRepository.insertPendingCanon` (`canon.repository.ts:20-34`) — add
  a required `sequenceNumber: number` arg; include it in the `.values(...)`
  mapping for every inserted entry (all entries from one call share the
  same turn, hence the same sequence number).
- `SessionRepository.applyTurnAtomic` (`session.repository.ts:570-574`) —
  pass `sequenceNumber: events.gmResponseSeq`, the same value already used
  for `writeAdventureTelemetry`'s `sequenceNumber` at line 625. This is the
  exact precedent cited in the pre-flight section — reuse the value that's
  already computed and in scope, don't compute a new one.
- Check `SynthesisRepository`'s `autoPromoteCanon` call — it doesn't insert
  rows, only updates status, so it's unaffected. Confirm no other
  `insertPendingCanon` call sites exist (grep before starting).

**Tests:**

  check; `canon.repository.ts` didn't show up with dedicated spec-int
  coverage during planning, confirm and add if missing): `insertPendingCanon`
  with a given `sequenceNumber` persists it on every inserted row; multiple

## Part 6 — The replay function (spec item 6)

Depends on Part 1 (`applyValidatedTurn`), Part 2 (`adventure_synthesis_snapshots`),
Part 5 (`pending_canon.sequence_number`). The largest single part; no
production code outside a new module is touched, so it's still a
contained review despite the size.

**Location:** `apps/zoltar-be/src/replay/reconstruct-state.ts`. A plain
`(db: Db, adventureId: string, targetSequenceNumber: number) => Promise<...>`
function, not a NestJS-injectable service — mirrors `buildSynthesisExport`'s
shape (`save-synthesis.core.ts:51`) so it's callable both from a future
M7.4 CLI/script and from in-process Nest code without presupposing which.
M7.4's own spec may dictate a different home for the *consumer*; this
function's placement can move then if needed, without changing its
signature.

**Contract on `targetSequenceNumber`:** must be the `sequence_number` of an
actual `player_action` `game_event` row for the adventure — the spec's
semantics ("state as of turn N... including the player's message that
triggers turn N") only makes sense anchored to a turn's first event. If no
`player_action` row has that exact sequence number, throw a clear error
(`ReplayError`, e.g.) rather than silently reconstructing a boundary no
real turn corresponds to. This contract isn't explicit in the spec's
pseudocode signature but is required to implement step 5 (messages) — make
it a documented precondition on the function.

**Step 1 — turn-0 baseline:**

```ts
const [snapshot] = await db
  .select()
  .from(schema.adventureSynthesisSnapshots)
  .where(eq(schema.adventureSynthesisSnapshots.adventureId, adventureId))
  .limit(1);
if (!snapshot) throw new ReplayError(`no synthesis snapshot for adventure ${adventureId}`);
let campaignState = snapshot.campaignStateData as MothershipCampaignState;
let gmContextBlob = snapshot.gmContextBlob as Record<string, unknown>;
```

**Steps 2–3 — fold forward.** The spec's pseudocode ("for each event's
logged payload, call the unified applier") undersells the real shape: not
every `game_event` row carries a piece of the fold. Per
`writeTurnEvents` (`session.events.ts:81-185`), a turn's events are written
in this fixed order, always within one transaction: `player_action` →
zero or more `dice_roll` → `gm_response` → optional `correction` →
`state_update`. Only two of those carry data the applier needs:

- `state_update.payload` is exactly `{applied: ValidationResult['applied'],
  thresholds: [...]}` (`session.events.ts:175`) — the `applied` half of
  every fold-forward step.
- `gm_response.payload.gmUpdates.npcStates` (via `gmPayloadFor`,
  `session.events.ts:187-195`) is the `npcStates` half — **unless** a
  `correction` event exists for that same turn, in which case
  `correction.payload.gmUpdates.npcStates` is the one that was actually
  applied (matches `session.service.ts:357`'s `finalParsed = correctionParsed
  ?? originalParsed`, and confirmed by `session.events.ts:161-164`: the
  original `gm_response` row's `supersededBy` points at the correction row,
  written immediately after it, before `state_update`).

Fold algorithm, single forward pass over `game_events WHERE adventureId = ?
AND sequenceNumber < targetSequenceNumber ORDER BY sequenceNumber ASC`:

```ts
let pendingNpcStates: Record<string, string> = {};
for (const event of events) {
  if (event.eventType === 'gm_response' || event.eventType === 'correction') {
    pendingNpcStates = (event.payload as any).gmUpdates?.npcStates ?? {};
    // a correction row, if present, always comes immediately after its
    // gm_response and before the turn's state_update, so this simply
    // overwrites the gm_response's value with the winning one.
  } else if (event.eventType === 'state_update') {
    const { newCampaignState, newGmContextBlob } = applyValidatedTurn({
      priorCampaignState: campaignState,
      priorGmContextBlob: gmContextBlob,
      applied: (event.payload as any).applied,
      npcStates: pendingNpcStates,
    });
    campaignState = newCampaignState;
    gmContextBlob = newGmContextBlob;
    pendingNpcStates = {};
  }
  // player_action / dice_roll: no state contribution, skip.
}
```

Reads `event.payload` as `Record<string, unknown>` off the DB — cast with a
narrow inline type or a small Zod check, since this is historical data
being trusted at replay time, not re-validated (replay replays already-
validated deltas; it does not re-run `validateStateChanges`).

**Step 4 — `pending_canon` baseline:**

```ts
const pendingCanon = await db
  .select()
  .from(schema.pendingCanon)
  .where(and(
    eq(schema.pendingCanon.adventureId, adventureId),
    lt(schema.pendingCanon.sequenceNumber, targetSequenceNumber),
  ))
  .orderBy(asc(schema.pendingCanon.sequenceNumber));
```

Rows with `sequenceNumber IS NULL` (pre-Part-5 legacy rows) are correctly
excluded by `lt(...)` against a NULL column — confirm this is the desired
behavior (it is, per the pre-flight note: pre-migration adventures are a
degraded case for replay, not a blocker).

**Step 5 — messages:**

```ts
const [turnStartEvent] = await db
  .select({ createdAt: schema.gameEvents.createdAt })
  .from(schema.gameEvents)
  .where(and(
    eq(schema.gameEvents.adventureId, adventureId),
    eq(schema.gameEvents.sequenceNumber, targetSequenceNumber),
    eq(schema.gameEvents.eventType, 'player_action'),
  ))
  .limit(1);
if (!turnStartEvent) throw new ReplayError(`no player_action at sequence ${targetSequenceNumber} for adventure ${adventureId}`);

const messages = await db
  .select()
  .from(schema.messages)
  .where(and(
    eq(schema.messages.adventureId, adventureId),
    lte(schema.messages.createdAt, turnStartEvent.createdAt),
  ))
  .orderBy(asc(schema.messages.createdAt));
```

Relies on the player message being inserted (`session.service.ts:241-247`)
strictly before the `player_action` event in the same `sendMessage` call —
true today (message insert happens before the transaction that writes
`player_action` even opens) and is the same ordering property the spec
explicitly says is out of scope to change.

**Return shape** matches the spec's signature exactly:
`{campaignState, gmContextBlob, pendingCanon, messages}`.
