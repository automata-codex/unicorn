### Task 2 — Hand-score the before-queries · Alex · ~1 evening

Worksheets are generated and waiting:

- `$ZOLTAR_EVAL_ROOT/eval-runs/query-worksheet-sonnet5-before.md` — **106 rows,
  14 turns** (start here)
- `$ZOLTAR_EVAL_ROOT/eval-runs/query-worksheet-sonnet46-before.md` — 287 rows,
  15 turns

Produced by `task eval:query-worksheet -- <run-dir> --output <path>`. **Use the
script for the after-set too**: the pairing is only valid if both halves came
out of it, and a hand-assembled second worksheet invites a reordered column or
a differently-escaped pipe that breaks the join silently.

Rows carry a stable `row` id scoped to their turn (`turn19-…/03`), so labels
join back even if rows move — Task 8 needs that.

Three judgments per query, plus two hint columns the script fills in:

| Col | Question |
|---|---|
| **C** | Is this mechanic **in the book**? A factual label, not blame |
| **N** | Did the **situation** call for a lookup at all? Judged from the player input alone |
| **E** | Does the query **express what was needed**? |
| **P** | Does the **primer** answer this? Pinned to a prompt revision |

**There is deliberately no "was this warranted" column.** The first version had
one, defined as "asks about a mechanic Mothership does not have," and it was
circular — the Warden cannot know the book lacks a cover bonus without looking.
`C` replaces it as a *fact about the query*: excusable in the before-set,
inexcusable in the after-set where the mechanical-model primer states it
outright. That asymmetry is how the primer's effect becomes visible, and it is
why warrant is not a fixed property of a query.

Score `y` / `n` / `?`, and **`—` where a column does not apply**. `E` is
undefined when `N=n` — no lookup was needed, so there was no need to express —
and that is `—`, not `?` and not `n`. `?` means "looked and could not decide,"
a real state; `—` means the question has no referent. Keeping them apart is the
same discipline that keeps `NOT_APPLICABLE` out of the structural checkers'
denominators. So `E`'s rate is over `N=y` rows only and must be reported with
that denominator beside it: row counts move between before and after, and a
rate improved by its hard cases dropping out is exactly what `eval:compare`'s
App/ΔApp columns exist to expose. `C` is independent of both.

**`C` and `P` are two different corpora and they never mix.** `rules_lookup`
searches `rules_chunk`, populated from the book alone; the primer lives in the
Warden system prompt and is never embedded or indexed. `C` asks whether
retrieval could *ever* have succeeded; `P` asks whether the Warden had already
been told. The book often answers only by omission — it never says "narrate
what a character sees instead of rolling" — while the primer says so outright,
and that gap is what `P` measures.

`C` cannot show the primer working: the corpus is held constant, so `C` for a
given query is identical before and after. The primer's effect appears as a
falling `C=n` **rate**, never as a label changing. `P` on the before-set is a
**prediction** of which queries should disappear; in the after-set a `P=y`
query still emitted is a primer that was ignored, and a `P=n` query still
emitted is a primer gap. `P` is scored against one prompt revision, named in
the worksheet header, and goes stale when the primer moves.

`$ZOLTAR_EVAL_ROOT/eval-runs/query-worksheet-rubric.md` — **the after-set must

Results in `docs/rules-extraction-findings.md § S25`.

Model it on `eval/checks/judged/rubrics.ts`, which holds one rubric per tag:
question, what passes, what violates, and the examples that fix the borderline.
Write it as you go; the borderlines are what you cannot anticipate, and those

**Do not score "did it retrieve the right thing" by hand** — that is Task 3's

**The retry-cascade failure mode does not exist in this corpus, and the
worksheet proves it rather than assuming it.** The `R` column groups

## 4. Traps

Each of these was learned the hard way in this milestone. Do not re-derive.

### Trap 1 — MRR is noisy; read `recall@3` as the verdict

Eight scorings at one unchanged configuration read
`0.856 0.856 0.856 0.842 0.856 0.842 0.856 0.842`. The spread is 0.0135 =
0.5/37 exactly — **one fixture alternating between rank 1 and rank 2**,
because `hnsw` is an *approximate* index and two chunks whose similarity
differs in the third decimal have no guaranteed traversal order.

`recall@3` was identical on all eight runs, and on every run of every round.

`§ S18` originally reported three identical 0.856 readings as evidence the
variance had gone away. It had not; three samples was luck. **Repeating a run
three times is not enough to establish stability when what you are testing for
is occasional reordering.** (`§ S22`, `docs/eval-methodology.md § Outcome`.)

### Trap 2 — A label fix is not an improvement

`§ S15.6`: a labelling pass raised recall from 91.9% to 94.6% **with the index
unchanged**. The ruler moved, not the thing being measured. If Task 1 closes
the bar, say so in exactly those terms.

### Trap 3 — Hold the corpus constant across before and after

Any query-side metric scored against the index must be run against the *same*
index for both readings, or it measures two things at once. `eval:query-vocab`'s
before-numbers were deliberately computed against the current 61-chunk index
even though those runs executed against an empty one (`§ S21.1`). Tier 2
inherits this: build it whenever, run it after the index freezes.

### Trap 4 — "pp.12-13 are missing" overstates the gap

The README and `§ S19` say the empty-table defect removes pp.12-13 and that
"equipment stat queries will miss." The pages are absent, but **the complete
weapons table is on printed p.2** and is retrievable. `§ S19.5` concluded the
fixup-patch condition had "fired with evidence on both halves" — the mechanism
evidence was real (p.12 content does retrieve for `rq-015`), but nobody checked
whether the same information was already available elsewhere. It was. Fix these
claims when Task 1 resolves.

### Trap 5 — Checkers branch on field *presence*, never on `fixtureSchemaVersion`

`eval:rescore` re-grades frozen `88fa84bd8329` artifacts that predate the
`roll_dice` fields entirely. Version-gating is the obvious mechanism and the
wrong one: the fixture version records what `capture-fixture` captured, and it
captures **no game events at all**. `FIXTURE_SCHEMA_VERSION` stays at 2.

### Trap 6 — Verify every mechanical claim against the index

Writing the Warden's mechanical-model primer from memory produced three errors
that would have shipped: `Sensors` (zero chunks — not a Mothership term),
"everything is roll-under" (Panic Checks roll *high* against Stress), and
"90-99 is a Critical Failure" (Criticals are doubles; 90-99 is a separate
auto-fail rule). A wrong primer is worse than none for the same reason
`chunk.py` gives for a wrong breadcrumb: it is read and acted on, not merely
displayed.

```bash
source .env
psql "$DATABASE_URL" -c "select count(*) from rules_chunk where content ilike '%<term>%';"
```

### Trap 7 — `templates/` is tracked, and fixup text is book text

**This trap previously said the opposite, and the correction is the point.**
An earlier version claimed `ingestion/mothership/{system.json,fixups.json,
hashes,templates}` were "all gitignored under the licensing posture," and that
a fresh clone would therefore ingest without the page exclusions.

None of that is true. **There is no `ingestion/.gitignore`.** The claim came
from a compound shell command whose `ls ingestion/mothership/` output —
literally `fixups.json / hashes / system.json / templates` — was read as the
contents of a gitignore file it happens to resemble. The only ignored artifact
under `ingestion/` is `.ingest-manifest.json`.

Two consequences, one good and one open:

- **Good:** `drop_pages` is committed. A fresh clone *does* get the page
  exclusions, and rounds 1 and 2 committed `system.json` regardless of what
  their commit messages claimed.
- **Open:** `templates/` is tracked, so authoring a fixup would commit
  transcribed book text by default. See Task 4(a)'s prerequisite. The wrong
  belief was masking a real licensing question rather than creating a fake one.

**The generalisable lesson:** a directory listing and a gitignore file are
indistinguishable when both are bare filenames, and `cat missing-file
2>/dev/null` prints nothing rather than complaining. Verify a
tracked-vs-ignored claim with `git check-ignore` or `git ls-files`, never by
eyeballing output you did not attribute to a specific command.

### Trap 8 — The stopping rule fired; do not casually add rounds

Three rounds moved aggregate `recall@3` by 0.0 pp. The milestone closes on the
shortfall condition, and `§ The stopping rule` is explicit that an unmet bar
honestly recorded is a success while one chased indefinitely is not. Round 4
is recorded as a deferral with its predicted outcome — run it as a deliberate
decision, not as one more round because the last one was interesting.
